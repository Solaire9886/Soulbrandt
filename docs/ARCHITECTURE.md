# Architecture

Canonical reference for how the Soulbrandt asset-import pipeline works today: what this
is, current conventions, format quirks, known gotchas, and what's still missing. `docs/PLAN.md`
has the roadmap — why things are built this way and what's coming. `docs/context.md` has the
session-by-session investigation history: the real bugs already found and fixed (with how
they were confirmed, not just guessed), interop gotchas, environment quirks, and dead ends
already tried and rejected — optional reading, useful for the *why* behind something here
or to check whether an approach has already been ruled out. `AGENTS.md` is the AI-agent
operating-instructions file and just points here for anything substantive.

Deep VFX/map-shading research write-ups and an evidence-driven investigation-method
checklist exist as a separate, external research archive (not tracked in this repo) —
ask the maintainer if you need one of them; the findings worth keeping are folded into
this document and `docs/context.md` directly, as elsewhere in this file.

## What this is

A Godot 4.7 (.NET/C#) project building a native asset-import pipeline for **Demon's Souls (PS3)**, reading FromSoftware's proprietary formats (FLVER0 meshes, TPF textures) directly into Godot resources. Project display name is "Soulbrandt"; the C# assembly/csproj is `Soulbrandt` too (`project.godot`'s `[dotnet] project/assembly_name` matches) — renamed from an old `Boletaria` codename, kept only as flavor text in a few in-code comments referring to the *in-game* kingdom of Boletaria, unrelated to the project name.

No game assets are bundled in this repo. `mounted` (gitignored) holds the user's own game copy, populated by an in-editor mount action — see "Asset mounting" below.

The repo (`github.com/Solaire9886/Soulbrandt`) is public and licensed **GPLv3** — not an arbitrary choice: `SoulsFormatsNEXT` (see below) is GPLv3 with no linking exception, and this project links against it directly, so the combined distributed work must be GPLv3 too. `README.md` carries an RPCS3-style disclaimer (no proprietary assets, no piracy support, no DRM-bypass methods); `CONTRIBUTING.md` covers the contributor workflow.

## Object VFX integration update (2026-09-15)

`MapSfxPreview` now accepts map-scoped, deduplicated object/dummy effect requests using
its existing cache, LOD selection and shared budgets. An opt-in **Preview Reviewed Object
Effects** inspector switch enables documented archstone, wagon and wisp examples in four

VFX have no consumer.

The shared map VFX controller now supports an opt-in **Preview Camera Region Effects**
switch for the reviewed Latria/Stonefang/Valley script regions. Latria94200 and Stonefang96000
render; Valley95202 still reports its unsupported recipe. Region unions preserve one camera

source adapter, not Lua execution.

## Map shading fix (2026-09-15)

Fresh native instruction comparisons found, and this pass corrected, three material-equation
bugs: (1) `lightmap_common.gdshaderinc`/`terrain_blend.gdshader` each multiplied by a
hard-coded `0.6` on top of the material's own `diffuse_tint` (which already carries
`g_DiffuseMapColorPower`, usually `0.6`) — that hard-coded factor is deleted, not replaced;
(2) `env_specular` (`hemisphere_ambient.gdshaderinc`) had no material-level specular
scaling at all — a `specular_tint` uniform (`g_SpecularMapColor * g_SpecularMapColorPower`,
`MtdShading.SpecularTint`) is now bound and multiplied in, on both `BuildLightmapMaterial`
and `BuildBlendMaterial`; (3) `terrain_blend.gdshader` read only `COLOR.a` (the layer-blend
weight) and discarded `COLOR.rgb` as an unknown signal — native `Mul`-family HemEnv programs
use it as a free multiplier on both the blended diffuse and the blended RGB specular, same
role the single-layer family's vertex colour already played, and specular1/specular2 are now
sampled `.rgb` instead of `.r`. The full evidence and derivation this was implemented from
is in the external research archive (`MAP_SHADING_ACCURACY_2026_09_15.md`, not tracked in
this repo). **Not done in this pass** (per that document's "Recommended implementation and
verification order" and "Remaining accuracy leads and limits"): a real rendered A/B
comparison, and the adaptation/bloom/fog/shadow items it explicitly separates out. This
supersedes the older assertions below (in "The DeS
rendering pipeline, reconstructed") that an additional universal HemEnv `0.6` was correct
and that terrain vertex RGB was unused.

## Standing priority: stability and resource safety

The importer works and is good at what it resolves — but getting it *working* has so far taken priority over getting it *safe to run unsupervised, at scale, on hardware that isn't this dev machine*. That needs to change as the project grows. The end goal (see `docs/PLAN.md`) is a regular, non-technical user pointing this at their own full game copy and eventually playing a recreation built on it — the same extraction/import machinery they'd run has to be far more resilient than "usually works, re-run it if it doesn't."

This isn't a hypothetical concern — doc history already shows real instances (all pre-2026-07-24, several since closed structurally rather than individually — see the note at the end of this section): a genuine FLVER0 vertex-layout crash that needed a corpus-wide fix before a bulk reimport was even reliable; a `Fatal error. Invalid Program: attempted to call an UnmanagedCallersOnly method from managed code` flake that killed a bulk reimport mid-batch and was just re-run to recover, not root-caused; a real case (post editor-crash) of 1395/3411 `.flver.import` files left pointing at cache artifacts that were never actually written — silently invisible to a later incremental `--import`, not a loud failure; and a real-rendering-driver verification path that's explicitly documented as too heavy to ever run concurrently with the GUI editor or another such check. None of these were caught by design — they were each found the hard way, after the fact.

Going forward, hangs, crashes, and runaway CPU/memory/disk usage anywhere in the extraction/import pipeline are treated as bugs worth root-causing, not flakes to route around by re-running — a shipped tool a regular user points at their own multi-GB game copy doesn't get the "just try again" luxury a dev-only reimport does. Concretely, this shapes future importer/extractor work: prefer failing safely and detectably (bounds on memory/CPU/time, resumability from partial progress) over silent retries or leaving corrupted intermediate state — the stale `.import` cache case above is exactly the failure shape to design against. An already-investigated, confirmed-external cause (e.g. Godot's own threaded-import-host bug) is fine to leave documented as a known flake; a newly-seen one is not, until it's actually been looked into.

**Most of the specific instances listed above no longer apply, structurally, not because they were individually patched.** The 2026-07-24 architecture pivot (see "Architecture" below) removed `EditorSceneFormatImporter` registration for `.flver` entirely — `.flver` is no longer a Godot-recognized resource type, so Godot's own threaded reimport queue never dispatches against it at all anymore. That closes the stale-`.flver.import`-metadata case, the `UnmanagedCallersOnly` reimport flake, and the concurrency self-throttle's whole reason for existing (all three were specific to that queue) as a side effect of removing the mechanism they depended on, not because each was individually root-caused and fixed. The general principle — fail safely and detectably, don't paper over hangs/crashes with retries — still applies fully to what's left: `AssetExtractor.cs`'s extraction step (still real I/O against a user's own multi-GB game copy) and `FlverLoader.cs`'s manual load path (still real parsing/decode work, just no longer routed through Godot's import system). This pivot doesn't make this category of risk go away in general — it removed one specific, well-documented source of it.

## Build & verify

Godot's own C# tooling (`GodotTools`, used by the editor's build/import machinery) hardcodes a `net8.0` requirement with no cross-major rollForward. Installing a .NET 8 SDK alongside whatever newer SDK is already present (via your distro's package manager where one packages it, or the official direct download from dotnet.microsoft.com otherwise) satisfies this with no manual `DOTNET_ROOT` override needed — plain `dotnet`/`godot-mono` on `PATH` resolves it. (An earlier revision of this doc had a manual merged root at `~/.dotnet-godot`, under the mistaken assumption that no distro packaged a net8 SDK at all; confirmed obsolete and dropped — see `docs/context.md`'s "Environment specifics" section for the full history.)

**Build the C# assembly** (do this after any change under `addons/archstone/`):
```
dotnet build Soulbrandt.csproj
```
Do **not** use `godot-mono --headless --build-solutions` to build — it reliably hangs in this environment. Plain `dotnet build` against `Soulbrandt.csproj` is the proven path.

**There is no `res://` reimport step anymore, and no unit test suite.** `.flver` is not a Godot-recognized resource type at all — no `EditorSceneFormatImporter` is registered for it (see "Architecture" below for why, and docs/context.md's reimport-concurrency entry for the full removal story). This means the entire "Force a reimport" batching recipe, per-batch cache invalidation, stale-`.flver.import` diagnosis, and "zero errors across a full bulk reimport" verification standard that used to apply here are gone, not just outdated — there is no reimport queue left to invalidate or batch. Everything from `mounted/` through to a visible model in the editor is driven by explicit user action (`FlverLoader.cs`, triggered from the Archstone toolbar's "Load Model(s)..."/"Load Folder..." — see "Asset mounting" below), not Godot's own import machinery.

Verification is done with throwaway `SceneTree`-extending GDScript scripts run headlessly, e.g.:
```
godot-mono --headless --path . -s check.gd
```
where `check.gd` does `load("res://addons/archstone/scripts/FlverLoader.cs").new().Instantiate("res://mounted/chr/c9999/c9999.flver")` and inspects the resulting node tree (surface count, `surface_get_material(i).albedo_texture`, etc. — the child is a real `MeshInstance3D`/`ArrayMesh` now, see "Architecture" below). No import/reimport/cache-invalidation step is needed at all — `FlverLoader` reads straight from `mounted/` on every call unless its own in-memory cache already has that path (`Evict`/`EvictAll` bust it manually). Write these scripts to a scratch location and delete them when done — none should be committed.

**`--headless` never actually compiles GLSL.** It forces Godot's dummy rendering driver, which happily loads/saves `ShaderMaterial`/`Shader` resources and reports zero errors regardless of whether the shader source is even valid — a clean `FlverLoader` load only proves the *build step* (material building, texture resolution) didn't throw, not that any new or edited `.gdshader`/`.gdshaderinc` actually compiles. Confirmed the hard way: a real shader-compile bug (Godot's built-ins like `ALBEDO` aren't assignable from a helper function, even a `#include`-d one only ever called from `fragment()`) shipped straight through a headless check with zero errors and only surfaced as broken rendering once opened for real. To actually catch shader errors, force a real rendering driver: `xvfb-run -a godot-mono --path . -s check.cs --rendering-driver opengl3 --display-driver x11` (needs `Xvfb`/`xvfb-run`, both in most distros' repos) — errors print as `SHADER ERROR: ...` with a file/line. This spins up real (software, via Mesa llvmpipe) GPU rendering, which is far heavier than a normal headless run — never run it while the GUI editor or another such check is also open; see docs/context.md's environment-specifics section on why concurrent Godot processes against this project are unsafe in general.

## Architecture

**There is no `EditorSceneFormatImporter` anymore — `.flver` is not a Godot-recognized resource type at all.** This is a deliberate 2026-07-24 pivot, not an oversight: an earlier `FlverSceneImporter.cs` did register one, but registering *any* `EditorSceneFormatImporter` for `.flver` meant every `res://mounted` filesystem scan (including the one that used to run automatically right after extraction) queued every `.flver` through Godot's own threaded reimport dispatch — the root cause of a hang → `systemd-coredump` CPU spike → crash cycle that a concurrency self-throttle inside the importer couldn't fully fix, because the instability traced to Godot's own reimport-host machinery, which a plugin has no control over (confirmed by reading Godot's engine source directly — see docs/context.md's reimport-concurrency entry for the full investigation, including the two confirmed dead ends: no `_can_import_threaded()` hook exists on this base class, and the `threading/worker_pool/max_threads` project setting is hardcoded-ignored for the editor process). The fix was architectural, not a tighter gate: stop routing `.flver` through Godot's import system at all.

The logic is split across two files instead:
- **`addons/archstone/scripts/FlverModelBuilder.cs`** — all the real FLVER0 parsing/mesh/material/texture-resolution logic, with zero dependency on Godot's import system. `BuildMesh(path, out anySurface)` reads a `.flver` straight from disk and returns an `ImporterMesh` with every surface's material already resolved (`StandardMaterial3D`, or `ShaderMaterial` for terrain-blend/water/lightmap materials, see below) — there is no intermediate OBJ/MTL/PNG file relay. (`desflver_test/`, an old standalone reference console app used early on for manual FLVER-parse comparison, has been removed — everything it covered now lives here and in this doc; its OBJ-export quirks, V-flip and triangle winding swap, never applied to the native path anyway — see the FLVER↔Godot conventions below.)
- **`addons/archstone/scripts/FlverLoader.cs`** — a plain `RefCounted`, one instance per editor session (created in `archstone.gd`'s `_enter_tree()`), holding a `FlverModelBuilder` plus its own session-lifetime `Dictionary<string, ArrayMesh?>` cache keyed by path. `Instantiate(path)` builds-or-reuses a mesh and returns a fresh `Node3D` wrapping a `MeshInstance3D` for that placement; `Evict`/`EvictAll` bust the cache (for after an importer-code change — no reimport step to force, just call this and load again). `EvictAll` also calls `FlverModelBuilder.ResetCaches()` (2026-07-26), clearing its texture-resolution caches (`_dirTextureCache`/`_decodedTextureCache`/the sibling-obj index below) too — not needed for a code-only change, since nothing on disk moved, but covers re-running "Import" mid-session to pull in new/changed `mounted/` content (e.g. testing modded assets) without needing a full editor restart to see it. Only ever called from one thread at a time (a toolbar button click), so its cache is a plain `Dictionary`, not `ConcurrentDictionary` — there's no Godot-owned scheduler dispatching concurrent calls against it the way the old importer had. `InstantiateMap(msbPath)` (2026-07-24, see "MSB map placement" below) builds on this same cache: it's one `Instantiate()` call per resolved map-piece, so a model reused across placements or maps only parses once.
- **`addons/archstone/scripts/MsbLoader.cs`** (2026-07-24) — pure `.msb` parsing/resolution, no scene nodes, mirroring the split above. `ReadMapPieces(msbPath)` reads a `.msb` via `SoulsFormatsNEXT`'s `MSBD`, resolves each `MapPiece` part's `ModelName` against the sibling model-bucket folder (`mapstudio/{name}.msb` ↔ `map/{name}/`, a confirmed 1:1 naming convention), and returns each part's model path plus real `Position`/`Rotation`/`Scale`. See "MSB map placement" below for scope and the still-open rotation-correctness caveat.
- **`addons/archstone/scripts/archstone.gd`**'s Archstone toolbar button now has four loading-related menu items alongside Mount/Import/Clear: **"Load Model(s)..."** and **"Load Folder..."** (both `EditorFileDialog`, `ACCESS_FILESYSTEM`, rooted at `mounted/` — the same proven dialog type already used for "Mount...", not a custom file browser) call `FlverLoader.InstantiateWithDefaultDrawParams()` for each resolved `.flver` path (that's `Instantiate()` plus `default_lightbank.param` row 0 bound, so a standalone model isn't stuck on shader defaults — see "Known deferred work") and drop the result under the currently-selected Scene-dock node (if it's a `Node3D`) or the edited scene's root; **"Load Map..."** (same dialog pattern, rooted at `mounted/map/mapstudio`, filtered to `*.msb`) calls `FlverLoader.InstantiateMap()` per selected `.msb`; and **"Reload Loaded Models"** calls `FlverLoader.EvictAll()`. An earlier version of this used a custom `Tree`-based dock for browsing/selecting files instead of `EditorFileDialog` — dropped after it proved unreliable in the live editor (rows wouldn't expand) in a way that couldn't be diagnosed blind; `EditorFileDialog` is Godot's own well-tested control, already working elsewhere in this exact file, so reuse beat continuing to debug a from-scratch `Tree` implementation.

**MSB map placement (2026-07-24) — map-piece placement only; the "decorations at the origin" bug this surfaced turned out to be a separate, now-fixed `FlverModelBuilder` gap, not an MSB problem.** `FlverModelBuilder` used to have no concept of map layout at all — bulk-loading a map folder just dropped every loose `.flver` at the origin. `MsbLoader`/`FlverLoader.InstantiateMap()` fix this for `MSBD.PartsParam.MapPieces`: `Position.X` is negated the same way `FlverModelBuilder`'s own vertex-position convention already does, and `RotationDegrees.Y`/`.Z` are negated to compensate the same mirror while `.X` is left alone. Corpus-checked, not assumed: most `MapPiece` parts carry an identity `Position`/`Rotation` in `MSBD` itself (a single-instance piece's placement lives in its own FLVER data, not MSB — see the rigid mesh-to-node binding entry above), but a real minority are genuinely reused multiple times and do carry a real per-instance MSB transform — e.g. `m08_00_00_00` has one model (`m0001B0`) placed **nine** separate times (`m0001B0_0000`-`_0008`, corrected from an earlier "seven" estimate) at nine distinct positions/rotations. **Spot-checked, not fully proven (2026-08-17):** rendered the five-instance `m0001B0_0000`-`_0004` chain (all pure-Y rotations, `-90°` to `149°`) headlessly under a real rendering driver and read the resulting image directly — it forms one continuous, non-mirrored rock formation whose curve matches the rotation sequence, with no piece inside-out, backwards, or disconnected. Only `RotationDegrees.Y`'s sign is actually exercised by this case (`.X`/`.Z` are `0` on every real instance checked so far); this naturalistic rock geometry also lacks the strong directional cues (text, a doorway, an asymmetric architectural feature) that would make a subtle handedness flip obvious, so treat this as good supporting evidence rather than the same confirmation bar the X-negation/winding-swap conventions above were held to — a stronger test case, if one turns up, would still be worth the same visual check. `MapPiece`-membership itself is real, working value regardless: it's now possible to tell which `.flver` files in a block folder are actually placed versus sitting there unreferenced — see "Known deferred work" below for how this relates to the Boletarian Palace z-fighting question. User testing of this first slice found real placement bugs (gates/fountains/whole building interiors sitting at the world origin) that turned out to be caused by `FlverModelBuilder` ignoring FLVER's own rigid mesh-to-node binding, not by anything in `MsbLoader`/`InstantiateMap` — now fixed, see the coordinate-conventions entry above and docs/context.md. Scoped to `MapPieces` only this pass — `Objects`/`Enemy`/`Player`/`Collision`/`Navmesh` parts are explicitly deferred (see "Known deferred work"). `LightID` → `LIGHT_BANK` resolution shipped 2026-08-17 (see "Lightmaps" below); `FogID` → `FOG_BANK` → `des_fog` distance fade shipped 2026-09-04 (part 45).

**`Objects` placement shipped (2026-08-17) — props/decorations/interactible scenery (`MSBD.Parts.Objects`), the second real part category after `MapPieces`.** `MsbLoader.ReadObjects()` resolves each `Object` part's `ModelName` (e.g. `o0300`) against the mounted `obj/` corpus rather than a map block folder — a genuinely different, but simpler, resolution rule: every mounted `obj/` container splits its `.flver` into its own `sib/` subfolder (`obj/{id}/sib/{id}.flver`, confirmed 100% consistent across all 777 real mounted `obj/` folders, not a guessed convention), so no directory scan or fallback chain is needed, just a deterministic path. `MsbLoader`'s placement-construction logic (position/rotation/scale/`LightID`/`FogID` extraction) is now shared between `ReadMapPieces`/`ReadObjects` via a private `BuildPlacements()` helper taking a per-category model-path resolver, rather than duplicated. `FlverLoader.InstantiateMap()` places both `MapPieces` and `Objects` under the same root, sharing the identical transform/lighting logic (`InstantiatePlacement()`) — texture resolution needs no new code at all, since `FlverModelBuilder`'s existing `CandidateDirs` chain already handles every obj/ container the same way it does for direct "Load Model(s)..." loads. Verified against real data: `m01_00_00_00` (Nexus) goes from ~60 `MapPieces`-only placements to 209 total (206 with mesh, 3 meshless — the same already-documented dummy-marker FLVER0 case, not new); `m08_00_00_00`'s 28 real `Objects` all resolved and placed with no crash. `Enemy`/`Player` parts are deliberately **not** next in line even though they're the same shape of work — no game-logic systems (AI, combat, animation state) exist yet to make placed enemy markers anything but inert clutter; revisit once that changes.

**`ImporterMesh`/`ImporterMeshInstance3D` are import-pipeline-only placeholder types with no rendering of their own — this bit twice, worth not reintroducing.** Godot's own scene-import post-processing (LOD/shadow mesh generation, compression) is what normally converts an `ImporterMesh`/`ImporterMeshInstance3D` into a real `ArrayMesh`/`MeshInstance3D` as part of saving an imported scene — that conversion is a property of going through the `res://` import pipeline, not of the `ImporterMesh` type itself. Since nothing in this project goes through that pipeline anymore, nothing does that conversion either: an early version of `FlverLoader.Instantiate()` used `ImporterMeshInstance3D`/`ImporterMesh` directly (mirroring what the old importer used to return) and produced scenes that were structurally correct — real nodes, real mesh data, real materials — but **completely invisible**, since `ImporterMeshInstance3D` never hooks into the rendering server at all. Fixed by calling `ImporterMesh.GetMesh()` (the same bridge API Godot's own importer uses internally) to get a real `ArrayMesh`, wrapped in a real `MeshInstance3D`. `FlverModelBuilder.BuildMesh()` still returns an `ImporterMesh` (a perfectly good mesh-authoring API on its own, and `GetMesh()` is only one call away) — the conversion happens in `FlverLoader.Instantiate()`, the one place that actually needs a renderable result.

Any child added under a loaded model's root **must** have `.Owner` set (recursively) to the actual scene root it's ultimately parented under — `PackedScene.pack()` only serializes descendants with an owner; a plain `AddChild()` alone is invisible to a scene save. `archstone.gd`'s `_set_owner_recursive()` does this after `FlverLoader.Instantiate()` returns, since `FlverLoader` itself doesn't know what scene it'll end up under.

Per-mesh geometry is built as plain C# arrays (position/normal/color/UV/index) and handed to the engine in one `SurfaceTool.CreateFromArrays()` call, rather than a per-vertex `SurfaceTool.AddVertex()`/`SetNormal()`/`SetUV()`/... loop — same per-vertex math, far fewer engine-boundary calls. `GenerateTangents()` still runs on the resulting `SurfaceTool` afterward; that call has no array-based equivalent.

Some FLVER0 meshes' own `BufferLayout` genuinely omits the Normal/UV/VertexColor member entirely (confirmed via `SoulsFormatsNEXT`'s `Vertex.Read`: a layout applies uniformly to every vertex in a mesh, so checking vertex 0 for a missing channel is representative of the whole mesh, not a per-vertex guess) — real, not a parse failure; the confirmed cases (`m9999b0`, `m9900`, `o9996`) all have the "reserved/debug ID" look FromSoft games use for collision-only or tool geometry never meant to render normally. The per-vertex loop falls back to `Vector3.Up`/`Colors.White`/`Vector2.Zero` for whichever channel a given mesh lacks, rather than indexing `[0]` unconditionally. `Mesh.Triangulate`'s `doCheckFlip` (its own internal winding-flip heuristic for triangle-strip meshes) is only requested when the mesh's vertices actually carry Normal data — the check itself reads `Normal` internally and is meaningless without it, so passing `true` unconditionally previously crashed the same class of mesh one level deeper inside `SoulsFormatsNEXT`.

**Texture resolution tries an ordered chain of candidate directories per texture reference** (`CandidateDirs`/`ResolveTexture` in `FlverModelBuilder.cs`), because Demon's Souls doesn't use one convention across categories, containers, or even individual materials on the same model. All five rules share one cache/merge primitive, `GetMergedTextures`/`LoadDirTextures` backed by `_dirTextureCache` (a plain `Dictionary<string, Dictionary<string, TPF.Texture>>` keyed by resolved directory — a plain `Dictionary` is safe here specifically because `FlverModelBuilder` is only ever driven by `FlverLoader`, which only ever calls it from one thread at a time; an earlier version of this cache was a `ConcurrentDictionary` back when a now-deleted `EditorSceneFormatImporter` dispatched calls across multiple worker threads against the same instance — see "Architecture" above), which merges *every* `.tpf` found in a directory rather than opening one guessed-basename file — a folder can hold more than one real tpf side by side (e.g. `WP_A_1503.tpf` and a separate `WP_A_1503_L.tpf` variant), and the entry a reference needs isn't always in the one whose name matches the folder. Corrupt/zero-byte `.tpf` files (3 confirmed real cases in the shipped game data: `o3104`, `o0050`, `o7999` — not an extraction bug) are skipped with a `GD.PushWarning` rather than aborting the whole model's import. Texture-name lookups are case-insensitive throughout. A second cache tier, `_decodedTextureCache` (keyed by `TPF.Texture` reference identity — safe since `TPF.Texture` has no `Equals`/`GetHashCode` override and `GetMergedTextures` already returns the same cached instances for a given directory across calls), sits downstream in `ResolveTexture` and dedupes the actual decode work (`Headerize` → Pfim DXT decompress → BGRA/RGBA swap → `GenerateMipmaps`) — `_dirTextureCache` only avoids re-reading/re-parsing a `.tpf` file, not re-decoding a texture already resolved once from it, and shared textures (a map-area bucket's ~19 tpfs reused by every piece in that area, cross-category reuse) are the norm here, not the edge case. Both caches are cleared together once tracked decoded-texture memory crosses a machine-scaled budget (`MaybeEvictDecodedTextures`, 25% of whatever `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes` reports for the current machine/container, scaling down automatically on weaker target hardware). In trust order:
1. **The model's own real container** (`OwnModelDir`) — same-basename `.tpf` flattened next to the `.flver` for chr (`mounted/chr/c2000/c2000.tpf`, no `tex` subfolder in the real container at all), or a sibling `tex/` folder for obj/parts, whose container instead splits the flver into its own `sib/` folder (`mounted/obj/o0211/sib/o0211.flver` + `mounted/obj/o0211/tex/o0211.tpf`) — confirmed via directory scan across every mounted obj/parts model, not an edge case. Always correct when the reference actually lives here, since it's exactly what got extracted for this specific model.
2. **The texture's own reference path** (`RefPathDir`) — parses the `Model/.../tex/` segment out of the reference string itself (a dev-tool path, not something the game re-validates at runtime) relative to the mounted root, nested-`tex/`-then-flat fallback. Correct for ordinary map pieces (whose per-area bucket, e.g. `mounted/map/m03/`, holds ~19 numbered `.tpf` files shared by every piece in that area) and for genuine cross-category reuse — e.g. `m4020b0.flver` (a Boletarian Palace corpse pile) uses `chr/c2000`'s own NPC texture set directly, resolved by this same rule with no separate code path needed.
3. **A sibling texture slot on the same material** (`SiblingMapAreaDir`) — if another reference on the same material resolves under `mounted/map`, tries that map-area folder for this one too. Recovers a stale/copy-pasted ref that still names the model's own folder while the real texture lives in a shared map-area bucket — confirmed on all six Nexus archstones (`o1000`-`o1050`): every one shares a single `m01` body texture, correctly labeled only on the `g_Lightmap` slot, with `g_Diffuse`/`g_Specular`/`g_Bumpmap` all copy-pasted from the `o1000` template and never updated.
4. **A map-area prefix baked into the filename** (`MapPrefixDir`, regex `^(m\d\d)_`) — tried even when every reference on the material lies about its own category. Confirmed on `o3120`/`o3129` (Boletaria wall pieces), where even the lightmap ref is mislabeled under `obj/o3120` but every texture name still honestly starts `m03_`.
5. **An unrelated obj/ model's own container** (`SiblingObjTextureDir`, 2026-07-26) — last resort, for a texture that isn't duplicated into *any* of the folders rules 1-4 check at all, only into a handful of other obj/ containers that happen to use the same shared prop-family asset. Builds a `textureName → [(objId, dir)]` reverse index over the whole `mounted/obj/` corpus, lazily and only once per editor session (most models never miss all four rules above; when they do, the index build also warms `_dirTextureCache` for whichever directory actually resolves the miss, so the texture itself isn't re-parsed from disk a second time). Ties among multiple hits are broken toward the numerically closest obj ID, not an arbitrary first match — confirmed real via two independent cases that both cluster by ID proximity: `o6510_1`'s bottle/vase pieces (`m02_obj_00.tga`, only in `o6504`/`o2401`-`o2402`'s own containers) and a cluster of `m02_01` map-piece decor (`m2020b1`, `m5100b1`-`m5190b1`, `m2230b1` — firewood/cart/tub clutter whose textures live only in the `o24xx` obj/ range, never in the shared `mounted/map/m02` bucket). See `docs/context.md` for the full investigation. `FlverLoader.EvictAll()` resets this index (along with `_dirTextureCache`/`_decodedTextureCache`) via `FlverModelBuilder.ResetCaches()` — see the `FlverLoader.cs` entry above.

Together rules 3-4 resolve ~90% of the obj/parts references that don't already succeed via rule 1 or 2 (measured against every mounted obj/parts material). A FLVER0 texture entry's `ParamName` (the slot, e.g. `g_Diffuse`) is a separate optional field that's sometimes simply absent even though the path and the texture itself are both real — `InferMissingParamNames` (runs first, before any of the above) recovers these by positionally matching each untyped entry against a `Dif`/`Spc`/`Bmp`/`Lit`/`Dcl` token found in the MTD's own bracket tag, in the same order the entries already appear — validated 100% (83/83 real affected materials, 44 files spanning chr/map/obj/parts, including the `c9983`/`c9981` Ghost/Wanderer phantom-gear template) before being wired in.

**FLVER↔Godot coordinate/winding conventions** (already handled correctly in `FlverModelBuilder`/`FlverLoader` — worth not "fixing" these again):
- **X is negated** on both position and normal: FLVER's coordinate convention is the mirror image of Godot's (confirmed via bind-pose FK on a character skeleton plus a map that visibly rendered as a mirror image of its sibling map — see `docs/context.md`). Without this, every map/model/texture placement is a correct-looking but fully mirrored left/right image of the real thing — self-consistent enough (correct winding, correct lighting) to go unnoticed for a long time.
- **Triangle winding is swapped** (two indices per face) — *because of* the X negation above, not despite it. Godot uses **clockwise** front-face winding, the opposite of the CCW convention Blender/Wavefront OBJ expect; mirroring one axis flips the apparent winding, so the swap is what keeps faces front-facing after the negation, not a separate correction for the CW/CCW convention itself.
- **Rigid mesh-to-node binding, per-vertex** (2026-07-24, `GetRigidNodeTransforms` in `FlverModelBuilder.cs`): a static (`UseBoneWeights == false`) mesh's vertices aren't always already in their final position, and a single mesh can mix vertices bound to *different* nodes — `Mesh.BoneIndices` is a small (28-entry) per-mesh palette of candidate `FLVER.Node`s, and each vertex's own `v.BoneIndices[0]` selects which palette entry applies to *that vertex* (confirmed real, not padding: a mesh with a 2-entry palette had real vertices referencing both). `BuildMesh` composes each palette entry's node transform (`Translation`/`Rotation`/`Scale`, walking `ParentIndex` for ancestors) once per mesh, then applies the vertex's own selected transform (in FLVER space, before the X-negation above) to its position/normal. Skip this and any vertex bound to a non-identity node sits wherever its raw local-space position puts it — usually at or near the origin, since node translations are frequently large. Confirmed via `m2304b0` (Doran's Mausoleum interior, `m02_00_00_00`, single-entry-palette meshes throughout — walls/floor on one node, the "standglass" windows on another, one coincidentally-identity node happening to leave one mesh looking right even before the fix) and `m2501b0` (the Nexus bridge+fountain, where two meshes each mix a `[general, fountain]` 2-entry palette — the fountain's own stone-ring decoration is the ~half of each mesh's vertices selecting the second palette entry; using only `BoneIndices[0]` for the whole mesh, an earlier version of this fix, left exactly that portion stuck at the origin while the rest of the same mesh was already correct) — see docs/context.md for the full investigation and corpus-wide impact (24% of files in `m02_00_00_00` affected in some way). `UseBoneWeights == true` meshes (real per-vertex skeletal skinning, not implemented) are left untransformed, same as before this fix — that's the already-documented, not-yet-started animation work, not this.
- **Root-caused and fixed (2026-07-25): the `m2304b0` "standglass" window one-sided bug was never about winding/normals at all.** `FLVER0.Mesh.CullBackfaces` ("whether triangles can be seen through from behind") was being parsed by `SoulsFormatsNEXT` correctly but never read anywhere in `FlverModelBuilder.cs` — every built material defaulted to Godot's single-sided `CullMode.Back` regardless of what the source data actually specified. Confirmed directly (a throwaway console app reading `m2304b0.flver`): every mesh in the file has `CullBackfaces=true` except the two window panes (`M[D].mtd`, no lightmap tag, 60/90 verts), which have `CullBackfaces=false` — exactly the "should render both sides" case Godot's default silently discarded. `GetOrBuildMaterial` now keys its cache by `(materialIndex, CullBackfaces)` rather than `materialIndex` alone — the two aren't equivalent: a corpus scan found 39 real files (mostly hair/parts) where meshes with different `CullBackfaces` legitimately share one `MaterialIndex`, which used to mean whichever mesh built the material first silently decided the cull mode for both. Applies `BaseMaterial3D.CullModeEnum.Disabled` when `CullBackfaces=false`, but that only covers the plain `StandardMaterial3D` path (973/1312 affected meshes game-wide) — `ShaderMaterial` (lightmap/blend/water) has no per-instance cull property, only a compile-time `render_mode` keyword. **The `m2304b0` windows themselves regressed a second time, silently, without this fix being touched at all** — the 2026-08-28 routing change ("every material with a real lighting model goes to the shader family, lightmap or not") moved `M[D].mtd` (`g_LightingType=3`, no lightmap texture) off `StandardMaterial3D` onto `BuildLightmapMaterial`'s `ShaderMaterial` path, which never had this fix, re-breaking these exact two window panes as a side effect of an unrelated, individually-correct change. Fixed for real 2026-09-05 (part 54) — see "Known deferred work" below, now closed rather than open.
- **Off-tree `Node3D`s can't call `GetGlobalTransform()` — worth not reaching for it again in this loader.** `Node3D::get_global_transform()` hard-requires `is_inside_tree()` and silently returns a bare identity `Transform3D()` otherwise (no visible error unless something reads the *result* and gets an obviously-wrong position — Godot itself only logs `Condition "!is_inside_tree()" is true`). This project's whole placement pipeline builds each placement fully off-tree (`FlverLoader.Instantiate()`/`InstantiatePlacement()` construct a complete standalone node subtree; only the caller parents it into a real scene afterward), so anything computed mid-build that needs "this placement's real position" has to compose the already-known *local* transforms by hand (`inst.Transform * meshInst.Transform` — `inst` has no ancestors yet) rather than ask for a global one. Confirmed the hard way: `ApplyDrawParams`'s point-light query position did exactly this and quietly fed a wrong, translation-discarding position into every `Object` placement's nearest-light lookup from the day it shipped — see the `POINT_LIGHT_BANK` entry above and `docs/context.md` part 60.
- No V-flip on UVs: `Image.CreateFromData` uses the same top-down row order as the raw decoded texture, so FLVER's raw V is already correct as-is.
- `FlverModelBuilder.BuildMesh()` returns `ImporterMesh` (a mesh-authoring API, fine on its own), but `FlverLoader.Instantiate()` **must** convert it to a real `ArrayMesh` via `GetMesh()` and use `MeshInstance3D`, not `ImporterMeshInstance3D` — see "Architecture" above for why (`ImporterMeshInstance3D` doesn't render at all outside Godot's own import pipeline, which this project no longer uses). Reverting this "for consistency" with the mesh-building code is the bug that shipped once already.
- **Alpha/blend handling is driven by `g_BlendMode`, a real 0-7 enum read from the material's `.mtd` (2026-08-27) — not the old MTD-filename-substring heuristic (`_Edge`/`_Alp`/`_Add`), which is gone.** `DesBlendMode` in `FlverModelBuilder.cs`: `0`=opaque, `1`=alpha-test (`AlphaScissor`, foliage-style cutout), `2`=alpha-blend (`Alpha`, soft transparency), `3`=water (see below), `4`=additive (`Alpha` + `BlendMode.Add`), `5`=subtractive (`Alpha` + `BlendMode.Sub`) — confirmed clean against all 584 blend-tagged MTDs, with `0` alone covering 286 MTDs and zero false positives. `7` is real but unconfirmed (2 `S_A03_Thunder00` materials only) and is treated as alpha-blend until it's identified. The old filename heuristic disagreed with the engine on 153/584 materials (26%) — it only ever under-detected, via a live case-sensitivity bug (the corpus ships both `_Edge` and `_edge`), tag-less variants (`A07_Shadowman_shadow[Dn]Sub`, no underscore), and every `A03_Sky*`/`Ps_Wander_Ghost`/`M_MagicBarrier` material rendering opaque — plus four light-shaft/cloud materials (`A03_cloud`, `A03_light_shaft`, `A04_light_shaft`, `M99_cloud11`) tagged `_Add` but actually alpha-blend, which were rendering additively over-bright. This is the same naming convention used across FromSoft's other Souls titles, still recognizable in the enum values' shape, just read from real per-material data now instead of guessed from a filename.
- `g_Specular` (a Blinn-Phong spec map) is mapped onto Godot's PBR `MetallicTexture` slot as a deliberate simplification (semantically wrong, but the only slot available without a custom shader) — `Metallic` must be explicitly set to `1.0` since it multiplies against the texture and defaults to `0`.
- **`Roughness` is derived from the material's own `.mtd` on `StandardMaterial3D` only (chr/parts) — deliberately not on the `ShaderMaterial` families (lightmap/blend/water).** `FlverModelBuilder.ResolveMtdShading()` looks up the material's `.mtd` by filename (same `_mtdIndex`/`GetMtdFloat`/`GetMtdColor3` primitives `BuildWaterMaterial` already used) and converts its real `g_SpecularPower` — a Phong shininess exponent that FLVER0's own material data never exposes at all — to roughness via the standard Phong→GGX approximation `roughness = sqrt(2/(n+2))`. Confirmed against reference DeS screenshots (`c9990`, the fluted armor set, 2026-07-24): every metal-family chr/parts material uses a real Phong-specular MTD (`C_Metal[DSB]_Skin.mtd`, `g_SpecularPower=7`) that was previously read for nothing but its `_Edge`/`_Alp`/`_Add` blend-mode substring. **Extending this to `BuildLightmapMaterial`/`BuildBlendMaterial` was tried and reverted the same day (2026-07-25) after a user-confirmed regression** — see the entry right after this one, and "Known deferred work" for the real blocker.
- **`g_DiffuseMapColor`/`g_DiffuseMapColorPower` — a real per-material diffuse tint — is read on all three families (`StandardMaterial3D`/lightmap/blend), unaffected by the roughness revert below.** `ResolveMtdShading()` applies `power` as a plain multiplier on the tint (`tint * power`, no upper clamp — the consumer uniforms are all `: source_color` and just multiply against the sampled texture in-shader, so values above 1 legitimately brighten anything not already saturated). **Not an exponent** — an earlier revision of this entry (and the code, until 2026-09-05) read it as `pow(color, power)`; that's a no-op whenever the tint is white (`1^x == 1` for any `x`), which is true for 488 of the 612 mounted MTDs, catching the sky-dome family outright: `M_Sky_light[Dn]`'s Japanese `Description` literally names it "天球_明るい" (sky, bright) with `power=1.5`, `M_Sky_dark[Dn]` "天球_暗い" (sky, dark) at `0.6`, both against pure-white `g_DiffuseMapColor` — under the exponent reading both rendered identical to plain `M_Sky[Dn]`. `power` genuinely varies 0-7 game-wide (confirmed not a fixed authoring constant); `S_DiffuseX2[Dn]_Add` (`power=2`, white tint) is the other name-level confirmation of "multiply", not "exponent". Falls back to white/no-op if the `.mtd` can't be found/parsed or the value is unset (568/584 sampled MTDs leave the *colour* itself white — a genuine minority, light-shaft/thunder/cloud VFX materials, the Wanderer's ghost-effect material, carry a real non-white tint; `power` varying is a separate, much more common case). `AlbedoColor` on `StandardMaterial3D` needed no shader change at all — it already multiplies natively against `AlbedoTexture` in Godot's own built-in shader; the `ShaderMaterial` families use a `diffuse_tint` uniform instead. This part of the 2026-07-25 work is unrelated to the roughness regression (it never touches `METALLIC`/`ROUGHNESS`) and was kept.
- **`g_LightingType` (2026-08-18) — a real three-way MTD field (corpus-scanned across all 612 mounted `.mtd`s), one value of which is now read and gated on.** `1` = Phong (chr/parts metal/leather, the family the roughness fix above covers) and `3` = HemEnv (lightmap/blend) both already matched this project's existing family split without needing to read the field explicitly. `0` — previously an unconfirmed guess ("plain diffuse-only Lambert") — turned out to be a distinct "no dynamic lighting at all" family: every sky-dome MTD, the `Ps_Wander_Ghost` dissolve material, and every additive-VFX material (`vollight`/`light_shaft`/`cloud`/snow), all sharing one real shader (`DS_Phn_ColDif.spx`), confirmed via direct MTD reads. `ResolveMtdShading()` now reads it; `BuildStandardMaterial` sets `ShadingMode = Unshaded` when it's `0` — skips Godot's ambient entirely rather than trying to boost `Emission` (an earlier, wrong-mechanism attempt at the same problem, see the entry below) — fixing a real user-reported bug where the sky dome read as washed-out and scene-ambient-dependent. (Since 2026-09-04 the opaque *sky-dome* type-0 materials route to `sky.gdshader` instead, for the FOG_BANK fade + exposure — see "Lightmaps"/`docs/context.md` part 45; ghost + additive VFX still take the unshaded `StandardMaterial3D` path.) User-confirmed in-editor. Not gated on anywhere else yet (`BuildLightmapMaterial`/`BuildBlendMaterial` still don't check it) — see "Known deferred work" for what's still open there. **Confirmed independently 2026-08-27** — `SoulsFormatsNEXT/Formats/MTD.cs`'s own `LightingType` enum has carried the answer the whole time (`None=0`, `HemDirDifSpcx3=1`, `HemEnvDifSpc=3`): `1` is hemisphere ambient **plus three directional lights**, not plain Phong — the same `LIGHT_BANK` directional-light terms the lightmap family already reads two-sevenths of (see "Known deferred work"). `BuildStandardMaterial` still routes `g_LightingType=1` to `StandardMaterial3D`+Godot PBR, which is why a `WorldEnvironment` cannot be safely added until that family gets a shader that computes its own result from those uniforms instead.

**Roughness on the lightmap/blend `ShaderMaterial` family was tried and fully reverted the same day (2026-07-25), not just patched — needs real environment/lighting work first, not another same-session guess.** Extending the `g_SpecularPower`→roughness fix above from `BuildStandardMaterial` to `BuildLightmapMaterial`/`BuildBlendMaterial` immediately regressed most map surfaces into a washed-out, glassy sheen (user-confirmed via screenshot). Root cause: `lightmap_common.gdshaderinc`/`terrain_blend.gdshader` both had a pre-existing `metallic = spec`/`METALLIC = spec` line (predating this work entirely, the same "spec map jammed into the metallic slot" simplification `BuildStandardMaterial` uses), inherited by the lightmap/blend shaders without re-checking whether it still made sense there. It was invisible before: `ROUGHNESS` defaulted to Godot's own `1.0` (fully rough), which suppresses almost all visible reflection-probe response regardless of `METALLIC`. The moment `ROUGHNESS` became a real, lower value (Boletaria's walls: `g_SpecularPower=4` → `roughness≈0.577`, confirmed via corpus scan, not an unusually shiny/mirror-like value on its own), `METALLIC` suddenly had a visible effect — and this project has **zero `WorldEnvironment`/reflection probes anywhere**, so there's nothing real for a metallic surface to reflect; Godot substitutes its own fallback ambient, reading as a flat, misplaced sheen. A first attempt (`metallic = 0.0`, keeping the new roughness) did **not** fix it, user-confirmed — meaning the real mechanism is either something else entirely or something beyond just `METALLIC`, not yet root-caused. Rather than keep guessing same-session, the whole roughness/`METALLIC` change on this material family was reverted outright (not commented out — see `docs/context.md` for why removal was chosen over leaving a disabled attempt in place) back to its pre-2026-07-25 state: `ROUGHNESS` unset (Godot default `1.0`), `metallic = spec`/`METALLIC = spec` restored. See "Known deferred work" for what this actually needs before it can be revisited.
- Terrain ground-blend materials (grass/dirt/stone transitions): a material whose MTD filename contains FromSoft's own `[M]`/`[ML]` blend-shader bracket tag (**not** whether `g_Specular_2`/`g_Bumpmap_2` are present — each is independently optional per layer; gating on their presence was tried first and was wrong, see `docs/context.md`) gets a `ShaderMaterial` using `addons/archstone/shaders/terrain_blend.gdshader` instead of `StandardMaterial3D`. The two layers blend by `VertexColor.A`. **`.R`/`.G`/`.B` (R=G=B on most, but not all, real vertices — confirmed non-white values exist) is a second, real signal, not AO/shading**: instruction-level comparison against native `Mul`-family HemEnv fragment programs (the map-shading research pass's finding #3, 2026-09-15) found it multiplies both the blended diffuse and the blended RGB specular sample, the same free-multiplier role the single-layer family's vertex colour already plays — `terrain_blend.gdshader` now does this (`diffuse_color`/`env_specular`'s `tint` argument both take `COLOR.rgb`). The earlier "deliberately not wired in, layer-blend data only" read (`docs/context.md`) was an ALBEDO-only experiment that never tried this multiplicative role and was wrong; not a re-open of the resolved blend-selector question above. The second layer's own UV set is FLVER's UV channel 1 (Godot's native UV2 slot, via the `Mesh.ArrayType.TexUV2` array — see the mesh-building note below); UV channel 2, when present, carries the lightmap (see "Lightmaps" below). Materials with `g_Diffuse_2` but no bracket tag are an unrelated "ghost" character dissolve effect, left on the single-layer path. `tex_scroll_0`/`tex_scroll_1` (one per diffuse layer, added 2026-08-27) cover the three `c5000` slime materials that scroll — same fixed-lightmap-UV reasoning as the single-layer family. Shader-only changes to `terrain_blend.gdshader` need no reimport — Godot loads `.gdshader` source live by path.

- Water surfaces (moats, swamps, lakes, fountains): gated on the material having a `g_Envmap` texture — confirmed unique to this family across all 8889 materials in the game, so unlike the other paths this needs no filename/MTD-tag heuristic at all. Gets a `ShaderMaterial` using `addons/archstone/shaders/water.gdshader`. **`water.gdshader` is reconstructed from DeS's real `DS_Water_Env` fragment program (107 instrs, disassembled) + the `DS_Water` vertex program + the per-material water `.mtd` + 6 RPCS3 frame captures that each caught one water draw (`docs/context.md`'s water entry, part 50).** The earlier "not recoverable from files" verdict was wrong — the tuning is all in the water `.mtd` (`DS_Water_Env.spx`, params `g_TileScale_0..2`, `g_TileBlend_0..2`, `g_WaterColor`, `g_Fresnel*`, `g_ReflectBand`/`g_RefractBand`, `g_BumpMapSmoose`, `g_WaterFadeBegin`), and the captures confirm each param → shader-constant mapping. `BuildWaterMaterial` is still the one path that reads the `.mtd` directly (via `SoulsFormats.MTD.Read()`, `_mtdIndex`-cached) since none of this has a FLVER0 equivalent; falls back to shader defaults if unresolvable. **Structure:** 3 scrolling bump-normal octaves (`uv_i = UV·g_TileScale_i.x + g_TexScroll_0·g_TileScale_i.y·TIME` — `.x` is the tiling multiplier applied *directly*, `.y` a per-octave speed multiplier on the raw `g_TexScroll_0` velocity, whose own magnitude is the base scroll speed; normalising it made m02 water ~30× too fast; the old flat `wave_detail_scale = 12` fudge is gone), each octave's Z reconstructed `sqrt(1−x²−y²)`, summed weighted by `g_TileBlend_i` (**not** renormalised), then `g_BumpMapSmoose` added to Z as a bias (negative → choppier, positive → flatter — it is *not* an xy multiplier); Fresnel `bias + scale·pow(1−N·V, pow)` (`pow == 0` → constant reflectance); reflection = a **cubemap** lookup (`g_Envmap` *is* a real cubemap, typically tiny — m02's is 32px — `FlverModelBuilder.ResolveWaterEnvCube` decodes it, dim neutral cube as fallback) + a `SCREEN_TEXTURE` tap for near geometry + a tight **sun glint** `pow(dot(R, sun), g_SpecularPower)` (`g_SpecularPower` is 100 on every water `.mtd`; `DS_Water_Env` adds this on top of the cube reflection, weight `c[39]`) which is what carries the wave pattern at any real viewing distance — the weight is `glint_color * glint_power`, bound from the material's own `g_SpecularMapColor`/`g_SpecularMapColorPower` (found via capture cross-check, `docs/context.md` part 50 follow-up; a first cut folded in `scatter_sun_color * scatter_sun_intensity` too, double-counting the sun and blowing the highlight out — dropped, round 2); the whole reflection is then Fresnel-weighted against the body colour; body = screen refraction (`SCREEN_UV + N.xy·band·nearFactor`, depth-guarded) tinted toward `g_WaterColor.rgb` by `g_WaterColor.a` (`water_alpha`), with a depth-buffer water-column read (`water_fade_begin`, a shoreline band *width* in world units, not a whole-lake depth gradient) mixing the finished surface toward `water_color` right at the coast. The finished surface then runs the **shared output stage** (`des_output` → `des_scatter` + `des_fog` + exposure) — `DS_Water_Env` inlines the same H&P scatter chain and `FOG_BANK` colour that land geometry gets, and its own depth-extinction `c[21]` is byte-identical to the `LIGHT_SCATTERING_BANK` extinction `c[104]`, so `des_output` is the faithful equivalent. Result to `ALBEDO`, `ALPHA = 1` on the transparent pass (for the screen taps). `a06_lava[we].mtd` also matches this family and genuinely declares `DS_Water_Env.spx` in the real game data (`docs/context.md` part 50 follow-up) — the `g_Envmap`-gated routing is correct, not a misroute; if lava still looks wrong vs. RPCS3 the gap is more likely a missing emissive/glow layer.

**Lightmaps** (`g_Lightmap`, a baked-lighting texture): present on 7394/11646 mounted materials (63%) and confirmed via corpus survey to never co-occur with water (`g_Envmap`). `StandardMaterial3D` has no slot for an independent-UV multiply texture, so every lightmapped material — not just terrain-blend ones — needs a `ShaderMaterial`. **No longer a straight `diffuse * lightmap` multiply** (see "Known deferred work" for why that was architecturally wrong) — both `lightmap_common.gdshaderinc`'s `lightmap_shade()` and `terrain_blend.gdshader`'s `fragment()` now do `albedo = diffuse * (hemi + envDif)`, where `hemi` is a two-color hemisphere-ambient term (`ambient_up`/`ambient_down` uniforms) and `envDif = texture(env_dif_cube, N) * env_color * env_intensity * lightmap`. **Both terms are driven by a per-pixel normal reconstructed from the bumpmap** (2-channel tangent-space sample, `Z = sqrt(1 - dot(xy,xy))`, TBN basis from `world_tangent`/`world_binormal`/`world_normal` varyings), and `envSpc` is summed straight into the result as `texture(env_spc_cube, reflect(-V, N)) * env_spc_color * env_spc_intensity * gate * specular_sample * tint * specular_tint` (`gate` is `min(shadow, lightmap)`, not lightmap alone — see the sun-shadow sentence just below; `specular_tint`, `g_SpecularMapColor * g_SpecularMapColorPower`, was added by the map-shading fix described further down this section, replacing an earlier version of this formula that had no material-level specular scaling at all). This structure is taken from a real captured DeS HemEnv fragment program rather than inferred: EnvDif is an irradiance lookup by the **surface normal**, EnvSpc a lookup by the **reflection vector**, and the lightmap acts as the gate the real shader applies as `min(shadow_attenuation, lightmap)` — combined with the v2 static sun-shadow term (`min(sun_shadow(), lightmap)`, see "Sun shadows" below) since 2026-09-03; before that the lightmap alone gated it. Baked occlusion still drives where env light lands. `use_normal_map` (set from C# when a `g_Bumpmap` actually resolved — true on 225 of 335 real Nexus surfaces) falls the per-pixel normal back to the interpolated vertex normal for the many `[D][L]`-style materials that ship no bumpmap. Cubemaps come in two real layouts and **only the block-compressed one may go through Pfim**: handed an uncompressed ARGB8888 face, Pfim reports `Rgb24` and reads 3 bytes per pixel out of 4, rotating the channels on a four-pixel cycle into a literal RGB rainbow (see `docs/context.md`'s "part 24" — this shipped briefly and wrecked every uncompressed-cubemap map: m02, m04, m06, m08, m99). Uncompressed faces are read straight out of the payload as A,R,G,B instead. An unresolved cubemap name binds a 1×1 white cubemap, collapsing both terms to the flat lightmap-scaled behaviour they replaced — matching the real FRPG shader shape (see below), not the old undifferentiated multiply. Real `LIGHT_BANK` `env_intensity` values run 1.5x-5x, which overexposes bright-lightmap surfaces on a handful of map pieces (see "Known deferred work") — a `[0,1]` clamp was tried and reverted the same day (2026-08-17, user-confirmed regression on most other, unaffected map pieces); left unclamped deliberately for now, since the overexposure is more useful as a visible marker of which pieces still need the real fix than a clamp that dulls everything else. `LIGHT_BANK` carries a second, separate environment term (`envSpc`, distinct from the `envDif` fields `env`/`env_intensity` above are sourced from) that the real shader keeps as a specular-reflection response rather than folding into the diffuse term — implemented the same way water.gdshader's own hand-computed reflection is (no real reflection probe exists in this project), weighted by the material's own specular texture. It used to go to `EMISSION`; since these shaders became `unshaded` (2026-08-27, see "The DeS rendering pipeline, reconstructed") there is only one output, so it is added to the result directly the way the real shader adds it. This math (uniforms, the world-normal helper, `hemisphere_ambient()`) lives in a third shared file, `addons/archstone/shaders/hemisphere_ambient.gdshaderinc`, `#include`-d by both `lightmap_common.gdshaderinc` and `terrain_blend.gdshader` rather than duplicated — the single-layer family already shared `lightmap_common.gdshaderinc` for diffuse/normal/specular/lightmap sampling, but `terrain_blend.gdshader` is otherwise a fully separate, self-contained shader, so only the hemisphere/env piece is factored out. Uniform defaults are DeS's own `param/drawparam/default_lightbank.param` row 0 (read via `SoulsFormats.PARAM`/`PARAMDEF`, not invented) — used only as the fallback `DrawParamReader.cs` (2026-08-17) falls back to when a placement's real `LightID` is the `255`/unset sentinel or its map has no own bank file; every other placement gets its own resolved row's values pushed via `FlverLoader.InstantiateMap()`'s `ApplyDrawParams` (which also resolves the part's `FogID`/`ToneMapID`/`ToneCorrectID` for the output stage), as a per-surface material override (`Duplicate()`'d off the shared cached mesh's base material, so one placement's values never leak onto another placement of the same reused model — see "Known deferred work" for the `colA`-scale fix and the still-open env-term overexposure caveat). Non-blend materials route on `g_BlendMode` (see "Alpha/blend handling" above) to one of four thin shader variants: `lightmap.gdshader` (opaque; also folds in the alpha-test case via a `hint_range(0,1)` `alpha_scissor_threshold` uniform defaulting to `0.0`, since referencing `ALPHA_SCISSOR_THRESHOLD` at all keeps Godot's non-sorted opaque render path regardless of the threshold value), `lightmap_alpha.gdshader` (alpha-blend), `lightmap_add.gdshader` (additive, `render_mode blend_add`), or `lightmap_sub.gdshader` (subtractive, `render_mode blend_sub`, added 2026-08-27 for the 139 real `a04_blood`-family meshes this family had no route for before) — four separate files rather than one runtime-switched shader because `blend_mix`/`blend_add`/`blend_sub` are compile-time `render_mode` keywords in Godot, not a per-material property the way `StandardMaterial3D.BlendMode` was; all four `#include "lightmap_common.gdshaderinc"` for the shared diffuse/normal/specular/lightmap sampling logic, exposed as a `lightmap_shade(uv, uv2, vertex_color, view_dir)` function returning the finished pre-output-stage colour — **not** a function that assigns `ALBEDO` directly, which fails to compile (confirmed via a real, non-dummy rendering driver — see "Build & verify" below): Godot's shader built-ins are only assignable directly inside `fragment()` itself, never from a helper function it calls, `#include`-d or not. The same restriction applies to `varying`s (a helper can't assign one either, only `vertex()`/`fragment()` can) and, less obviously, to *reading* some built-ins at all: `MODEL_MATRIX` isn't visible inside a non-entry function even just to read (unlike `NORMAL`, which is) — `hemisphere_ambient.gdshaderinc`'s `hemisphere_world_normal()` takes both as explicit parameters rather than reading the built-ins directly, and each shader's own `vertex()` calls it and assigns the varying itself. `lightmap_shade` also applies `g_TexScroll_0` (a per-second UV scroll rate, real on the two `m99` lava surfaces — scrolls the diffuse/normal/specular sample only, not the lightmap's own UV, which stays fixed to its baked geometry) and multiplies the mesh's own vertex colour into the diffuse sample, not the final albedo, so it doesn't scale the `envSpc` emission (both added 2026-08-27; real, nonzero vertex colour is present on 35% of map meshes per a full-corpus census). **The HemEnv branch does not additionally scale that vertex colour by a fixed `0.6`** — the `f[COL0]` multiply in every captured HemEnv fragment program (`docs/context.md` part 43) is the material's own `g_DiffuseMapColorPower` (`0.6` on most map MTDs), already folded into `diffuse_tint` by `ReadMtdShading`; a same-value hard-coded `0.6` was mistakenly stacked on top of it in-shader, double-attenuating every lightmapped surface (the map-shading research pass's finding #1, fixed 2026-09-15). `terrain_blend.gdshader` carried the identical duplicate on its composed diffuse+spec result and is fixed the same way; it also now multiplies both the diffuse and RGB specular blend by `COLOR.rgb` (finding #3 — see the terrain-blend entry above), which the diffuse-power fix alone does not restore. `env_specular` additionally gained a `specular_tint` uniform (`g_SpecularMapColor * g_SpecularMapColorPower`, finding #2) — previously the `envSpc` term had no material-level specular scaling at all. Blend materials keep using `terrain_blend.gdshader` for the diffuse1/diffuse2 layer blend itself (865/912 real blend materials have a lightmap; the other 47 leave the uniform unset, which safely no-ops via `hint_default_white`). The lightmap's own UV is always the *last* UV channel (confirmed via corpus survey: zero exceptions across ~11.6k materials) — Godot's native UV2 slot on non-blend materials (which only need one other UV channel, for the diffuse), or a third per-vertex channel on blend materials (whose native UV/UV2 are already spoken for by the two diffuse layers), packed into `Mesh.ArrayType.Custom0` as raw floats. `Custom0` is only readable inside `vertex()`, unlike `UV`/`UV2`/`COLOR` which are also available in `fragment()` directly (also confirmed the same way, not assumed) — `terrain_blend.gdshader` forwards it to `fragment()` via an explicit `varying vec2 lightmap_uv` set in its own `vertex()`. Custom0's component format (`Mesh.ArrayCustomFormat.RgFloat`, 2 floats/vertex) isn't inferable from the raw array the way `Vertex`/`Normal`/`UV` are, so `BuildMesh` passes it explicitly via `ImporterMesh.AddSurface`'s `flags` parameter — confirmed correct by reading back a loaded mesh's `Custom0` surface array and checking it against the source FLVER's raw UV data.

**`SoulsFormatsNEXT/`** is a git **submodule** pointing at the user's own fork (`github.com/Solaire9886/SoulsFormatsNEXT`) of the community SoulsFormats library, not the upstream `soulsmods` repo directly — check `SoulsFormatsNEXT/FORMATS.md` for format documentation. Two local patches live as real commits on that fork (`origin` remote; `upstream` remote still points at `soulsmods/SoulsFormatsNEXT` for pulling future updates): one known upstream bug patched — `Formats/FLVER/FLVER0/Mesh.cs` had a `version >= 0x12`-based heuristic for picking a UV fixed-point scale factor (1024 vs 2048) that is wrong for Demon's Souls — verified empirically (UV wireframes overlaid on decoded textures) that Demon's Souls always needs `1024` regardless of header version; if SoulsFormatsNEXT is ever synced from upstream, re-check this hasn't regressed. The other patch retargets its own `.csproj` to `net8.0` to stay a valid `ProjectReference` target for `Soulbrandt.csproj` (also net8.0). Cloning this project fresh needs `git clone --recurse-submodules` (or `git submodule update --init` after a plain clone) to pull the submodule in. **A third patch is complete but uncommitted (2026-09-06, `docs/context.md` parts 57-58)** — a `DemonsSouls`-flagged variant of `Formats/FFXDLSE/` (the particle-effect format `FFXDLSE.cs`'s own doc comment says only supports DS2) for reading DeS's real `.ffx` effect definitions, verified against the full mounted corpus (3,091/3,091 files parse). See "Known deferred work" below for what's still needed beyond parsing. Not pushed to the fork without explicit permission, per this project's standing git-action rule.

**BND/DCX container unpacking needs no external tool.** `addons/archstone/scripts/AssetExtractor.cs` reads FromSoftware's containers directly in-process via `SoulsFormatsNEXT`'s `DCX`/`BND3`/`BND4` readers — see "Asset mounting" below. No third-party unpacker (WitchyBND, Yabber, etc.) is needed anywhere in this workflow.

## Asset mounting

`mounted` (repo root, gitignored) is a real directory — **not a symlink anymore**. The toolbar's "Archstone" menu (`addons/archstone/scripts/archstone.gd`, `import.tscn`) has seven actions, in two groups. **Extraction** (unchanged in spirit, but no longer touches Godot's import system at all — see below): "Mount..." only validates a chosen root (checks it contains at least one known category folder) and remembers it — it does **not** extract anything by itself; "Import" then offers a **Full Import** or **Choose Categories...** (checkboxes) confirmation, either of which kicks off the real extraction; "Clear Mounted Assets..." recursively deletes `res://mounted` after a confirmation dialog, for freeing disk space or forcing a clean re-extract. **Loading** (new, replaces what used to happen automatically via Godot's own reimport queue): "Load Model(s)..." and "Load Folder..." each open an `EditorFileDialog` (`ACCESS_FILESYSTEM`, rooted at `mounted/`) to pick specific `.flver` files or a whole folder (loaded recursively — the "grab every piece for this area in one go" case), calling `FlverLoader.InstantiateWithDefaultDrawParams()` for each (see "Known deferred work" for why the default-lightbank variant) and dropping the result under the selected Scene-dock node or the edited scene's root; "Load Map..." (rooted at `mounted/map/mapstudio`, filtered to `*.msb`) calls `FlverLoader.InstantiateMap()` per selected `.msb` — see "MSB map placement" above for what this does and doesn't cover yet; "Reload Loaded Models" calls `FlverLoader.EvictAll()` so the next load rebuilds from source (use after an importer-code change).

The user points "Mount..." at their own raw, unmodified copy of the game (`.../Demon's Souls (USA)/PS3_GAME/USRDIR`); once "Import" runs, `addons/archstone/scripts/AssetExtractor.cs` walks it and unpacks `.bnd`/`.dcx` containers directly via `SoulsFormatsNEXT`'s `DCX`/`BND3`/`BND4` readers (confirmed against real containers: this game's compression is `DCX_EDGE`, and `SoulsFormatsNEXT` has a literal `Type.DemonsSouls = Type.DCX_EDGE` alias) — no external tool involved at all. Output goes straight into `res://mounted` in the same loose-file layout `FlverModelBuilder.cs` already expects. **Extraction deliberately does not call `EditorInterface.get_resource_filesystem().scan()` afterward anymore** — it used to, and that single call was the actual mechanism that funneled every newly-extracted `.flver` straight into Godot's crash-prone reimport queue even after a concurrency self-throttle had been added to the (now-deleted) importer; see docs/context.md's reimport-concurrency entry. Extraction now just writes loose files, full stop — nothing observes `mounted/` changing until you explicitly click "Load Model(s)..."/"Load Folder...". Re-running extraction is idempotent (mtime-based skip, near-instant once already extracted) and scoped to a small category allowlist (`chr`, `map`, `obj`, `parts`, `mtd`, `param`, `paramdef`, `shader`, `sfx` — see `AssetExtractor.KnownCategories`; the raw dump's `movie`/`sound`/`msg`/`script`/etc are never touched). The chosen root path is remembered in `user://archstone_mount.cfg` (a `ConfigFile`, structurally outside the repo — never `res://override.cfg` or `EditorSettings`, see `docs/context.md` for why).

Extraction is also runnable headlessly, independent of any editor GUI session: `godot-mono --headless --path . -s addons/archstone/scripts/extract_cli.gd -- --raw-root=/path/to/raw [--categories=chr,map]`. `AssetExtractor.cs` itself has zero `EditorPlugin`/`EditorInterface` dependency — both entry points call the exact same code. This is also the only way to exercise this feature in a GUI-less environment.

This is still the editor-side increment (`docs/PLAN.md`'s Phase 1 item 1), but meaningfully closer to the eventual shipped-runtime goal than it looks: `AssetExtractor.cs`, `FlverModelBuilder.cs`, and `FlverLoader.cs` all have zero `EditorPlugin`/`EditorInterface` dependency — only `archstone.gd`'s toolbar/dialog triggering is editor-only. A full runtime loader for exported/shipped game builds still needs its own driving code (no editor, no manual button clicks, no pre-extraction step at all) and isn't started, but the actual parsing/building logic underneath it no longer needs to change to get there.

## The shader library (`shader/*.shaderbnd`)

`PS3_GAME/USRDIR/shader/` holds five `.shaderbnd` containers — plain `BND3`, read with `BND3.Read` and nothing special. **`ds_flver.shaderbnd` is the material shader library: 4.6MB, 1349 entries** (134 `.vpo` vertex programs, 1215 `.fpo` fragment programs), each carrying its original build path. `ds_filter.shaderbnd` (31 entries) holds the post chain — `DS_Fil_HDR`, `DS_Fil_HDR_ColAdj`, `DS_Fil_CalcAdaptedLum`, `DS_Fil_Bloom`, `DS_Fil_Dof`, `DS_Fil_CameraBlur`, all named. **Mounted as of 2026-08-28**: `shader` is in `AssetExtractor.KnownCategories`, landing at `mounted/shader/<container>/<entry>` (1421 files). That needed one extractor change beyond the allowlist — these entry names carry no `data/DVDROOT` prefix, and `ResolveEntryOutputPath` returns `null` for anything without one, which `WriteEntry` **silently dropped**. `FallbackEntryOutputPath` now mirrors the container's own place in the raw tree and gives it a folder named after itself, so `ds_flver`'s 1349 entries can't collide with `ds_filter`'s identically-shaped names. It strips a trailing `.dcx` first: every container ships as both a plain and a `.dcx` copy that decompress to the same binder, and without that they land in two folders.

**Fragment program names are a fixed-width field layout, `_`-padded to fixed columns:**

`DS_<family>_<textures>_<shadow>_<lightingModel>.fpo`

| Field | Values |
|---|---|
| family | `Phn` (626), `Gst` (576), `Dbg` (9), `Water` (3), `Ghost` (1) |
| textures | `Dif` → `DifSpc` → `DifSpcBmp` → `+Mul` → `+Lit`, and `+LitSdw`/`+LitCsd` |
| shadow | `Sdw` (shadow map) or `Csd` (cascaded) — **separate compiled shaders**, 400 in total |
| lighting model | `HemDir3`, `HemEnv`, `HemEnvLerp`, each × `{—, PntS, PntSS, PntSSSS}`; plus a bare `Non`/`Pnt`/`PntS`/`PntSS`/`PntSSS`/`PntSSSS` set |

Vertex program names use a different middle field — `DS_<family>_<vertexLayout>_<textures>_<variant>.vpo`, where the layout is `PIN`/`PIWN`/`PINT`/`PINTT` (position/index/normal, `W` = weights, `T`/`TT` = tangent sets) and the variant is `Non`/`Sdw`/`Dep`/`DepAlp`.

**Three things this settles that were previously inferred:**

- **`HemEnvLerp` is a real, first-class lighting model** with a full variant set — the loose end from the pipeline trace, where `FragmentProgram151` lerps its result toward a constant colour by the EnvDif cubemap's alpha.
- **Point lights reach map geometry.** `HemEnv` is the map/lightmap family and it has `PntS`/`PntSS`/`PntSSSS` variants, so map surfaces receive 1/2/4 point lights. `POINT_LIGHT_BANK` is recorded below as a fixture-preset table with no known consumer; it has one.
- **Shadowing is a compile-time variant, not a runtime branch** — which mirrors how this project already has to split `blend_mix`/`blend_add` into separate `.gdshader` files.

`ShaderLibrary.cs` reads this as data — names only, never a byte of shader code. `ResolveMaterialShader(mtdShaderPath)` takes an MTD's own `ShaderPath` and returns the family, texture-feature set, and the lists of lighting models and shadow variants the engine would choose among for that material; `GetLightingModels()`/`GetFamilies()`/`GetLibraryStats()` describe the library itself. Parsing is by **feature-substring detection, not `_`-token splitting** — the names are padded to fixed columns, so a feature run appears fused (`DifSpcBmpMulLitCsd`) or split (`DifSpcBmpMul_Csd`) depending on where the columns fall, and only substring detection reads both shapes identically. Verified against the whole corpus: **612 of 612 mounted MTDs resolve, zero unresolved.**

**Routing runs off this as of 2026-08-28.** `FlverModelBuilder.ClassifyMaterial` takes its water/blend/lightmap decision from the resolved family and feature set — `Mul` is what it used to detect as the `"[M]"`/`"[ML]"` bracket tag, `Lit` as `g_Lightmap` presence — falling back to the old slot/tag heuristics only when the `.mtd` can't be read at all. Checked against the whole corpus before switching: **610 of 612 MTDs classify identically**, and both disagreements are the magic barrier, a genuine `ColDifMul` two-layer material whose name carries no bracket tag. No FLVER map material references it, so that fixes a latent case rather than a visible one.

**A load-bearing negative result: the material does *not* determine the lighting model.** `DS_Phn_ColDifSpcBmp.spx` (104 MTDs, the most common map material) and `DS_Phn_ColDifSpcBmpMulLit.spx` both resolve to the *same* 13 lighting models — `HemDir3`, `HemEnv`, `HemEnvLerp`, their point-light variants, and `Non`. So which model a surface gets is a pure runtime choice and cannot be inferred from the shader path; `MTD.LightingType` remains the only authored signal for it. Anything that tries to route lighting off the `.spx` name is building on sand.

**Material → shader is an authored mapping, not a heuristic.** Every `.mtd` carries a `ShaderPath` naming its `.spx` (32 distinct values across the 612 mounted MTDs), and those map 1:1 onto the fpo names — `DS_Phn_ColDifSpcBmpMulLit.spx` → `DS_Phn_DifSpcBmpMulLit_<shadow>_<model>.fpo`. The material fixes family and texture set; the runtime picks the shadow variant and lighting model. (`Col` is the vertex-colour multiply this project already implements.)

**Every MTD also carries a dev-written Japanese `Description`.** These confirm, in the authors' own words, routing this project previously derived statistically: **`Mul` = multi-texture (the terrain blend), `Lit` = light texture (the lightmap), `α抜き` = alpha cutout, `半透明` = semi-transparent.** Worth reading before inferring anything else about a material family.

**What the binaries do *not* contain: symbols.** A `.vpo`/`.fpo` is raw RSX microcode behind a `FF 0F 00 11` header with the parameter name table stripped, so uniform register names are not recoverable from these files, and the CPU-supplied per-draw constants (`c104`–`c110` in the scattering chain) are not in them either. What *is* present is the compiler's **embedded literal pool**, which is often enough to identify what a stripped shader is doing: in `DS_Phn_PINTT_DDL_Sdw.vpo` it decodes to `(1/1024, 1/ln2, 1/ln2, 1.0)` — the `c466` block — and to `127.5/256` and `512/255`, the standard unsigned-byte vertex-attribute decode constants.

**A standalone tool names the anonymous RPCS3 captures against this library — `tools/RsxShaderMatch` (2026-08-31).** RPCS3's shader-log dumps (`shaderlog/FragmentProgramN`) are plain GLSL with the names stripped. The tool decodes each `.fpo`'s raw RSX fragment microcode into a structural fingerprint (ordered texture-unit run, inline-constant count, KIL/FENC, sampler types) and matches the captures against it, restoring the dev's own filename: on the captures collected so far, **363 high-confidence names across 423 captures, 195 distinct shaders identified**. It also carries a readable RSX disassembler (`disasm`) — the D5/D6/D7 shader fixes in the pipeline section below were read straight from the disassembled reference programs, not inferred. Plain .NET console app, no Godot/SoulsFormats dependency, excluded from `Soulbrandt.csproj`; `tools/RsxShaderMatch/README.md` documents the `.fpo`/`.vpo` format and the build stages. **Vertex-program matching landed 2026-08-31 (`--vertex`, Stage 5)** — a separate RSX ISA (co-issued vector+scalar ops, no halfword swap), so its own decoder (`RsxVp.cs`), ported from `CgBinaryVertexProgram.cpp`. It leans on the three sets that survive name stripping: input attributes (`attributeInputMask` — the skinning split), referenced constant indices (the `D`/`DD`/`DL` texgen split is `c120` alone vs `+c121` vs `+c122`), and output registers. **HIGH 143 / MED 12 / LOW 57 of 212 vertex captures, 28 distinct canonical shaders identified** (`vertex-names.json`); the LOW tail is genuine ambiguity — `DS_Fil_*` fullscreen-quad shaders share one passthrough vpo, and `Dep`/`DepAlp` prepass vpos are identical across texgen variants. **`DS_Phn_*` and `DS_Gst_*` vertex programs are byte-identical** (exact disasm diff — the ghost effect is entirely fragment-side), so the matcher collapses the family token and reports the canonical `DS_*_<layout>_<texgen>_<pass>`. Two findings that correct earlier inferences: the `HemEnv` reference bytecode carries **no** bumpmap term in the variant captured most often (per-pixel relief there is entirely the env-cubemap reflection, matching the D-series conclusion below); and **`HemEnvLerp` is an environment-lighting *transition*** — env-diffuse cross-faded between *two* cubemaps by a per-draw scalar — not the "lerp toward a constant colour" the part-18 trace attributed to it (that behaviour is in plain `HemEnv`).

## The DeS rendering pipeline, reconstructed (and what this project implements of it)

Traced 2026-08-27 from real RPCS3 fragment-program dumps of the Nexus and Boletaria, not inferred — see `docs/context.md`'s "part 18" for the trace. The reference material is `FragmentProgram151` (a lightmapped HemEnv map piece, the family most Nexus geometry uses) cross-checked against `FragmentProgram124` (a bumpmapped HemEnv material with EnvSpc) and `FragmentProgram11` (a HemDir3 terrain blend).

**Per-material, in the fragment shader:**

1. **Diffuse** sampled at UV0; a second layer sampled at the same register's `zw` pair and blended into it by **vertex-colour alpha** (the terrain-blend family) — `fma(diff_color.wwww, layerB - layerA, layerA)`.
2. **Normal**: when the material has a bumpmap, a per-pixel normal is reconstructed (2-channel tangent-space sample, `Z = sqrt(1 - dot(xy,xy))`, TBN basis built by cross product); when it doesn't, the interpolated vertex normal is used directly. Both paths are real and appear in different shaders.
3. **EnvDif** cubemap sampled by the **surface normal**; **EnvSpc** cubemap sampled by the **reflection vector** (`2(N·V)N - V`), weighted by the **RGB** specular sample and by vertex colour — both confirmed in the disassembled `DS_Phn_DifSpcBmp…HemEnv` (the term folds `COL0` in, and uses the sampled `.xyz`, not just red). EnvSpc is per-material — plenty of shaders bind only EnvDif.
4. **Hemisphere** = `mix(down, up, (N.y + 1) / 2)`, using whichever normal step 2 produced. **Not gated by anything.**
5. **Shadow**: a cascaded shadow-map projection (the long matrix-select chain at the top of the shader) plus a distance fade.
6. **The gate** — literally `min(shadow_attenuation, lightmap)`, the lightmap sampled at its own separate UV set.
7. **Composition** — `result = diffuse * material_diffuse_tint * vertex_colour * (hemisphere + EnvDif * gate) + EnvSpc_term`, `EnvSpc_term` weighted by its own `material_specular_tint` (`g_SpecularMapColor * g_SpecularMapColorPower`) as well as the RGB specular sample and vertex colour. The captured `× 0.6` on the vertex-colour multiply (`docs/context.md` part 43) is `material_diffuse_tint` itself (`g_DiffuseMapColorPower` is `0.6` on most map MTDs) — not a second, separate engine constant on top of it; see "Map shading fix" above.
8. **Atmosphere** — `result * tc8 + tc9`, both interpolated per-vertex and applied per-pixel, so this is a *per-material* term in this engine, not a scene-wide pass. **`tc8` is a vec3, not a scalar**, and the vertex program builds it from a per-channel `exp2()`: this is extinction plus in-scatter, i.e. **Hoffman & Preetham's real-time outdoor light-scattering model**, whose parameters `LIGHT_SCATTERING_BANK` carries under the paper's own names (`lsBetaRay` Rayleigh, `lsBetaMie` Mie, `lsHGg` the Henyey-Greenstein asymmetry, plus `distanceMul`/`inscatteringMul`). This is the dominant outdoor atmosphere term — `FOG_BANK` was long assumed to be a linear-fog other half; a frame-capture sweep (context.md part 36) proved DeS never uses RSX fixed-function fog, but `FOG_BANK`'s colour *is* consumed, as the target of a hand-rolled `mix()` distance fade (`des_fog`, part 45), applied just before this scattering term. `blendCoef` ("scattering's degree of involvement, 100 = max") is a strength dial on the scattering. Addressed by `MSBD.Part.ScatterID`, a sibling of `LightID`.
9. **Exposure normalize** — `output = clamp(result * k / exposure_constant, 0.0, 1.0)`. **This is universal: 190 of 219 real material shaders end with exactly this.** DeS packs HDR-range lighting into a `[0,1]` target *in the material shader itself*.

**Per-frame, in `ds_filter.shaderbnd`:** luminance downsample (`SampleLumInitial`/`Final` — average log-luminance, `EX2` of a 16-tap mean) → `CalcAdaptedLum` (temporal adaptation via an `EX2` blend, clamped to `TONE_MAP_BANK`'s `[minAdaptedLum, maxAdapredLum]`; emits `E = grayKeyValue / adaptedLum`) → `BrightPassFilter` (`(scene − threshold) / (1 − knee)`) / blur / `Bloom` → **`DS_Fil_HDR_ColAdj`**: `saturate(scene · 2.0) + bloom · w`, then a `TONE_CORRECT_BANK` 3×3 colour matrix + offset (plain `DS_Fil_HDR` is the same minus the matrix) → DOF/motion blur. **Every stage here is linear** — the whole chain was disassembled 2026-09-04 (`docs/context.md` part 43) and there is **no Reinhard curve and no 1D LUT anywhere** (`DS_Fil_HDR.fpo` is 5 instructions, its two samplers are the scene and bloom render targets, not LUTs). **Of this chain, only the bright-pass→bloom stage is approximated so far** — see "Bloom" below. Eye adaptation has no path under Compatibility; its resting value feeds the geometry-pass exposure `E` as a fixed `clamp(0.10, min, max)` (part 48). The post pass's `saturate(scene · 2.0)` pairs with the geometry pass's `saturate(result · E / 2)` (step 9) — the `/ 2` is RGBA8 headroom for the bright-pass, and the `· 2` undoes it — so the net exposure across both passes is `saturate(result · E)`, which is what `des_tonemap` does. `des_tone_correct` **is** `DS_Fil_HDR_ColAdj`'s colour matrix (`M·colour + offset` from `TONE_CORRECT_BANK`'s brightness/contrast/saturation/hue), reproduced to measurement precision (part 44).

**What this project implements (output stage reworked across parts 43–48, 2026-09-04):**

| Pipeline stage | This project |
|---|---|
| diffuse × material tint (`g_DiffuseMapColorPower`, usually `0.6`) × vertex colour | ✔ matches — fixed 2026-09-15 (see "Map shading fix" above); previously applied the tint's own `0.6` a second time as a hard-coded constant |
| two-layer blend by `COLOR.a`, both layers × `COLOR.rgb` | ✔ matches — the `COLOR.rgb` multiply added 2026-09-15 (`terrain_blend.gdshader`), previously discarded |
| per-pixel normal when bumpmapped, vertex normal otherwise | ✔ matches (`use_normal_map`) |
| hemisphere `mix(down, up, (N.y+1)/2)`, ungated | ✔ matches |

**The output stage** (`addons/archstone/shaders/output_stage.gdshaderinc`, added 2026-08-27) implements steps 8-10 as `des_output(color, view_distance, view_dir)`: `LIGHT_SCATTERING_BANK`'s extinction-plus-in-scatter, then the transfer function, then `TONE_CORRECT_BANK`'s per-channel brightness/contrast plus saturation and a hue rotation. `FlverLoader.ApplyDrawParams` pushes the scatter/tonemap/tonecorrect banks per placement from the part's own `ScatterID`/`ToneMapID`/`ToneCorrectID`, alongside the `LIGHT_BANK` values it already resolved. **The fog stage is `des_fog`, a hand-rolled distance fade** (`docs/context.md` part 45, added 2026-09-04): `mix(colour, FOG_BANK.col/255·(colA/100), saturate((view_distance − fogBeginZ)/(fogEndZ − fogBeginZ) · degRotW/100))`, applied *before* `des_scatter` — matching the `mix()` two instructions ahead of `result·tc8 + tc9` in every HemEnv fragment program. `FlverLoader.ApplyFogBank` binds it per placement from `MSBD.Part.FogID`. It is **not** RSX fixed-function fog (`SET_FOG_PARAMS` never issued, no `f[FOGC]` reads — `docs/context.md` part 36); the earlier `des_fog()` that modelled RSX fog was correctly removed, but its blanket removal also dropped this real term. The bank colour and `degRotW/100` weight were verified exact against the shaders' inline constants on m01/m02/m03/m06.

**The atmosphere is `LIGHT_SCATTERING_BANK`'s Hoffman-Preetham scattering**, structurally confirmed from the vertex bytecode and — after parts 46–48 — user-confirmed "extremely accurate", with only minor residual inconsistencies deferred behind the rest of the pipeline. In-scatter is normalized by **per-channel `1/β`** — the captured vertex constant `c106` equals `1/c104` (the extinction β) to 4 sig figs on m01/m02/m03 (`docs/context.md` part 46). β is blue-heavy, so `1/β` is red-heavy and the normalized in-scatter comes out near-neutral — the grey haze the RPCS3 reference shows. The earlier "scalar fold, in-scatter stays blue" reading (part 35) was calibrated to a visual expectation, not to `c106`; a per-channel divide was in fact right. `c105` (reflectance) rides inside the transmittance (`(1−blend) + blend·fex·c105`), not the in-scatter. The Rayleigh/Mie wavelength weights (in-scatter numerator) are part 35's cross-area measurement (`c108`/`c109` are stable). Extinction is separate and **bluer** — `EXTINCTION_WAVELENGTH_WEIGHTS = (0.59, 0.87, 1.54)`, the mean-normalised average of the captured `c104` from m01/m02 (B/R ~2.6, vs ~2.0 for scattering — wavelength-dependent absorption), used for both `fex` and the `1/β` divide (part 47). It makes distant geometry shed blue faster, so a blue-violet FOG_BANK tint washes back toward the surface's own lighting instead of staying violet. The extinction *magnitude* (`scatter_distance_scale`) is still a fitted unit-scale — the captured `c104` is much stronger, so a re-fit against it is available. See `docs/context.md` parts 35–37, 46–47.

**What is still open**: `scatter_distance_scale` / the in-scatter magnitude is the one remaining unverified fit — re-anchored several times, deferred to the screen-space pipeline work (bloom, DoF) since it can't be judged before a full pipeline exists. A small residual map-piece lighting-colour gap is parked with it.

**Not recoverable from files:** `c104`/`c108`/`c109`/`c110` are CPU-supplied per draw. The `.vpo` literal pool is exhausted (`c466` = `(1/1024, 1/ln2, 1/ln2, 1.0)`, plus vertex-attribute decode constants), and a survey of `other/*.properties`, `paramdef/*.tdf` and `other/*.tpf` found only network config, param-editor enum labels and texture banks.

Two deliberate compressions of the engine's structure, both because the target is the same output rather than the same intermediate:

- **`des_tonemap` is a pure linear exposure — `saturate(color · E)` — because that is all DeS does.** Both passes were disassembled (`docs/context.md` part 43): the geometry epilogue is `saturate(color · E / 2.0)` (`E = c16.x`, the frame's adapted exposure, constant across a frame) and the fullscreen `DS_Fil_HDR_ColAdj.fpo` is `saturate(scene · 2.0) + bloom·w` then a colour matrix. **No Reinhard, no shoulder, no LUT anywhere** — the earlier belief that `DS_Fil_HDR` tabulates a Reinhard 2002 curve was wrong; its .fpo is five instructions and its samplers are the scene and bloom RTs. The geometry `/ 2` and post `· 2` cancel (the `/ 2` is one stop of RGBA8 headroom for the bright-pass), so the net is `saturate(color · E)`. `E` is modelled as `tone_key / tone_adapted_lum`, with `tone_adapted_lum = clamp(0.10, min, max)` (part 48) — captured `E` is 1.78 (Boletaria), 1.77 (Nexus 094137), 1.31 (m03); `clamp(0.10, ...)` reproduces all of these. A first attempt at this correction shipped `saturate(color · E · 0.5)` — it kept the geometry `/ 2` without the post `· 2`, so everything came out 2× too dark (user-confirmed); fixed by dropping the `· 0.5`.
- **`des_tone_correct` is engine-accurate (verified part 44).** The real `DS_Fil_HDR_ColAdj` applies `TONE_CORRECT_BANK` as `M · colour + offset` — a 3×3 colour matrix (`c[2]/c[3]/c[4]` rows) plus an offset (`c[5]`), built CPU-side. Back-solving the captured Nexus matrix against `TONE_CORRECT_BANK` row 0 (brightness `0.8/0.87/0.83`, contrast `1.1`, saturation `0.9`): `M = S(sat)·diag(contrast)·diag(brightness)` with Rec.601 luma, and the contrast pivot's `0.5·(1−contrast)` offset, reproduce the captured `c[2..5]` to ~2 decimals. `des_tone_correct`'s `brightness → contrast-pivot → saturation → hue` composition **is** that — the earlier "unrecoverable LUT / rebuild as a matrix" note predated the `DS_Fil_HDR_ColAdj` disassembly. Bound per-part from `ToneCorrectID`; `clamp` is only at the end, matching the matrix's single write.
- **Adapted luminance is a uniform, not a measured value.** The engine derives it from the frame's own geometric-mean log-luminance clamped into `[minAdaptedLum, maxAdapredLum]`; the Compatibility renderer can't read frame luminance back. `FlverLoader` passes **`clamp(0.10, minAdaptedLum, maxAdapredLum)`** — the captured geometry-pass `E` (`grayKey / adaptedLum`) on two frames (Nexus 094137, Boletaria) both imply the engine's adapted luminance rested at ~0.101, i.e. DeS scenes sit near 0.10 rather than at the authored floor (part 48). That gives `E ≈ 1.8` on every gameplay row-0 (m01–m08), `1.0` on m05 (Valley of Defilement, `grayKey 0.10`), `1.29` on m07's tight band — matching the captures; binding `minAdaptedLum` had given `2.25` (≈25% hot) on any map with an 0.08 floor. It stays a uniform so a bright exterior can still be given the other end; real auto-exposure still floats with the view (a Nexus bright-vantage frame captured `E = 1.148`), which a fixed stand-in can't follow — a load-time luminance pass is the accurate-but-heavier option. **This is the one value in the output stage not read straight from authored data.** **Identified 2026-09-06 (`docs/context.md` part 56) as the likely cause of a user-reported "maps are darker" regression** — the `0.10` floor is calibrated only against bright *outdoor* captures and applies the same `E ≈ 1.8` to every placement regardless of local darkness, where real per-frame eye-adaptation would raise `E` further in a genuinely dark room. `g_DiffuseMapColorPower` (part 51) was checked against a live capture and ruled out as the cause — every `HemDir3` draw in one frame really does carry that per-material 0.5/0.6 constant, confirmed from the patched microcode itself, not just the MTD description. Deliberately not patched with an unverified per-area proxy — see "Known deferred work" for why this is parked behind a real player camera instead.

**Both lighting models live in one shader family, selected by a `lighting_model` uniform** (`hemisphere_ambient.gdshaderinc`): `LIGHTING_HEM_ENV` (`MTD.LightingType=3`, the map/lightmap population — hemisphere + environment cubemaps) and `LIGHTING_HEM_DIR3` (`=1`, chr/parts/obj — hemisphere + `LIGHT_BANK`'s three directional lights, plus a **three-lobe Phong** specular: `pow(max(reflect(-V,N)·L_i, 0), g_SpecularPower)` over those *same* three directions, weighted by the single spec-only colour `colA_s` and the RGB specular sample. The reference bytecode builds no half-vector — it is Phong, not Blinn-Phong — and `LightBank.paramdef` has no per-light spec colour or a used spec-only direction, so `degRotX_s/Y_s` stays a uniform only for the unaudited `HemDir3Pnt*` family. Disassembly in `docs/context.md` part 34). The engine compiles a separate binary per combination; a uniform branch is the same choice made at the same point and is what Godot can express. **The two are mutually exclusive on purpose** — `HemDir3` carries no `Env` in its name and `MTD.LightingType.HemDirDifSpcx3` lists no environment term, so a HemDir3 material takes no cubemap contribution. That also avoids a material with no lightmap picking up `env_diffuse` at full strength, since the lightmap sampler defaults to white.

This is what took `g_LightingType=1` materials off `StandardMaterial3D`, which had no real lighting path at all in a project with no light nodes — the reason placed props rendered black without a `WorldEnvironment`. Verified on a real `m01` load: 75 surfaces route to HemDir3 and all 75 bind real directional lights.

**Every material with a real lighting model now goes to the shader family, lightmap or not** (closed 2026-08-28). A `g_LightingType=3` material shipping no lightmap is not a special case: the engine's gate is `min(shadow, lightmap)`, so such a material is gated by the shadow term alone — ~1 wherever nothing shadows it — and the shader's `hint_default_white` lightmap is the correct stand-in for that with no shadow system. It lands about 2.3x brighter than an equivalent lightmapped surface, not blown out. **This was the last population still relying on Godot's own lighting, and therefore the actual reason props rendered black without a `WorldEnvironment`** — the HemDir3 work alone didn't fix it because only 4 of m01's meshes are `g_LightingType=1`; the 60 black ones were all type 3 without a lightmap. Type 0 (unlit) splits: **opaque sky-dome backdrops** (MTD name contains "sky") get `sky.gdshader` — the diffuse through `output_stage.gdshaderinc`'s `des_fog` + `des_tonemap` + `des_tone_correct` (DeS runs sky domes through the same fog/exposure epilogue as lit geometry; the missing FOG_BANK green tint was why m02's backdrop spire read steel-blue — `docs/context.md` part 45). The ghost/dissolve and additive-VFX type-0 materials stay on `StandardMaterial3D`/`vfx_scroll`. On a real `m02` load: **1651 HemEnv + 37 HemDir3 + 1 sky + a few StandardMaterial3D**.

**Outdoor maps (m02 Boletaria etc.) read too bright/flat — root-caused and fixed across `docs/context.md` parts 43–48 (2026-09-04), user-confirmed "extremely accurate now".** The output stage had, in order of discovery: (1) HemEnv multiplies vertex colour by a fixed `0.6` we omitted (part 43 — `× 0.6` in `lightmap_common.gdshaderinc` / `terrain_blend.gdshader`); (2) `des_tonemap` was a Reinhard curve when DeS's whole tone pipeline is linear (part 43 — now `clamp(color · E, 0, 1)`); (3) the `FOG_BANK` colour distance-fade was missing entirely (part 45 — `des_fog`, restored from the HemEnv epilogue's own `mix()`, not RSX fog); (4) the sky/backdrop dome bypassed the output stage (part 45 — now `sky.gdshader`); (5) the in-scatter normalisation was a scalar where the captured `c106 == 1/c104` is per-channel (part 46), and (6) extinction runs bluer than scattering — `EXTINCTION_WAVELENGTH_WEIGHTS` from `c104` (part 47); (7) the adapted-luminance stand-in was `minAdaptedLum` where the captured exposure implies ~`0.10` (part 48 — now `clamp(0.10, min, max)`). m01 only ever "looked right" because errors (2)+(5) cancelled its strong scattering. The **"colour-space mismatch" theory (part 42) is dead**: a direct render probe under Compatibility (part 44) showed no linear→sRGB output encode and `: source_color` a genuine no-op on fetch — the pipeline is uniformly gamma-space. `des_tone_correct` was checked (part 44) and is already the exact `DS_Fil_HDR_ColAdj` matrix. Also ruled out: lightmap coverage (m02 is 85% lightmapped), directional lights (HemEnv has none), env-cube decode (byte-correct), drawparam binding (verified at runtime). **Remaining, smaller:** the v1 shadow term mis-/under-shadows (the ~17% non-lightmapped detail surfaces DeS gates with the cascaded shadow map get no gate here); no bloom; no player point light; the scatter *magnitude* (`scatter_distance_scale`) and the fixed-vs-dynamic exposure stand-in are still fits, deferred until the rest of the pipeline lands.

**`water.gdshader` is `unshaded` too, and takes the same output stage** as of 2026-08-28. It previously wrote its result to `EMISSION` with `ALBEDO=0` plus a `ROUGHNESS`/`SPECULAR` sun-glint from the editor's preview sun; now it writes `ALBEDO` and runs `des_output` like the other unshaded families (the 2026-09-05 rebuild — see the material-shading bullet above and `docs/context.md` part 50). `FlverLoader` gates the light-bank and output-stage uniform groups separately (`HasUniform`), so water gets fog/scattering/tonemap without needing ambient uniforms it has no use for.

**These shaders are `unshaded`.** They compute a finished colour the way DeS's material shaders do, so there is nothing for Godot's own lighting to add; `EMISSION`/`NORMAL_MAP`/`METALLIC` are gone and the `envSpc` term is summed straight into the result. Before this they were lit shaders in a scene with no lights and no `WorldEnvironment`, which meant **the only thing lighting them was the 3D editor viewport's default preview sun and sky** — an arbitrary input that scaled every result and tinted it blue. Anything measured against the old look was measured through that.

**The material-shading and output-stage halves are now structurally engine-accurate (parts 16–48), user-confirmed "extremely accurate".** DeS applies exposure and tone-correction inside the geometry-pass fragment shader, so `des_output` reproduces the whole per-material chain: `des_fog` (FOG_BANK fade) → `des_scatter` (H&P, per-channel `1/β` in-scatter, `EXTINCTION_WEIGHTS`) → `des_tonemap` (linear `saturate(color·E)`, `E` from `clamp(0.10, min, max)`) → `des_tone_correct` (the `DS_Fil_HDR_ColAdj` matrix, brightness/contrast/saturation/hue). Genuinely **not** here: the `ds_filter` *fullscreen* stages — the eye-adaptation feedback that makes `E` float with the view (a fixed stand-in can't follow it), additive bloom, DOF, motion blur. Those operate on the exposed framebuffer, so a raw geometry result reading slightly off is not on its own evidence the shading math is wrong.

## Bloom (`WorldEnvironment` glow)

`FlverLoader.BuildBloomEnvironment` adds one `WorldEnvironment` per loaded map (node "BloomEnvironment", added 2026-08-31). It approximates DeS's `DS_Fil_BrightPassFilter` → `DS_Fil_Bloom` stage, which is the one post-process effect that has to run screen-space **and** show in the editor's own 3D viewport — the only Godot mechanism that does both under the Compatibility renderer is the built-in `Environment.glow`. A `CanvasLayer`/`hint_screen_texture` pass composites only at runtime; `CompositorEffect` needs Forward+/Mobile.

**It is deliberately bounded to glow.** Every other `Environment` feature is pinned to identity/off — `AmbientLightSource`/`ReflectedLightSource` **disabled**, `TonemapMode = Linear`, adjustments/SSAO/SSIL/SSR/SDFGI/fog all off. This is *not* the "ambient/reflection `WorldEnvironment`" that earlier notes say this project must not have: the reason that one regressed was the `StandardMaterial3D` map population collapsing under engine ambient with no light nodes (part 25), and a glow-only Environment with ambient disabled cannot bring that back. The unshaded shader family takes no ambient or reflection regardless.

**Calibration** comes from `TONE_MAP_BANK` row 0: `bloomMul/100` → `GlowBloom` (0.80 Nexus, 0.50 Boletaria/Latria — the dial that actually carries the effect on an LDR buffer), `bloomBegin/100` → `GlowHdrThreshold` (0.20), plus a mid-level `SetGlowLevel` spread standing in for `DS_Fil_Bloom`'s wide downscaled gaussian. User-checked in-editor 2026-08-31: present and roughly right, Nexus a little hot — the numbers are a placeholder to retune against RPCS3, the mechanism is not.

**Ceiling.** `TONE_CORRECT_BANK` is a 3×3 colour matrix + offset (parts 43–44), applied in-shader by `des_tone_correct` per-part, which `Environment` can't be. Eye adaptation (`CalcAdaptedLum`) has **no path** under Compatibility (auto-exposure is Forward+/Mobile only), so `E` stays a fixed per-map stand-in; and `Environment` is one-per-viewport so it can never do per-part `ToneMapID`/`FogID` (which is why exposure/atmosphere stay in-shader). There is no HDR tonemap to host — DeS's chain is linear (part 43). Additive bloom is the one `ds_filter` stage that genuinely wants screen space; doing it accurately (not the glow-only `WorldEnvironment` approximation) would mean a `CompositorEffect` and a renderer switch off Compatibility — a fork avoided for weaker-hardware reasons.

## Sun shadows (`ShadowRenderer`)

`ShadowRenderer.cs` (a `[Tool]` `Node`, built by `FlverLoader.InstantiateMap` once every placement is in) gives a loaded map one directional sun shadow, driven by the map's **`SHADOW_BANK` row** (`m<XX>_shadowbank.param` against `ShadowBank.paramdef`, via `DrawParamReader.GetShadowBankRow`; `FlverLoader.AttachShadowRenderer` uses **row 0**, the map baseline — parts carry per-`ShadowID` rows but one region uses one). DeS uses **4-split *perspective* shadow maps** (the `ShadowBank` fields `calibulateFar`/`persedDepthOffset`/`radFactor` are all tagged "PSM"; the cast matrices in the frame captures are perspective, `rrc-shadow` / `docs/context.md` parts 37/49). This is **v2: one STATIC orthographic depth pass** over the lit casters' bounds — the projection is fixed in the world (fixed sun + fixed geometry ⇒ fixed shadow) and **does not follow the editor camera at all**. The only camera-dynamic part is the shader-side distance fade. The 4-split camera-relative atlas + the real PSM warp are layered on this later (`docs/PLAN.md`'s shadow item). opengl3 compile check clean; user-confirmed in-editor "about right now" (`docs/context.md` part 49).

**Region — static.** A `SubViewport` (2048×2048, `transparent_bg`, `own_world_3d`, `UPDATE_ALWAYS` — static content, this just keeps the texture populated in-editor) holds an **orthographic** `Camera3D` aimed along the **shadow's own** direction (`SHADOW_BANK.lightDegRotX/Y` via `FlverLoader.SunDirection`, *not* the `LIGHT_SCATTERING_BANK` sun), positioned once at map load. 2048² is DeS's full shadow *surface* — the engine splits it into a 2×2 grid of 1024² cascade tiles; v2 uses it as one map (the split waits for a player camera, see the reductions note). Region = the merged world-AABB of the lit casters, radius `min(½·diagonal + 2, 200)` — the 200 cap keeps atlas texels sane on a pathological multi-area MSB (m01_00_00_00 spans the Nexus hub *and* the Old One area far below); geometry past the cap goes unshadowed until the 4-split atlas, a deliberate v2 limit. `pullback = radius + shadowVolumeDepth + 5`, `far = 2·radius + shadowVolumeDepth + 10`. One sibling `MeshInstance3D` per placed map-piece/object mesh **that carries a lit map/prop material** (`FlverLoader.CastsSunShadow` — the `shadow_strength`-uniform test; sky domes / ghost / additive VFX on `StandardMaterial3D` and water excluded), each sharing the source `Mesh` *resource* with one shared `shadow_depth.gdshader` `MaterialOverride`. That shader is `unshaded, cull_front` (only back faces write depth → a lit surface sits ahead of its recorded occluder by ~the mesh thickness — the self-shadow-acne fix, trading mild contact-shadow light-leak) and writes linear light-space distance packed 16-bit across R,G.

**Receive side** (`hemisphere_ambient.gdshaderinc`, shared by `lightmap*` / `terrain_blend`): `sun_shadow(world_pos, view_distance)` projects through `shadow_light_clip` (`= light_proj · light_view`; `.xy/.w` divide — `.w` is 1 under ortho but the code stays general for the 4-split perspective phase) for the atlas UV, and rebuilds the receiver's own linear light-space depth through `shadow_light_view` (a second mat4, mirroring exactly what `shadow_depth.gdshader` wrote), unpacks the 16-bit occluder depth (`r + g/255`), and does a **rotated 12-tap Poisson-disk PCF** (point taps over ~2.5 texels, disk rotation hashed per fragment from `world_pos` so it dithers without shimmering on a static scene — the Compatibility stand-in for DeS's one hardware 2×2 `TXPR`) with `shadow_bias` (a small world-space-constant tiebreaker, `≈ 0.05/far`; `cull_front` is the real acne defence). It returns a **per-channel** term, the disasm form `1 − (shadow_density − shadow_tint)·fade·inShadow`: `shadow_density` = `SHADOW_BANK.densityRatio/100` (a full shadow is partial, never fully black), `shadow_tint` = `colR/G/B / 255` (lifts specific channels), `fade` = `clamp((fadeBegin + fadeRange − view_distance)/fadeRange, 0, 1)` from `fadeBeginDist`/`fadeDist` — **this is the only part that tracks the camera**: it makes shadows fade out with distance from the viewer, exactly as DeS does, without touching the cast. `vec3(1.0)` (no darkening) when `shadow_strength` is 0, faded out, outside the atlas, or on an empty (0.0) texel. Applied as DeS's **`min(shadow, lightmap)`**: on the env term for HemEnv, `×` on the directional + spec term for HemDir3; the two-colour hemisphere floor stays ungated (matches the bytecode). `view_distance` is threaded through `lightmap_shade` (all four `lightmap*` variants) and `terrain_blend`.

**Per-instance binding.** `ShadowRenderer.BindReceivers` pushes every shadow uniform (`shadow_map`, the three matrices, `shadow_bias`/`shadow_strength`/`shadow_density`/`shadow_tint`/`shadow_fade_*`) onto each caster surface material **once** — the projection never changes, so there is nothing to update per frame and `ShadowRenderer` has no `_Process`. It reuses the per-instance override `ApplyDrawParams` already made where a `LightID` resolved, and `Duplicate()`s the shared base material to an override where it didn't (so one map's shadow state never leaks onto another placement of the same reused model).

**Engine-accurate**: direction, `densityRatio`, tint, the distance fade, `shadowVolumeDepth`, and the `1 − (density − tint)·fade·inShadow` composition are all `ShadowBank.paramdef` fields + the `DS_*_Sdw` / `Csd` fragment disasm (`docs/context.md` part 49). **Reductions / deferred**: one static region, not the 4-split camera-relative **perspective** (PSM) atlas — `beginDist`/`endDist` (the cascade split ranges) and `calibulateFar`/`persedDepthOffset`/`radFactor` (the PSM warp) unmodelled, and with them the per-pixel/per-draw cascade select. **The 4-split waits for a player camera by design**: DeS's cascades track the view frustum (including look direction), so in the editor free-fly cam they'd sweep exactly the way the two reverted follower cuts did — a chase cam at gameplay speed is what makes CSM read as stable. The interim resolution lever is the 2048² atlas (4× the texels of the earlier 1024²); it's still a whole-region ortho box, so resolution is coarse on a large map (the cap trades reach for texel size). Poisson PCF over packed-8-bit depth stands in for one hardware `TXPR` on a true depth sampler; `cull_front` trades acne for light-leak; no alpha-scissor caster variant (foliage / `DepAlp` casts solid); the `lightDegRotX/Y` → vector reading is unverified (elevation-azimuth vs Euler); not wired into the "Load Folder" path (one SubViewport per model); a load-target node with a non-identity transform misaligns the clones (isolated world). Earlier this session: v2 first tried a mild-perspective camera (shadows swam as it followed the view), then an ortho camera that followed the view with texel-grid snapping (shadows still slid — a moving cast is a moving cast); both reverted for the static region (part 49). v1 was a single orthographic region with a coarse re-render threshold + 3×3 PCF (parts 38–41); a whole-map capped box (part 38) and a reverted `MapAreaCuller` draw-group cull (part 40) before that.

- **Nothing in the lightmap/blend shader family read the normal map — every lighting term was blind to it, which is why engraved/relief surface detail disappeared ("waxy" walls). Root-caused and fixed 2026-08-27; kept here for the reasoning trail.** Per-pixel normals and env-cubemap sampling landed together, as the scoping check at the end of this entry required. `hemisphere_ambient()` blends on `world_normal`, a varying computed from the **vertex** normal in `vertex()`, and the env term is a flat `lightmap` sample with no normal dependence at all. `NORMAL_MAP` *is* assigned, but in Godot that only feeds the engine's own lighting response — and this project has no light nodes, so it modulates nothing. The real HemEnv shader does the opposite: it reconstructs a per-pixel normal from the bumpmap (2-channel tangent-space sample, `Z = sqrt(1 - (x²+y²))`, TBN basis built by cross product) and uses that per-pixel normal for **both** the hemisphere blend factor **and** the env cubemap's reflection vector. So the fix is per-pixel normals inside our own shading math — **not** adding directional lights, which the map family provably doesn't use (see the `LIGHT_BANK` entry above). User-reported via a Nexus wall comparison where RPCS3 shows clear engraving relief in shadowed arches and this project shows nearly flat black. **Important scoping check before anyone implements this: per-pixel normals in the *hemisphere* term alone would be invisible in both current test areas.** The hemisphere blend interpolates between the `_u` and `_d` colours, and on the real rows those endpoints are equal or nearly so — `m02` rows 0/1/2/4 (Boletaria B0, the main test block) have `up` and `down` **byte-identical**, so the blend is a constant and no normal, per-pixel or not, changes its result; `m01` row 0 (the main Nexus) differs by only 0.06 total across RGB. The normal-dependence that actually carries engraved detail in the real shader is the **env cubemap reflection** (`TEX3D(11, reflect(V, N_perpixel))`), which is high-frequency and genuinely normal-driven — our env term is a flat lightmap sample instead. So per-pixel normals and env-cubemap sampling have to land **together** to be worth anything; neither delivers alone.

Needs a frame-capture cross-check (`rrc-draws` on a Boletaria frame vs. the MSB part list) before it can be trusted; it's the seam the eventual map assembler grows from (`docs/PLAN.md` Phase 1 item 4). Two earlier `WorldEnvironment`-based tonemap attempts were reverted (the real cause was the `StandardMaterial3D` population collapsing to near-black under `AmbientLightEnergy` with no light nodes in-scene, not the tone values); the fix was the in-shader output stage plus routing `g_LightingType=1` onto the `HemDir3` shader (part 25). See `docs/context.md`'s dig entries for that trail. Env cubemap names built in the `default` namespace don't resolve → white cubemap → the env terms degrade to their pre-cubemap flat form, as intended. The plain `FlverLoader.Instantiate` path (used by `InstantiatePlacement`, which overrides afterward) is unchanged. A placed character will still pick up its block's real `LIGHT_BANK` once enemy placement lands.

So there is no hardware-fog blend curve to capture, and `FOG_BANK` does not drive one. The RSX-fog `des_fog()` was removed 2026-09-03. **But `FOG_BANK`'s colour is not unused** — part 45 (2026-09-04) found it is the target of a hand-rolled `mix()` distance fade in the standard HemEnv fragment epilogue (not ~7 niche shaders — every one), verified exact against the bank on m01/m02/m03/m06. A new `des_fog` + `GetFogBankRow` + `ApplyFogBank` implement it; see the output-stage section and `docs/context.md` parts 36, 45.

- **User testing of `Objects` placement (2026-08-17) surfaced four real gaps, all investigated and root-caused against real data rather than left as guesses:**

  - **Some placed `Objects` are event/cutscene-gated content that MSB alone can't distinguish from always-visible content** (an NPC's droppable personal item, an archstone never seen in normal Nexus traversal, a boss-fight prop thrown mid-cutscene). Checked `Part.DrawGroups`/`DispGroups` (also already parsed, unused) as a possible static gate — ruled out: the flagged objects' `DrawGroups` overlap normally with always-visible objects' groups, so this isn't a spatial/collision-area visibility question. The real gate is almost certainly DeS's EMEVD event-script layer (which sets the flags controlling spawn/despawn/cutscene-triggered visibility) — a wholly separate, unparsed system, out of scope for the graphical/model-side priority. Same tell as the `LightID=255` sentinel: `_0000` has `InitAnimID=1` (an active animation), the other three all have `InitAnimID=-1` (unset). Best read: inactive stub/reference entries, not meant to independently render. A cheap heuristic (skip `Objects` with `InitAnimID=-1` at the exact origin) could hide this specific case, but hasn't been checked against the wider corpus for false positives — not applied yet.
  - **Some `Objects`' materials don't visually match world lighting because they never get lightmapped at all, not because of a separate "dynamic lighting" system** (the user's working theory going in). Notably, their MTDs are literally the character `_Skin` family (`M[D]_Skin.mtd`/`M[DB]_Skin.mtd`) — these props reuse chr-style materials rather than having their own lightmapped map-prop materials. Same already-documented gap as the character/parts cubemap-reflection and `WorldEnvironment` items above, now confirmed to extend to at least some `Objects`, not just chr/parts.

- **Character/parts specular accuracy beyond roughness is unimplemented — and confirmed (2026-07-24, scouted per user request) to be a real cubemap reflection system.** `g_SpecularMapColor`/`g_SpecularMapColorPower` (tint/intensity) and `g_EnvSpcSlotNo` (an environment-reflection slot index) are real per-material MTD fields, present on every Phong-lit chr/parts material (`g_LightingType=1`, e.g. `C_Metal[DSB]_Skin.mtd`/`C_Leather[DSB]_Skin.mtd`, each with its own `g_SpecularPower`/`g_EnvSpcSlotNo`). **`g_SpecularMapColor`/`g_SpecularMapColorPower` are now read** (`ReadMtdShading` computes `MtdShading.SpecularTint` for every material, added 2026-09-15 for the HemEnv map family — see "Map shading fix" above) **but chr/parts (`HemDir3`, `hemdir3_specular`) still has no consumer for it**, same "read, no consumer" shape as `EnvSpcSlot`/the cubemaps below — `hemdir3_specular`'s three-lobe Phong is weighted by `spec_light_color`/`g_SpecularPower` only. `other/envlight.tpf` in the raw game root (outside `AssetExtractor`'s category allowlist, never extracted) holds `EnvSpc_def_000`-`_003`/`EnvDif_def_000`, each a genuine 64×64 `TPF.Texture.Type=Cubemap` — `C_Metal[DSB]_Skin.mtd`'s `g_EnvSpcSlotNo=2` and `C_Leather[DSB]_Skin.mtd`'s `=1` line up exactly with these indices. A parallel per-map drawparam bank family also exists — `paramdef/envlighttexbank.paramdef` + `param/drawparam/{m01..m08,m99,default}_envlighttexbank.param`, same shape as `LIGHT_BANK`/`FOG_BANK` — with `resNameId_Dif0`/`resNameId_Spc0..3` (per-slot resource-ID references; only the default bank's 1:1 mapping onto `envlight.tpf` is confirmed, per-map resolution and where those textures would live isn't) and `sepcPow_Dif0`/`_Spc0..3` (per-slot specular power). The numeric calibration lives in the MTDs and the drawparam banks (the same place water's `DS_Water_Env` params turned out to be — see the water bullet), which for chr/parts means the `envlighttexbank` family above plus `g_SpecularMapColor`/`g_EnvSpcSlotNo`; the `.rrc` capture route can confirm the param → constant mapping the way it did for water. **The per-map cubemap resolution rule (referenced above as unconfirmed) was recovered exactly 2026-08-27**: every map ships `map/<mXX>/<mXX>_9999.tpf` with real `Cubemap`-typed entries named `EnvDif_<mXX>_<NNN>`/`EnvSpc_<mXX>_<NNN>`, and `LIGHT_BANK`'s own `envDif`/`envSpc_0..3` integer fields are that `NNN` suffix (zero-padded, case-insensitive) — verified against every `LIGHT_BANK` row actually referenced by an MSB part, 930/930 resolved. `g_EnvSpcSlotNo` (0-3, on 530 MTDs) picks which of the four `envSpc` slots a material uses, and correlates with `g_SpecularPower` roughly monotonically by slot (median specular power 4/7/60 for slots 1/2/3; slot 0 is a mixed "unset" default bucket, not "roughest"). **Cubemap decoding shipped 2026-08-27 — `FlverModelBuilder.ResolveEnvCubemap(mapPrefix, cubemapName)` returns a real Godot `Cubemap`, still with no consumer.** The TPF entries are *not* DDS-wrapped and the format differs per map (`m02`: `format=10`, 32x32, 24576 bytes = 6 × 32×32×4 uncompressed; `m01`: `format=0`, 64x64, block-compressed with a per-face mip chain, 2744-byte stride). `Headerizer` already handles cubemaps (`CUBEMAP_ALLFACES`, and note its own comment that cubemaps pad to *eight* textures) — but **Pfim has no cubemap concept and silently decodes face 0 only**, returning one face plus its mips. So `DecodeCubemap` re-wraps each face as its own single-image DDS (copy the header, zero `dwCaps2` at offset 112, append that face's slice) and runs Pfim per face, reusing its DXT decoding rather than reimplementing it. Faces come back as `Rgba32` for `m01` and `Rgb24` for `m02`, so both are handled — the 2D path's throw-on-anything-but-`Rgba32` would have rejected half the corpus. Cached per `<mapPrefix>/<name>` including nulls, cleared by `ResetCaches()`. **Both halves of the lookup are now read and neither has a consumer**: `DrawParamReader.GetEnvCubemapNames(blockName, lightID)` returns the five names a row selects, and `MtdShading.EnvSpcSlot` carries the material's slot (`-1` = the 82 MTDs that don't declare one, distinct from a real slot 0). Deliberately stopped there — how a cubemap should reach a material is a separate unsettled question (`StandardMaterial3D` has no cubemap slot, and the last time reflection response was added with nothing real to reflect it regressed every map surface — see the roughness revert above). `GetEnvCubemapNames` returns a `Godot.Collections.Dictionary` rather than a typed struct **because a custom C# struct is not a Godot Variant type and therefore cannot be called from GDScript at all** — which would make it unverifiable, since a throwaway GDScript check script is this project's only test path. Worth remembering before adding any other data-only C# API here. **Independently cross-validated 2026-09-06** by diffing the real "PC Remaster" fan mod's own modified files against vanilla (`docs/context.md`'s "Part 55 follow-up 3"): it enables cubemap reflections on armor by changing `g_LightingType` from `1` (`HemDir3`, no env term) to `3` (`HemEnv`, this project's map family) on every chr/parts MTD, with a paired specular re-tune on the same materials — the exact mechanism this entry already describes, confirmed from a completely independent source. Not something to adopt as-is (vanilla DeS armor is real specular tuning, not this - the mod is a deliberate, re-tuned enhancement, not a restoration).
