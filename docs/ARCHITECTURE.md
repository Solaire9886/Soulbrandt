# Architecture

Canonical reference for how the Soulbrandt asset-import pipeline works today: what this
is, current conventions, format quirks, known gotchas, and what's still missing. `docs/PLAN.md`
has the roadmap — why things are built this way and what's coming. `docs/context.md` has the
session-by-session investigation history: the real bugs already found and fixed (with how
they were confirmed, not just guessed), interop gotchas, environment quirks, and dead ends
already tried and rejected — optional reading, useful for the *why* behind something here
or to check whether an approach has already been ruled out. `AGENTS.md` is the AI-agent
operating-instructions file and just points here for anything substantive.

## What this is

A Godot 4.7 (.NET/C#) project building a native asset-import pipeline for **Demon's Souls (PS3)**, reading FromSoftware's proprietary formats (FLVER0 meshes, TPF textures) directly into Godot resources. Project display name is "Soulbrandt"; the C# assembly/csproj is `Soulbrandt` too (`project.godot`'s `[dotnet] project/assembly_name` matches) — renamed from an old `Boletaria` codename, kept only as flavor text in a few in-code comments referring to the *in-game* kingdom of Boletaria, unrelated to the project name.

No game assets are bundled in this repo. `mounted` (gitignored) holds the user's own game copy, populated by an in-editor mount action — see "Asset mounting" below.

The repo (`github.com/Solaire9886/Soulbrandt`) is public and licensed **GPLv3** — not an arbitrary choice: `SoulsFormatsNEXT` (see below) is GPLv3 with no linking exception, and this project links against it directly, so the combined distributed work must be GPLv3 too. `README.md` carries an RPCS3-style disclaimer (no proprietary assets, no piracy support, no DRM-bypass methods); `CONTRIBUTING.md` covers the contributor workflow.

## Standing priority: stability and resource safety

The importer works and is good at what it resolves — but getting it *working* has so far taken priority over getting it *safe to run unsupervised, at scale, on hardware that isn't this dev machine*. That needs to change as the project grows. The end goal (see `docs/PLAN.md`) is a regular, non-technical user pointing this at their own full game copy and eventually playing a recreation built on it — the same extraction/import machinery they'd run has to be far more resilient than "usually works, re-run it if it doesn't."

This isn't a hypothetical concern — doc history already shows real instances (all pre-2026-07-24, several since closed structurally rather than individually — see the note at the end of this section): a genuine FLVER0 vertex-layout crash that needed a corpus-wide fix before a bulk reimport was even reliable; a `Fatal error. Invalid Program: attempted to call an UnmanagedCallersOnly method from managed code` flake that killed a bulk reimport mid-batch and was just re-run to recover, not root-caused; a real case (post editor-crash) of 1395/3411 `.flver.import` files left pointing at cache artifacts that were never actually written — silently invisible to a later incremental `--import`, not a loud failure; and a real-rendering-driver verification path that's explicitly documented as too heavy to ever run concurrently with the GUI editor or another such check. None of these were caught by design — they were each found the hard way, after the fact.

Going forward, hangs, crashes, and runaway CPU/memory/disk usage anywhere in the extraction/import pipeline are treated as bugs worth root-causing, not flakes to route around by re-running — a shipped tool a regular user points at their own multi-GB game copy doesn't get the "just try again" luxury a dev-only reimport does. Concretely, this shapes future importer/extractor work: prefer failing safely and detectably (bounds on memory/CPU/time, resumability from partial progress) over silent retries or leaving corrupted intermediate state — the stale `.import` cache case above is exactly the failure shape to design against. An already-investigated, confirmed-external cause (e.g. Godot's own threaded-import-host bug) is fine to leave documented as a known flake; a newly-seen one is not, until it's actually been looked into.

**Most of the specific instances listed above no longer apply, structurally, not because they were individually patched.** The 2026-07-24 architecture pivot (see "Architecture" below) removed `EditorSceneFormatImporter` registration for `.flver` entirely — `.flver` is no longer a Godot-recognized resource type, so Godot's own threaded reimport queue never dispatches against it at all anymore. That closes the stale-`.flver.import`-metadata case, the `UnmanagedCallersOnly` reimport flake, and the concurrency self-throttle's whole reason for existing (all three were specific to that queue) as a side effect of removing the mechanism they depended on, not because each was individually root-caused and fixed. The general principle — fail safely and detectably, don't paper over hangs/crashes with retries — still applies fully to what's left: `AssetExtractor.cs`'s extraction step (still real I/O against a user's own multi-GB game copy) and `FlverLoader.cs`'s manual load path (still real parsing/decode work, just no longer routed through Godot's import system). This pivot doesn't make this category of risk go away in general — it removed one specific, well-documented source of it.

## Build & verify

Godot's own C# tooling (`GodotTools`, used by the editor's build/import machinery) hardcodes a `net8.0` requirement with no cross-major rollForward. Installing a .NET 8 SDK alongside whatever newer SDK is already present (via your distro's package manager where one packages it, or the official direct download from dotnet.microsoft.com otherwise) satisfies this with no manual `DOTNET_ROOT` override needed — plain `dotnet`/`godot-mono` on `PATH` resolves it. (An earlier revision of this doc had a manual merged root at `~/.dotnet-godot`, under the mistaken assumption that no distro packaged a net8 SDK at all; confirmed obsolete and dropped — see `docs/context.md`'s "Environment specifics" section for the full history.)

**Build the C# assembly** (do this after any change under `addons/archstone/`):
```
dotnet build Soulbrandt.csproj
```
Do **not** use `godot-mono --headless --build-solutions` to build — it reliably hangs in this environment. Plain `dotnet build` against `Soulbrandt.csproj` is the proven path.

**There is no `res://` reimport step anymore, and no unit test suite.** `.flver` is not a Godot-recognized resource type at all — no `EditorSceneFormatImporter` is registered for it (see "Architecture" below for why, and docs/context.md's reimport-concurrency entry for the full removal story). This means the entire "Force a reimport" batching recipe, per-batch cache invalidation, stale-`.flver.import` diagnosis, and "zero errors across a full bulk reimport" verification standard that used to apply here are gone, not just outdated — there is no reimport queue left to invalidate or batch. Everything from `mounted/` through to a visible model in the editor is driven by explicit user action (`FlverLoader.cs`, triggered from the Archstone toolbar's "Load Model(s)..."/"Load Folder..." — see "Asset mounting" below), not Godot's own import machinery.

Verification is done with throwaway `SceneTree`-extending GDScript scripts run headlessly, e.g.:
```
godot-mono --headless --path . -s check.gd
```
where `check.gd` does `load("res://addons/archstone/scripts/FlverLoader.cs").new().Instantiate("res://mounted/chr/c9999/c9999.flver")` and inspects the resulting node tree (surface count, `surface_get_material(i).albedo_texture`, etc. — the child is a real `MeshInstance3D`/`ArrayMesh` now, see "Architecture" below). No import/reimport/cache-invalidation step is needed at all — `FlverLoader` reads straight from `mounted/` on every call unless its own in-memory cache already has that path (`Evict`/`EvictAll` bust it manually). Write these scripts to a scratch location and delete them when done — none should be committed.

**`--headless` never actually compiles GLSL.** It forces Godot's dummy rendering driver, which happily loads/saves `ShaderMaterial`/`Shader` resources and reports zero errors regardless of whether the shader source is even valid — a clean `FlverLoader` load only proves the *build step* (material building, texture resolution) didn't throw, not that any new or edited `.gdshader`/`.gdshaderinc` actually compiles. Confirmed the hard way: a real shader-compile bug (Godot's built-ins like `ALBEDO` aren't assignable from a helper function, even a `#include`-d one only ever called from `fragment()`) shipped straight through a headless check with zero errors and only surfaced as broken rendering once opened for real. To actually catch shader errors, force a real rendering driver: `xvfb-run -a godot-mono --path . -s check.cs --rendering-driver opengl3 --display-driver x11` (needs `Xvfb`/`xvfb-run`, both in most distros' repos) — errors print as `SHADER ERROR: ...` with a file/line. This spins up real (software, via Mesa llvmpipe) GPU rendering, which is far heavier than a normal headless run — never run it while the GUI editor or another such check is also open; see docs/context.md's environment-specifics section on why concurrent Godot processes against this project are unsafe in general.

## Architecture

**There is no `EditorSceneFormatImporter` anymore — `.flver` is not a Godot-recognized resource type at all.** This is a deliberate 2026-07-24 pivot, not an oversight: an earlier `FlverSceneImporter.cs` did register one, but registering *any* `EditorSceneFormatImporter` for `.flver` meant every `res://mounted` filesystem scan (including the one that used to run automatically right after extraction) queued every `.flver` through Godot's own threaded reimport dispatch — the root cause of a hang → `systemd-coredump` CPU spike → crash cycle that a concurrency self-throttle inside the importer couldn't fully fix, because the instability traced to Godot's own reimport-host machinery, which a plugin has no control over (confirmed by reading Godot's engine source directly — see docs/context.md's reimport-concurrency entry for the full investigation, including the two confirmed dead ends: no `_can_import_threaded()` hook exists on this base class, and the `threading/worker_pool/max_threads` project setting is hardcoded-ignored for the editor process). The fix was architectural, not a tighter gate: stop routing `.flver` through Godot's import system at all.

The logic is split across two files instead:
- **`addons/archstone/scripts/FlverModelBuilder.cs`** — all the real FLVER0 parsing/mesh/material/texture-resolution logic, with zero dependency on Godot's import system. `BuildMesh(path, out anySurface)` reads a `.flver` straight from disk and returns an `ImporterMesh` with every surface's material already resolved (`StandardMaterial3D`, or `ShaderMaterial` for terrain-blend/water/lightmap materials, see below) — there is no intermediate OBJ/MTL/PNG file relay. (`desflver_test/`, an old standalone reference console app used early on for manual FLVER-parse comparison, has been removed — everything it covered now lives here and in this doc; its OBJ-export quirks, V-flip and triangle winding swap, never applied to the native path anyway — see the FLVER↔Godot conventions below.)
- **`addons/archstone/scripts/FlverLoader.cs`** — a plain `RefCounted`, one instance per editor session (created in `archstone.gd`'s `_enter_tree()`), holding a `FlverModelBuilder` plus its own session-lifetime `Dictionary<string, ArrayMesh?>` cache keyed by path. `Instantiate(path)` builds-or-reuses a mesh and returns a fresh `Node3D` wrapping a `MeshInstance3D` for that placement; `Evict`/`EvictAll` bust the cache (for after an importer-code change — no reimport step to force, just call this and load again). `EvictAll` also calls `FlverModelBuilder.ResetCaches()` (2026-07-26), clearing its texture-resolution caches (`_dirTextureCache`/`_decodedTextureCache`/the sibling-obj index below) too — not needed for a code-only change, since nothing on disk moved, but covers re-running "Import" mid-session to pull in new/changed `mounted/` content (e.g. testing modded assets) without needing a full editor restart to see it. Only ever called from one thread at a time (a toolbar button click), so its cache is a plain `Dictionary`, not `ConcurrentDictionary` — there's no Godot-owned scheduler dispatching concurrent calls against it the way the old importer had. `InstantiateMap(msbPath)` (2026-07-24, see "MSB map placement" below) builds on this same cache: it's one `Instantiate()` call per resolved map-piece, so a model reused across placements or maps only parses once.
- **`addons/archstone/scripts/MsbLoader.cs`** (2026-07-24) — pure `.msb` parsing/resolution, no scene nodes, mirroring the split above. `ReadMapPieces(msbPath)` reads a `.msb` via `SoulsFormatsNEXT`'s `MSBD`, resolves each `MapPiece` part's `ModelName` against the sibling model-bucket folder (`mapstudio/{name}.msb` ↔ `map/{name}/`, a confirmed 1:1 naming convention), and returns each part's model path plus real `Position`/`Rotation`/`Scale`. See "MSB map placement" below for scope and the still-open rotation-correctness caveat.
- **`addons/archstone/scripts/archstone.gd`**'s Archstone toolbar button now has four loading-related menu items alongside Mount/Import/Clear: **"Load Model(s)..."** and **"Load Folder..."** (both `EditorFileDialog`, `ACCESS_FILESYSTEM`, rooted at `mounted/` — the same proven dialog type already used for "Mount...", not a custom file browser) call `FlverLoader.Instantiate()` for each resolved `.flver` path and drop the result under the currently-selected Scene-dock node (if it's a `Node3D`) or the edited scene's root; **"Load Map..."** (same dialog pattern, rooted at `mounted/map/mapstudio`, filtered to `*.msb`) calls `FlverLoader.InstantiateMap()` per selected `.msb`; and **"Reload Loaded Models"** calls `FlverLoader.EvictAll()`. An earlier version of this used a custom `Tree`-based dock for browsing/selecting files instead of `EditorFileDialog` — dropped after it proved unreliable in the live editor (rows wouldn't expand) in a way that couldn't be diagnosed blind; `EditorFileDialog` is Godot's own well-tested control, already working elsewhere in this exact file, so reuse beat continuing to debug a from-scratch `Tree` implementation.

**MSB map placement (2026-07-24) — map-piece placement only; the "decorations at the origin" bug this surfaced turned out to be a separate, now-fixed `FlverModelBuilder` gap, not an MSB problem.** `FlverModelBuilder` used to have no concept of map layout at all — bulk-loading a map folder just dropped every loose `.flver` at the origin. `MsbLoader`/`FlverLoader.InstantiateMap()` fix this for `MSBD.PartsParam.MapPieces`: `Position.X` is negated the same way `FlverModelBuilder`'s own vertex-position convention already does, and `RotationDegrees.Y`/`.Z` are negated to compensate the same mirror while `.X` is left alone. Corpus-checked, not assumed: most `MapPiece` parts carry an identity `Position`/`Rotation` in `MSBD` itself (a single-instance piece's placement lives in its own FLVER data, not MSB — see the rigid mesh-to-node binding entry above), but a real minority are genuinely reused multiple times and do carry a real per-instance MSB transform — e.g. `m08_00_00_00` has one model (`m0001B0`) placed **nine** separate times (`m0001B0_0000`-`_0008`, corrected from an earlier "seven" estimate) at nine distinct positions/rotations. **Spot-checked, not fully proven (2026-08-17):** rendered the five-instance `m0001B0_0000`-`_0004` chain (all pure-Y rotations, `-90°` to `149°`) headlessly under a real rendering driver and read the resulting image directly — it forms one continuous, non-mirrored rock formation whose curve matches the rotation sequence, with no piece inside-out, backwards, or disconnected. Only `RotationDegrees.Y`'s sign is actually exercised by this case (`.X`/`.Z` are `0` on every real instance checked so far); this naturalistic rock geometry also lacks the strong directional cues (text, a doorway, an asymmetric architectural feature) that would make a subtle handedness flip obvious, so treat this as good supporting evidence rather than the same confirmation bar the X-negation/winding-swap conventions above were held to — a stronger test case, if one turns up, would still be worth the same visual check. `MapPiece`-membership itself is real, working value regardless: it's now possible to tell which `.flver` files in a block folder are actually placed versus sitting there unreferenced — see "Known deferred work" below for how this relates to the Boletarian Palace z-fighting question. User testing of this first slice found real placement bugs (gates/fountains/whole building interiors sitting at the world origin) that turned out to be caused by `FlverModelBuilder` ignoring FLVER's own rigid mesh-to-node binding, not by anything in `MsbLoader`/`InstantiateMap` — now fixed, see the coordinate-conventions entry above and docs/context.md. Scoped to `MapPieces` only this pass — `Objects`/`Enemy`/`Player`/`Collision`/`Navmesh` parts are explicitly deferred (see "Known deferred work"). `LightID` → `LIGHT_BANK` resolution shipped 2026-08-17 (see "Lightmaps" below); `FogID`/`WorldEnvironment` fog wiring is still deferred.

**`Objects` placement shipped (2026-08-17) — props/decorations/interactible scenery (`MSBD.Parts.Objects`), the second real part category after `MapPieces`.** `MsbLoader.ReadObjects()` resolves each `Object` part's `ModelName` (e.g. `o0300`) against the mounted `obj/` corpus rather than a map block folder — a genuinely different, but simpler, resolution rule: every mounted `obj/` container splits its `.flver` into its own `sib/` subfolder (`obj/{id}/sib/{id}.flver`, confirmed 100% consistent across all 777 real mounted `obj/` folders, not a guessed convention), so no directory scan or fallback chain is needed, just a deterministic path. `MsbLoader`'s placement-construction logic (position/rotation/scale/`LightID`/`FogID` extraction) is now shared between `ReadMapPieces`/`ReadObjects` via a private `BuildPlacements()` helper taking a per-category model-path resolver, rather than duplicated. `FlverLoader.InstantiateMap()` places both `MapPieces` and `Objects` under the same root, sharing the identical transform/lighting logic (`InstantiatePlacement()`) — texture resolution needs no new code at all, since `FlverModelBuilder`'s existing `CandidateDirs` chain already handles every obj/ container the same way it does for direct "Load Model(s)..." loads. Verified against real data: `m01_00_00_00` (Nexus) goes from ~60 `MapPieces`-only placements to 209 total (206 with mesh, 3 meshless — the same already-documented dummy-marker FLVER0 case, not new); `m08_00_00_00`'s 28 real `Objects` all resolved and placed with no crash. `Enemy`/`Player` parts are deliberately **not** next in line even though they're the same shape of work — no game-logic systems (AI, combat, animation state) exist yet to make placed enemy markers anything but inert clutter; revisit once that changes.

**`ImporterMesh`/`ImporterMeshInstance3D` are import-pipeline-only placeholder types with no rendering of their own — this bit twice, worth not reintroducing.** Godot's own scene-import post-processing (LOD/shadow mesh generation, compression) is what normally converts an `ImporterMesh`/`ImporterMeshInstance3D` into a real `ArrayMesh`/`MeshInstance3D` as part of saving an imported scene — that conversion is a property of going through the `res://` import pipeline, not of the `ImporterMesh` type itself. Since nothing in this project goes through that pipeline anymore, nothing does that conversion either: an early version of `FlverLoader.Instantiate()` used `ImporterMeshInstance3D`/`ImporterMesh` directly (mirroring what the old importer used to return) and produced scenes that were structurally correct — real nodes, real mesh data, real materials — but **completely invisible**, since `ImporterMeshInstance3D` never hooks into the rendering server at all. Fixed by calling `ImporterMesh.GetMesh()` (the same bridge API Godot's own importer uses internally) to get a real `ArrayMesh`, wrapped in a real `MeshInstance3D`. `FlverModelBuilder.BuildMesh()` still returns an `ImporterMesh` (a perfectly good mesh-authoring API on its own, and `GetMesh()` is only one call away) — the conversion happens in `FlverLoader.Instantiate()`, the one place that actually needs a renderable result.

Any child added under a loaded model's root **must** have `.Owner` set (recursively) to the actual scene root it's ultimately parented under — `PackedScene.pack()` only serializes descendants with an owner; a plain `AddChild()` alone is invisible to a scene save. `archstone.gd`'s `_set_owner_recursive()` does this after `FlverLoader.Instantiate()` returns, since `FlverLoader` itself doesn't know what scene it'll end up under.

Per-mesh geometry is built as plain C# arrays (position/normal/color/UV/index) and handed to the engine in one `SurfaceTool.CreateFromArrays()` call, rather than a per-vertex `SurfaceTool.AddVertex()`/`SetNormal()`/`SetUV()`/... loop — same per-vertex math, far fewer engine-boundary calls. `GenerateTangents()` still runs on the resulting `SurfaceTool` afterward; that call has no array-based equivalent.

Some FLVER0 meshes' own `BufferLayout` genuinely omits the Normal/UV/VertexColor member entirely (confirmed via `SoulsFormatsNEXT`'s `Vertex.Read`: a layout applies uniformly to every vertex in a mesh, so checking vertex 0 for a missing channel is representative of the whole mesh, not a per-vertex guess) — real, not a parse failure; the confirmed cases (`m9999b0`, `m9900`, `o9996`) all have the "reserved/debug ID" look FromSoft games use for collision-only or tool geometry never meant to render normally. The per-vertex loop falls back to `Vector3.Up`/`Colors.White`/`Vector2.Zero` for whichever channel a given mesh lacks, rather than indexing `[0]` unconditionally. `Mesh.Triangulate`'s `doCheckFlip` (its own internal winding-flip heuristic for triangle-strip meshes) is only requested when the mesh's vertices actually carry Normal data — the check itself reads `Normal` internally and is meaningless without it, so passing `true` unconditionally previously crashed the same class of mesh one level deeper inside `SoulsFormatsNEXT`.

**Texture resolution tries an ordered chain of candidate directories per texture reference** (`CandidateDirs`/`ResolveTexture` in `FlverModelBuilder.cs`), because Demon's Souls doesn't use one convention across categories, containers, or even individual materials on the same model. All five rules share one cache/merge primitive, `GetMergedTextures`/`LoadDirTextures` backed by `_dirTextureCache` (a plain `Dictionary<string, Dictionary<string, TPF.Texture>>` keyed by resolved directory — a plain `Dictionary` is safe here specifically because `FlverModelBuilder` is only ever driven by `FlverLoader`, which only ever calls it from one thread at a time; an earlier version of this cache was a `ConcurrentDictionary` back when a now-deleted `EditorSceneFormatImporter` dispatched calls across multiple worker threads against the same instance — see "Architecture" above), which merges *every* `.tpf` found in a directory rather than opening one guessed-basename file — a folder can hold more than one real tpf side by side (e.g. `WP_A_1503.tpf` and a separate `WP_A_1503_L.tpf` variant), and the entry a reference needs isn't always in the one whose name matches the folder. Corrupt/zero-byte `.tpf` files (3 confirmed real cases in the shipped game data: `o3104`, `o0050`, `o7999` — not an extraction bug) are skipped with a `GD.PushWarning` rather than aborting the whole model's import. Texture-name lookups are case-insensitive throughout. A second cache tier, `_decodedTextureCache` (keyed by `TPF.Texture` reference identity — safe since `TPF.Texture` has no `Equals`/`GetHashCode` override and `GetMergedTextures` already returns the same cached instances for a given directory across calls), sits downstream in `ResolveTexture` and dedupes the actual decode work (`Headerize` → Pfim DXT decompress → BGRA/RGBA swap → `GenerateMipmaps`) — `_dirTextureCache` only avoids re-reading/re-parsing a `.tpf` file, not re-decoding a texture already resolved once from it, and shared textures (a map-area bucket's ~19 tpfs reused by every piece in that area, cross-category reuse) are the norm here, not the edge case. Both caches are cleared together once tracked decoded-texture memory crosses a machine-scaled budget (`MaybeEvictDecodedTextures`, 25% of whatever `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes` reports for the current machine/container, scaling down automatically on weaker target hardware). In trust order:
1. **The model's own real container** (`OwnModelDir`) — same-basename `.tpf` flattened next to the `.flver` for chr (`mounted/chr/c2000/c2000.tpf`, no `tex` subfolder in the real container at all), or a sibling `tex/` folder for obj/parts, whose container instead splits the flver into its own `sib/` folder (`mounted/obj/o0211/sib/o0211.flver` + `mounted/obj/o0211/tex/o0211.tpf`) — confirmed via directory scan across every mounted obj/parts model, not an edge case. Always correct when the reference actually lives here, since it's exactly what got extracted for this specific model.
2. **The texture's own reference path** (`RefPathDir`) — parses the `Model/.../tex/` segment out of the reference string itself (a dev-tool path, not something the game re-validates at runtime) relative to the mounted root, nested-`tex/`-then-flat fallback. Correct for ordinary map pieces (whose per-area bucket, e.g. `mounted/map/m03/`, holds ~19 numbered `.tpf` files shared by every piece in that area) and for genuine cross-category reuse — e.g. `m4020b0.flver` (a Boletarian Palace corpse pile) uses `chr/c2000`'s own NPC texture set directly, resolved by this same rule with no separate code path needed.
3. **A sibling texture slot on the same material** (`SiblingMapAreaDir`) — if another reference on the same material resolves under `mounted/map`, tries that map-area folder for this one too. Recovers a stale/copy-pasted ref that still names the model's own folder while the real texture lives in a shared map-area bucket — confirmed on all six Nexus archstones (`o1000`-`o1050`): every one shares a single `m01` body texture, correctly labeled only on the `g_Lightmap` slot, with `g_Diffuse`/`g_Specular`/`g_Bumpmap` all copy-pasted from the `o1000` template and never updated.
4. **A map-area prefix baked into the filename** (`MapPrefixDir`, regex `^(m\d\d)_`) — tried even when every reference on the material lies about its own category. Confirmed on `o3120`/`o3129` (Boletaria wall pieces), where even the lightmap ref is mislabeled under `obj/o3120` but every texture name still honestly starts `m03_`.
5. **An unrelated obj/ model's own container** (`SiblingObjTextureDir`, 2026-07-26) — last resort, for a texture that isn't duplicated into *any* of the folders rules 1-4 check at all, only into a handful of other obj/ containers that happen to use the same shared prop-family asset. Builds a `textureName → [(objId, dir)]` reverse index over the whole `mounted/obj/` corpus, lazily and only once per editor session (most models never miss all four rules above; when they do, the index build also warms `_dirTextureCache` for whichever directory actually resolves the miss, so the texture itself isn't re-parsed from disk a second time). Ties among multiple hits are broken toward the numerically closest obj ID, not an arbitrary first match — confirmed real via two independent cases that both cluster by ID proximity: `o6510_1`'s bottle/vase pieces (`m02_obj_00.tga`, only in `o6504`/`o2401`-`o2402`'s own containers) and a cluster of `m02_01` map-piece decor (`m2020b1`, `m5100b1`-`m5190b1`, `m2230b1` — firewood/cart/tub clutter whose textures live only in the `o24xx` obj/ range, never in the shared `mounted/map/m02` bucket). See `docs/context.md` for the full investigation. `FlverLoader.EvictAll()` resets this index (along with `_dirTextureCache`/`_decodedTextureCache`) via `FlverModelBuilder.ResetCaches()` — see the `FlverLoader.cs` entry above.

Together rules 3-4 resolve ~90% of the obj/parts references that don't already succeed via rule 1 or 2 (measured against every mounted obj/parts material). A FLVER0 texture entry's `ParamName` (the slot, e.g. `g_Diffuse`) is a separate optional field that's sometimes simply absent even though the path and the texture itself are both real — `InferMissingParamNames` (runs first, before any of the above) recovers these by positionally matching each untyped entry against a `Dif`/`Spc`/`Bmp`/`Lit`/`Dcl` token found in the MTD's own bracket tag, in the same order the entries already appear — validated 100% (83/83 real affected materials, 44 files spanning chr/map/obj/parts, including the `c9983`/`c9981` Ghost/Wanderer phantom-gear template) before being wired in.

**FLVER↔Godot coordinate/winding conventions** (already handled correctly in `FlverModelBuilder`/`FlverLoader` — worth not "fixing" these again):
- **X is negated** on both position and normal: FLVER's coordinate convention is the mirror image of Godot's (confirmed via bind-pose FK on a character skeleton plus a map that visibly rendered as a mirror image of its sibling map — see `docs/context.md`). Without this, every map/model/texture placement is a correct-looking but fully mirrored left/right image of the real thing — self-consistent enough (correct winding, correct lighting) to go unnoticed for a long time.
- **Triangle winding is swapped** (two indices per face) — *because of* the X negation above, not despite it. Godot uses **clockwise** front-face winding, the opposite of the CCW convention Blender/Wavefront OBJ expect; mirroring one axis flips the apparent winding, so the swap is what keeps faces front-facing after the negation, not a separate correction for the CW/CCW convention itself.
- **Rigid mesh-to-node binding, per-vertex** (2026-07-24, `GetRigidNodeTransforms` in `FlverModelBuilder.cs`): a static (`UseBoneWeights == false`) mesh's vertices aren't always already in their final position, and a single mesh can mix vertices bound to *different* nodes — `Mesh.BoneIndices` is a small (28-entry) per-mesh palette of candidate `FLVER.Node`s, and each vertex's own `v.BoneIndices[0]` selects which palette entry applies to *that vertex* (confirmed real, not padding: a mesh with a 2-entry palette had real vertices referencing both). `BuildMesh` composes each palette entry's node transform (`Translation`/`Rotation`/`Scale`, walking `ParentIndex` for ancestors) once per mesh, then applies the vertex's own selected transform (in FLVER space, before the X-negation above) to its position/normal. Skip this and any vertex bound to a non-identity node sits wherever its raw local-space position puts it — usually at or near the origin, since node translations are frequently large. Confirmed via `m2304b0` (Doran's Mausoleum interior, `m02_00_00_00`, single-entry-palette meshes throughout — walls/floor on one node, the "standglass" windows on another, one coincidentally-identity node happening to leave one mesh looking right even before the fix) and `m2501b0` (the Nexus bridge+fountain, where two meshes each mix a `[general, fountain]` 2-entry palette — the fountain's own stone-ring decoration is the ~half of each mesh's vertices selecting the second palette entry; using only `BoneIndices[0]` for the whole mesh, an earlier version of this fix, left exactly that portion stuck at the origin while the rest of the same mesh was already correct) — see docs/context.md for the full investigation and corpus-wide impact (24% of files in `m02_00_00_00` affected in some way). `UseBoneWeights == true` meshes (real per-vertex skeletal skinning, not implemented) are left untransformed, same as before this fix — that's the already-documented, not-yet-started animation work, not this.
- **Root-caused and fixed (2026-07-25): the `m2304b0` "standglass" window one-sided bug was never about winding/normals at all.** `FLVER0.Mesh.CullBackfaces` ("whether triangles can be seen through from behind") was being parsed by `SoulsFormatsNEXT` correctly but never read anywhere in `FlverModelBuilder.cs` — every built material defaulted to Godot's single-sided `CullMode.Back` regardless of what the source data actually specified. Confirmed directly (a throwaway console app reading `m2304b0.flver`): every mesh in the file has `CullBackfaces=true` except the two window panes (`M[D].mtd`, no lightmap tag, 60/90 verts), which have `CullBackfaces=false` — exactly the "should render both sides" case Godot's default silently discarded. `GetOrBuildMaterial` now keys its cache by `(materialIndex, CullBackfaces)` rather than `materialIndex` alone — the two aren't equivalent: a corpus scan found 39 real files (mostly hair/parts) where meshes with different `CullBackfaces` legitimately share one `MaterialIndex`, which used to mean whichever mesh built the material first silently decided the cull mode for both. Applies `BaseMaterial3D.CullModeEnum.Disabled` when `CullBackfaces=false`, but only for the plain `StandardMaterial3D` path (973/1312 affected meshes game-wide) — `ShaderMaterial` (lightmap/blend/water) has no per-instance cull property, only a compile-time `render_mode` keyword, so the 338 double-sided meshes on the lightmap path still render single-sided; see "Known deferred work" below.
- No V-flip on UVs: `Image.CreateFromData` uses the same top-down row order as the raw decoded texture, so FLVER's raw V is already correct as-is.
- `FlverModelBuilder.BuildMesh()` returns `ImporterMesh` (a mesh-authoring API, fine on its own), but `FlverLoader.Instantiate()` **must** convert it to a real `ArrayMesh` via `GetMesh()` and use `MeshInstance3D`, not `ImporterMeshInstance3D` — see "Architecture" above for why (`ImporterMeshInstance3D` doesn't render at all outside Godot's own import pipeline, which this project no longer uses). Reverting this "for consistency" with the mesh-building code is the bug that shipped once already.
- **Alpha/blend handling is driven by `g_BlendMode`, a real 0-7 enum read from the material's `.mtd` (2026-08-27) — not the old MTD-filename-substring heuristic (`_Edge`/`_Alp`/`_Add`), which is gone.** `DesBlendMode` in `FlverModelBuilder.cs`: `0`=opaque, `1`=alpha-test (`AlphaScissor`, foliage-style cutout), `2`=alpha-blend (`Alpha`, soft transparency), `3`=water (see below), `4`=additive (`Alpha` + `BlendMode.Add`), `5`=subtractive (`Alpha` + `BlendMode.Sub`) — confirmed clean against all 584 blend-tagged MTDs, with `0` alone covering 286 MTDs and zero false positives. `7` is real but unconfirmed (2 `S_A03_Thunder00` materials only) and is treated as alpha-blend until it's identified. The old filename heuristic disagreed with the engine on 153/584 materials (26%) — it only ever under-detected, via a live case-sensitivity bug (the corpus ships both `_Edge` and `_edge`), tag-less variants (`A07_Shadowman_shadow[Dn]Sub`, no underscore), and every `A03_Sky*`/`Ps_Wander_Ghost`/`M_MagicBarrier` material rendering opaque — plus four light-shaft/cloud materials (`A03_cloud`, `A03_light_shaft`, `A04_light_shaft`, `M99_cloud11`) tagged `_Add` but actually alpha-blend, which were rendering additively over-bright. This is the same naming convention used across FromSoft's other Souls titles, still recognizable in the enum values' shape, just read from real per-material data now instead of guessed from a filename.
- `g_Specular` (a Blinn-Phong spec map) is mapped onto Godot's PBR `MetallicTexture` slot as a deliberate simplification (semantically wrong, but the only slot available without a custom shader) — `Metallic` must be explicitly set to `1.0` since it multiplies against the texture and defaults to `0`.
- **`Roughness` is derived from the material's own `.mtd` on `StandardMaterial3D` only (chr/parts) — deliberately not on the `ShaderMaterial` families (lightmap/blend/water).** `FlverModelBuilder.ResolveMtdShading()` looks up the material's `.mtd` by filename (same `_mtdIndex`/`GetMtdFloat`/`GetMtdColor3` primitives `BuildWaterMaterial` already used) and converts its real `g_SpecularPower` — a Phong shininess exponent that FLVER0's own material data never exposes at all — to roughness via the standard Phong→GGX approximation `roughness = sqrt(2/(n+2))`. Confirmed against reference DeS screenshots (`c9990`, the fluted armor set, 2026-07-24): every metal-family chr/parts material uses a real Phong-specular MTD (`C_Metal[DSB]_Skin.mtd`, `g_SpecularPower=7`) that was previously read for nothing but its `_Edge`/`_Alp`/`_Add` blend-mode substring. **Extending this to `BuildLightmapMaterial`/`BuildBlendMaterial` was tried and reverted the same day (2026-07-25) after a user-confirmed regression** — see the entry right after this one, and "Known deferred work" for the real blocker.
- **`g_DiffuseMapColor`/`g_DiffuseMapColorPower` — a real per-material diffuse tint — is read on all three families (`StandardMaterial3D`/lightmap/blend), unaffected by the roughness revert below.** `ResolveMtdShading()` applies it as `pow(color, power)`, not a plain multiply (`power` genuinely varies 0-7 game-wide, confirmed not a fixed authoring constant). Falls back to white/no-op if the `.mtd` can't be found/parsed or the value is unset (568/584 sampled MTDs leave it white — a genuine minority, light-shaft/thunder/cloud VFX materials, the Wanderer's ghost-effect material, carry a real tint). `AlbedoColor` on `StandardMaterial3D` needed no shader change at all — it already multiplies natively against `AlbedoTexture` in Godot's own built-in shader; the `ShaderMaterial` families use a `diffuse_tint` uniform instead. This part of the 2026-07-25 work is unrelated to the roughness regression (it never touches `METALLIC`/`ROUGHNESS`) and was kept.
- **`g_LightingType` (2026-08-18) — a real three-way MTD field (corpus-scanned across all 612 mounted `.mtd`s), one value of which is now read and gated on.** `1` = Phong (chr/parts metal/leather, the family the roughness fix above covers) and `3` = HemEnv (lightmap/blend) both already matched this project's existing family split without needing to read the field explicitly. `0` — previously an unconfirmed guess ("plain diffuse-only Lambert") — turned out to be a distinct "no dynamic lighting at all" family: every sky-dome MTD, the `Ps_Wander_Ghost` dissolve material, and every additive-VFX material (`vollight`/`light_shaft`/`cloud`/snow), all sharing one real shader (`DS_Phn_ColDif.spx`), confirmed via direct MTD reads. `ResolveMtdShading()` now reads it; `BuildStandardMaterial` sets `ShadingMode = Unshaded` when it's `0` — skips Godot's ambient entirely rather than trying to boost `Emission` (an earlier, wrong-mechanism attempt at the same problem, see the entry below) — fixing a real user-reported bug where the sky dome read as washed-out and scene-ambient-dependent. User-confirmed in-editor. Not gated on anywhere else yet (`BuildLightmapMaterial`/`BuildBlendMaterial` still don't check it) — see "Known deferred work" for what's still open there. **Confirmed independently 2026-08-27** — `SoulsFormatsNEXT/Formats/MTD.cs`'s own `LightingType` enum has carried the answer the whole time (`None=0`, `HemDirDifSpcx3=1`, `HemEnvDifSpc=3`): `1` is hemisphere ambient **plus three directional lights**, not plain Phong — the same `LIGHT_BANK` directional-light terms the lightmap family already reads two-sevenths of (see "Known deferred work"). `BuildStandardMaterial` still routes `g_LightingType=1` to `StandardMaterial3D`+Godot PBR, which is why a `WorldEnvironment` cannot be safely added until that family gets a shader that computes its own result from those uniforms instead.

**Roughness on the lightmap/blend `ShaderMaterial` family was tried and fully reverted the same day (2026-07-25), not just patched — needs real environment/lighting work first, not another same-session guess.** Extending the `g_SpecularPower`→roughness fix above from `BuildStandardMaterial` to `BuildLightmapMaterial`/`BuildBlendMaterial` immediately regressed most map surfaces into a washed-out, glassy sheen (user-confirmed via screenshot). Root cause: `lightmap_common.gdshaderinc`/`terrain_blend.gdshader` both had a pre-existing `metallic = spec`/`METALLIC = spec` line (predating this work entirely, the same "spec map jammed into the metallic slot" simplification `BuildStandardMaterial` uses), inherited by the lightmap/blend shaders without re-checking whether it still made sense there. It was invisible before: `ROUGHNESS` defaulted to Godot's own `1.0` (fully rough), which suppresses almost all visible reflection-probe response regardless of `METALLIC`. The moment `ROUGHNESS` became a real, lower value (Boletaria's walls: `g_SpecularPower=4` → `roughness≈0.577`, confirmed via corpus scan, not an unusually shiny/mirror-like value on its own), `METALLIC` suddenly had a visible effect — and this project has **zero `WorldEnvironment`/reflection probes anywhere**, so there's nothing real for a metallic surface to reflect; Godot substitutes its own fallback ambient, reading as a flat, misplaced sheen. A first attempt (`metallic = 0.0`, keeping the new roughness) did **not** fix it, user-confirmed — meaning the real mechanism is either something else entirely or something beyond just `METALLIC`, not yet root-caused. Rather than keep guessing same-session, the whole roughness/`METALLIC` change on this material family was reverted outright (not commented out — see `docs/context.md` for why removal was chosen over leaving a disabled attempt in place) back to its pre-2026-07-25 state: `ROUGHNESS` unset (Godot default `1.0`), `metallic = spec`/`METALLIC = spec` restored. See "Known deferred work" for what this actually needs before it can be revisited.
- Terrain ground-blend materials (grass/dirt/stone transitions): a material whose MTD filename contains FromSoft's own `[M]`/`[ML]` blend-shader bracket tag (**not** whether `g_Specular_2`/`g_Bumpmap_2` are present — each is independently optional per layer; gating on their presence was tried first and was wrong, see `docs/context.md`) gets a `ShaderMaterial` using `addons/archstone/shaders/terrain_blend.gdshader` instead of `StandardMaterial3D`. The two layers blend by `VertexColor.A` — **not** `.R`/`.G`/`.B` (R=G=B is a separate, still-unidentified per-vertex signal; confirmed *not* a shading/AO gradient either, despite briefly looking like one). Both wrong turns and their evidence are in `docs/context.md` — worth not re-trying either. **New lead, not yet investigated (2026-07-22):** outside confirmation says vertex color is load-bearing for both lightmap and blend-material shading in DeS specifically (more so than DS1) — possibly tied to the same `LightID`/`FogID` drawparam data described in "Known deferred work" below, rather than a standalone AO-shaped value. See docs/context.md's "Lightmap/drawparam system, part 5." The second layer's own UV set is FLVER's UV channel 1 (Godot's native UV2 slot, via the `Mesh.ArrayType.TexUV2` array — see the mesh-building note below); UV channel 2, when present, carries the lightmap (see "Lightmaps" below). Materials with `g_Diffuse_2` but no bracket tag are an unrelated "ghost" character dissolve effect, left on the single-layer path. `tex_scroll_0`/`tex_scroll_1` (one per diffuse layer, added 2026-08-27) cover the three `c5000` slime materials that scroll — same fixed-lightmap-UV reasoning as the single-layer family. Vertex colour was deliberately **not** wired into this family's diffuse the way the single-layer family got it the same day: the shader taxonomy recovered from `shader/ds_flver.shaderbnd` (see "Known deferred work") explains why — blend materials are the engine's own `Mul` feature slot, so their vertex-colour channel already carries layer-blend data (`.a` is the blend weight; `.rgb`'s two discrete values are still unidentified, but confirmed not to be AO/shading), not a free tint input the way most other shaders use it. Shader-only changes to `terrain_blend.gdshader` need no reimport — Godot loads `.gdshader` source live by path.

- Water surfaces (moats, swamps, lakes, fountains): gated on the material having a `g_Envmap` texture — confirmed unique to this family across all 8889 materials in the game, so unlike the other paths this needs no filename/MTD-tag heuristic at all. Gets a `ShaderMaterial` using `addons/archstone/shaders/water.gdshader`. These materials carry only `g_Bumpmap`+`g_Envmap`, no diffuse — `g_Envmap` is a small flat "impression" texture (confirmed by decoding and viewing one directly), used as a matcap-style reflection lookup, not a real cubemap. Per-material wave/reflection tuning (tile scale, scroll speed, water tint, Fresnel curve, opacity) has no equivalent in FLVER0's own material data, so this is the one path that reads the real `.mtd` file directly via `SoulsFormats.MTD.Read()` (indexed once at builder construction — see `_mtdIndex` in `FlverModelBuilder.cs`) instead of just the MTD path string; falls back to the shader's own built-in defaults if that file can't be resolved. `g_WaterColor` is a Float4 — its 4th component (`water_alpha`) blends the see-through screen-refraction toward a flat opaque tint, which is what actually separates murky/opaque water (e.g. swamps) from clear reflective water (e.g. moats); reading only its RGB and ignoring alpha was an earlier bug, see `docs/context.md`. `water_alpha` is further scaled by a depth-based shore/deep fade (`g_WaterFadeBegin`, via `hint_depth_texture` + `INV_PROJECTION_MATRIX` reconstruction) so shallow edges stay see-through even on otherwise-murky water. `ROUGHNESS`/`SPECULAR` are derived from `g_ReflectBand` (confirmed real, varies `0`/`0.1` game-wide — `g_SpecularPower` was checked and is a constant `100` everywhere, not usable), adding a small *extra* real specular sun-glint on top. **The whole reflection/refraction/Fresnel result is written to `EMISSION`, not `ALBEDO`** (`ALBEDO` is left at `vec3(0)`) — this is a self-contained, hand-computed color the same way the original PS3 shader worked internally, not a physically-based surface meant to plug into Godot's lighting model; writing it to `ALBEDO` made it nearly invisible (Godot's PBR shifts energy from diffuse to specular as roughness drops, and there's no real reflection probe in-scene for a low-roughness "mirror" to reflect). The refraction sample's screen-space offset is `N.xy * refract_band`, scaled down and hard-clamped to a small constant (`refraction_scale = 0.03`, ±0.03 max) — `g_RefractBand`'s real range (`0.05`-`0.8`) is far too large to use directly as a raw `SCREEN_UV` delta (0-1 range); **this specific scale constant is an uncalibrated guess**, unlike everything else here, since there's no visibility into what unit the original shader actually used. The bump-sample coordinate (`g_TileScale_N`/`g_TexScroll_N`, tiling+scroll together) also has a flat `wave_detail_scale = 12.0` multiplier — applied to raw UV, the wave pattern tiled at ~40-95 *world units* per repeat on large meshes, user-confirmed as the actual cause of a "stretched, reflective-looking" wave pattern; **this constant is also an uncalibrated guess**. `a06_lava[we].mtd` also matches this family (`g_Envmap`-gated) and currently renders through this same shader, which is almost certainly wrong for lava — not yet addressed. **`g_BumpMapSmoose` (2026-07-25)** — a real per-material value (-0.5 to 1 game-wide) that was the one water `.mtd` param this shader still didn't read, despite `BuildWaterMaterial` already reading nearly everything else; applied as a wave-normal intensity scale (`tangentNormal.xy * bump_smoose`, renormalized) — like `wave_detail_scale`/`refraction_scale` above, **this specific application is an uncalibrated guess**, since there's no visibility into what the original shader actually did with this value. **Visual accuracy tuning is deliberately paused, not abandoned or considered broken.** Coloring/depth-fade/tiling are working and were confirmed reasonably close against real screenshots (Defilement's brightness matched a sampled real reference to within a few percent); the remaining gap (Boletaria's water reads noticeably darker than reference footage even accounting for every real per-material MTD difference) traces to there being **no `WorldEnvironment`/tonemap/exposure configuration anywhere in this project** — checked directly, none exists — so comparisons so far have been against the 3D editor's own opaque default preview lighting, not a controlled baseline. Further water-shader tuning is on hold until real lighting/environment/ambience work happens (see `docs/PLAN.md`'s Phase 1 item 4, which now scopes a real `WorldEnvironment` setup as part of the future map assembler rather than a standalone task) — see `docs/context.md` for the full investigation.

**Lightmaps** (`g_Lightmap`, a baked-lighting texture): present on 7394/11646 mounted materials (63%) and confirmed via corpus survey to never co-occur with water (`g_Envmap`). `StandardMaterial3D` has no slot for an independent-UV multiply texture, so every lightmapped material — not just terrain-blend ones — needs a `ShaderMaterial`. **No longer a straight `diffuse * lightmap` multiply** (see "Known deferred work" for why that was architecturally wrong) — both `lightmap_common.gdshaderinc`'s `lightmap_shade()` and `terrain_blend.gdshader`'s `fragment()` now do `albedo = diffuse * (hemi + envDif)`, where `hemi` is a two-color hemisphere-ambient term (`ambient_up`/`ambient_down` uniforms) and `envDif = texture(env_dif_cube, N) * env_color * env_intensity * lightmap`. **Both terms are driven by a per-pixel normal reconstructed from the bumpmap** (2-channel tangent-space sample, `Z = sqrt(1 - dot(xy,xy))`, TBN basis from `world_tangent`/`world_binormal`/`world_normal` varyings), and `envSpc` is summed straight into the result as `texture(env_spc_cube, reflect(-V, N)) * env_spc_color * env_spc_intensity * lightmap * specular`. This structure is taken from a real captured DeS HemEnv fragment program rather than inferred: EnvDif is an irradiance lookup by the **surface normal**, EnvSpc a lookup by the **reflection vector**, and the lightmap acts as the gate the real shader applies as `min(shadow_attenuation, lightmap)` — this project has no shadow map, so the lightmap alone gates it, which is what keeps baked occlusion driving where env light lands. `use_normal_map` (set from C# when a `g_Bumpmap` actually resolved — true on 225 of 335 real Nexus surfaces) falls the per-pixel normal back to the interpolated vertex normal for the many `[D][L]`-style materials that ship no bumpmap. Cubemaps come in two real layouts and **only the block-compressed one may go through Pfim**: handed an uncompressed ARGB8888 face, Pfim reports `Rgb24` and reads 3 bytes per pixel out of 4, rotating the channels on a four-pixel cycle into a literal RGB rainbow (see `docs/context.md`'s "part 24" — this shipped briefly and wrecked every uncompressed-cubemap map: m02, m04, m06, m08, m99). Uncompressed faces are read straight out of the payload as A,R,G,B instead. An unresolved cubemap name binds a 1×1 white cubemap, collapsing both terms to the flat lightmap-scaled behaviour they replaced — matching the real FRPG shader shape (see below), not the old undifferentiated multiply. Real `LIGHT_BANK` `env_intensity` values run 1.5x-5x, which overexposes bright-lightmap surfaces on a handful of map pieces (see "Known deferred work") — a `[0,1]` clamp was tried and reverted the same day (2026-08-17, user-confirmed regression on most other, unaffected map pieces); left unclamped deliberately for now, since the overexposure is more useful as a visible marker of which pieces still need the real fix than a clamp that dulls everything else. `LIGHT_BANK` carries a second, separate environment term (`envSpc`, distinct from the `envDif` fields `env`/`env_intensity` above are sourced from) that the real shader keeps as a specular-reflection response rather than folding into the diffuse term — implemented the same way water.gdshader's own hand-computed reflection is (no real reflection probe exists in this project), weighted by the material's own specular texture. It used to go to `EMISSION`; since these shaders became `unshaded` (2026-08-27, see "The DeS rendering pipeline, reconstructed") there is only one output, so it is added to the result directly the way the real shader adds it. This math (uniforms, the world-normal helper, `hemisphere_ambient()`) lives in a third shared file, `addons/archstone/shaders/hemisphere_ambient.gdshaderinc`, `#include`-d by both `lightmap_common.gdshaderinc` and `terrain_blend.gdshader` rather than duplicated — the single-layer family already shared `lightmap_common.gdshaderinc` for diffuse/normal/specular/lightmap sampling, but `terrain_blend.gdshader` is otherwise a fully separate, self-contained shader, so only the hemisphere/env piece is factored out. Uniform defaults are DeS's own `param/drawparam/default_lightbank.param` row 0 (read via `SoulsFormats.PARAM`/`PARAMDEF`, not invented) — used only as the fallback `DrawParamReader.cs` (2026-08-17) falls back to when a placement's real `LightID` is the `255`/unset sentinel or its map has no own bank file; every other placement gets its own resolved row's values pushed via `FlverLoader.InstantiateMap()`'s `ApplyDrawParams` (which also resolves the part's `FogID`/`ToneMapID`/`ToneCorrectID` for the output stage), as a per-surface material override (`Duplicate()`'d off the shared cached mesh's base material, so one placement's values never leak onto another placement of the same reused model — see "Known deferred work" for the `colA`-scale fix and the still-open env-term overexposure caveat). Non-blend materials route on `g_BlendMode` (see "Alpha/blend handling" above) to one of four thin shader variants: `lightmap.gdshader` (opaque; also folds in the alpha-test case via a `hint_range(0,1)` `alpha_scissor_threshold` uniform defaulting to `0.0`, since referencing `ALPHA_SCISSOR_THRESHOLD` at all keeps Godot's non-sorted opaque render path regardless of the threshold value), `lightmap_alpha.gdshader` (alpha-blend), `lightmap_add.gdshader` (additive, `render_mode blend_add`), or `lightmap_sub.gdshader` (subtractive, `render_mode blend_sub`, added 2026-08-27 for the 139 real `a04_blood`-family meshes this family had no route for before) — four separate files rather than one runtime-switched shader because `blend_mix`/`blend_add`/`blend_sub` are compile-time `render_mode` keywords in Godot, not a per-material property the way `StandardMaterial3D.BlendMode` was; all four `#include "lightmap_common.gdshaderinc"` for the shared diffuse/normal/specular/lightmap sampling logic, exposed as a `lightmap_shade(uv, uv2, vertex_color, view_dir)` function returning the finished pre-output-stage colour — **not** a function that assigns `ALBEDO` directly, which fails to compile (confirmed via a real, non-dummy rendering driver — see "Build & verify" below): Godot's shader built-ins are only assignable directly inside `fragment()` itself, never from a helper function it calls, `#include`-d or not. The same restriction applies to `varying`s (a helper can't assign one either, only `vertex()`/`fragment()` can) and, less obviously, to *reading* some built-ins at all: `MODEL_MATRIX` isn't visible inside a non-entry function even just to read (unlike `NORMAL`, which is) — `hemisphere_ambient.gdshaderinc`'s `hemisphere_world_normal()` takes both as explicit parameters rather than reading the built-ins directly, and each shader's own `vertex()` calls it and assigns the varying itself. `lightmap_shade` also applies `g_TexScroll_0` (a per-second UV scroll rate, real on the two `m99` lava surfaces — scrolls the diffuse/normal/specular sample only, not the lightmap's own UV, which stays fixed to its baked geometry) and multiplies the mesh's own vertex colour into the diffuse sample, not the final albedo, so it doesn't scale the `envSpc` emission (both added 2026-08-27; real, nonzero vertex colour is present on 35% of map meshes per a full-corpus census). Blend materials keep using `terrain_blend.gdshader` for the diffuse1/diffuse2 layer blend itself (865/912 real blend materials have a lightmap; the other 47 leave the uniform unset, which safely no-ops via `hint_default_white`). The lightmap's own UV is always the *last* UV channel (confirmed via corpus survey: zero exceptions across ~11.6k materials) — Godot's native UV2 slot on non-blend materials (which only need one other UV channel, for the diffuse), or a third per-vertex channel on blend materials (whose native UV/UV2 are already spoken for by the two diffuse layers), packed into `Mesh.ArrayType.Custom0` as raw floats. `Custom0` is only readable inside `vertex()`, unlike `UV`/`UV2`/`COLOR` which are also available in `fragment()` directly (also confirmed the same way, not assumed) — `terrain_blend.gdshader` forwards it to `fragment()` via an explicit `varying vec2 lightmap_uv` set in its own `vertex()`. Custom0's component format (`Mesh.ArrayCustomFormat.RgFloat`, 2 floats/vertex) isn't inferable from the raw array the way `Vertex`/`Normal`/`UV` are, so `BuildMesh` passes it explicitly via `ImporterMesh.AddSurface`'s `flags` parameter — confirmed correct by reading back a loaded mesh's `Custom0` surface array and checking it against the source FLVER's raw UV data.

**`SoulsFormatsNEXT/`** is a git **submodule** pointing at the user's own fork (`github.com/Solaire9886/SoulsFormatsNEXT`) of the community SoulsFormats library, not the upstream `soulsmods` repo directly — check `SoulsFormatsNEXT/FORMATS.md` for format documentation. Two local patches live as real commits on that fork (`origin` remote; `upstream` remote still points at `soulsmods/SoulsFormatsNEXT` for pulling future updates): one known upstream bug patched — `Formats/FLVER/FLVER0/Mesh.cs` had a `version >= 0x12`-based heuristic for picking a UV fixed-point scale factor (1024 vs 2048) that is wrong for Demon's Souls — verified empirically (UV wireframes overlaid on decoded textures) that Demon's Souls always needs `1024` regardless of header version; if SoulsFormatsNEXT is ever synced from upstream, re-check this hasn't regressed. The other patch retargets its own `.csproj` to `net8.0` to stay a valid `ProjectReference` target for `Soulbrandt.csproj` (also net8.0). Cloning this project fresh needs `git clone --recurse-submodules` (or `git submodule update --init` after a plain clone) to pull the submodule in.

**BND/DCX container unpacking needs no external tool.** `addons/archstone/scripts/AssetExtractor.cs` reads FromSoftware's containers directly in-process via `SoulsFormatsNEXT`'s `DCX`/`BND3`/`BND4` readers — see "Asset mounting" below. No third-party unpacker (WitchyBND, Yabber, etc.) is needed anywhere in this workflow.

## Asset mounting

`mounted` (repo root, gitignored) is a real directory — **not a symlink anymore**. The toolbar's "Archstone" menu (`addons/archstone/scripts/archstone.gd`, `import.tscn`) has seven actions, in two groups. **Extraction** (unchanged in spirit, but no longer touches Godot's import system at all — see below): "Mount..." only validates a chosen root (checks it contains at least one known category folder) and remembers it — it does **not** extract anything by itself; "Import" then offers a **Full Import** or **Choose Categories...** (checkboxes) confirmation, either of which kicks off the real extraction; "Clear Mounted Assets..." recursively deletes `res://mounted` after a confirmation dialog, for freeing disk space or forcing a clean re-extract. **Loading** (new, replaces what used to happen automatically via Godot's own reimport queue): "Load Model(s)..." and "Load Folder..." each open an `EditorFileDialog` (`ACCESS_FILESYSTEM`, rooted at `mounted/`) to pick specific `.flver` files or a whole folder (loaded recursively — the "grab every piece for this area in one go" case), calling `FlverLoader.Instantiate()` for each and dropping the result under the selected Scene-dock node or the edited scene's root; "Load Map..." (rooted at `mounted/map/mapstudio`, filtered to `*.msb`) calls `FlverLoader.InstantiateMap()` per selected `.msb` — see "MSB map placement" above for what this does and doesn't cover yet; "Reload Loaded Models" calls `FlverLoader.EvictAll()` so the next load rebuilds from source (use after an importer-code change).

The user points "Mount..." at their own raw, unmodified copy of the game (`.../Demon's Souls (USA)/PS3_GAME/USRDIR`); once "Import" runs, `addons/archstone/scripts/AssetExtractor.cs` walks it and unpacks `.bnd`/`.dcx` containers directly via `SoulsFormatsNEXT`'s `DCX`/`BND3`/`BND4` readers (confirmed against real containers: this game's compression is `DCX_EDGE`, and `SoulsFormatsNEXT` has a literal `Type.DemonsSouls = Type.DCX_EDGE` alias) — no external tool involved at all. Output goes straight into `res://mounted` in the same loose-file layout `FlverModelBuilder.cs` already expects. **Extraction deliberately does not call `EditorInterface.get_resource_filesystem().scan()` afterward anymore** — it used to, and that single call was the actual mechanism that funneled every newly-extracted `.flver` straight into Godot's crash-prone reimport queue even after a concurrency self-throttle had been added to the (now-deleted) importer; see docs/context.md's reimport-concurrency entry. Extraction now just writes loose files, full stop — nothing observes `mounted/` changing until you explicitly click "Load Model(s)..."/"Load Folder...". Re-running extraction is idempotent (mtime-based skip, near-instant once already extracted) and scoped to a small category allowlist matching what `FlverModelBuilder` actually reads (`chr`, `map`, `obj`, `parts`, `mtd` — see `AssetExtractor.KnownCategories`; the raw dump's `movie`/`sound`/`msg`/`param`/etc are never touched). The chosen root path is remembered in `user://archstone_mount.cfg` (a `ConfigFile`, structurally outside the repo — never `res://override.cfg` or `EditorSettings`, see `docs/context.md` for why).

Extraction is also runnable headlessly, independent of any editor GUI session: `godot-mono --headless --path . -s addons/archstone/scripts/extract_cli.gd -- --raw-root=/path/to/raw [--categories=chr,map]`. `AssetExtractor.cs` itself has zero `EditorPlugin`/`EditorInterface` dependency — both entry points call the exact same code. This is also the only way to exercise this feature in a GUI-less environment.

This is still the editor-side increment (`docs/PLAN.md`'s Phase 1 item 1), but meaningfully closer to the eventual shipped-runtime goal than it looks: `AssetExtractor.cs`, `FlverModelBuilder.cs`, and `FlverLoader.cs` all have zero `EditorPlugin`/`EditorInterface` dependency — only `archstone.gd`'s toolbar/dialog triggering is editor-only. A full runtime loader for exported/shipped game builds still needs its own driving code (no editor, no manual button clicks, no pre-extraction step at all) and isn't started, but the actual parsing/building logic underneath it no longer needs to change to get there.

## The shader library (`shader/*.shaderbnd`)

`PS3_GAME/USRDIR/shader/` holds five `.shaderbnd` containers — plain `BND3`, read with `BND3.Read` and nothing special. **`ds_flver.shaderbnd` is the material shader library: 4.6MB, 1349 entries** (134 `.vpo` vertex programs, 1215 `.fpo` fragment programs), each carrying its original build path. `ds_filter.shaderbnd` (31 entries) holds the post chain — `DS_Fil_HDR`, `DS_Fil_HDR_ColAdj`, `DS_Fil_CalcAdaptedLum`, `DS_Fil_Bloom`, `DS_Fil_Dof`, `DS_Fil_CameraBlur`, all named. **Mounted as of 2026-08-28**: `shader` is in `AssetExtractor.KnownCategories`, landing at `mounted/shader/<container>/<entry>` (1421 files). That needed one extractor change beyond the allowlist — these entry names carry no `data/DVDROOT` prefix, and `ResolveEntryOutputPath` returns `null` for anything without one, which `WriteEntry` **silently dropped**. `FallbackEntryOutputPath` now mirrors the container's own place in the raw tree and gives it a folder named after itself, so `ds_flver`'s 1349 entries can't collide with `ds_filter`'s identically-shaped names. It strips a trailing `.dcx` first: every container ships as both a plain and a `.dcx` copy that decompress to the same binder, and without that they land in two folders.

**Fragment program names are a fixed-width field layout, `_`-padded to fixed columns:**

`DS_<family>_<textures>_<shadow>_<lightingModel>.fpo`

| Field | Values |
|---|---|
| family | `Phn` (626), `Gst` (576), `Dbg` (9), `Water` (3), `Ghost` (1) |
| textures | `Dif` → `DifSpc` → `DifSpcBmp` → `+Mul` → `+Lit`, and `+LitSdw`/`+LitCsd` |
| shadow | `Sdw` (shadow map) or `Csd` (cascaded) — **separate compiled shaders**, 400 in total |
| lighting model | `HemDir3`, `HemEnv`, `HemEnvLerp`, each × `{—, PntS, PntSS, PntSSSS}`; plus a bare `Non`/`Pnt`/`PntS`/`PntSS`/`PntSSS`/`PntSSSS` set |

Vertex program names use a different middle field — `DS_<family>_<vertexLayout>_<textures>_<variant>.vpo`, where the layout is `PIN`/`PIWN`/`PINT`/`PINTT` (position/index/normal, `W` = weights, `T`/`TT` = tangent sets) and the variant is `Non`/`Sdw`/`Dep`/`DepAlp`.

**Three things this settles that were previously inferred:**

- **`HemEnvLerp` is a real, first-class lighting model** with a full variant set — the loose end from the pipeline trace, where `FragmentProgram151` lerps its result toward a constant colour by the EnvDif cubemap's alpha.
- **Point lights reach map geometry.** `HemEnv` is the map/lightmap family and it has `PntS`/`PntSS`/`PntSSSS` variants, so map surfaces receive 1/2/4 point lights. `POINT_LIGHT_BANK` is recorded below as a fixture-preset table with no known consumer; it has one.
- **Shadowing is a compile-time variant, not a runtime branch** — which mirrors how this project already has to split `blend_mix`/`blend_add` into separate `.gdshader` files.

`ShaderLibrary.cs` reads this as data — names only, never a byte of shader code. `ResolveMaterialShader(mtdShaderPath)` takes an MTD's own `ShaderPath` and returns the family, texture-feature set, and the lists of lighting models and shadow variants the engine would choose among for that material; `GetLightingModels()`/`GetFamilies()`/`GetLibraryStats()` describe the library itself. Parsing is by **feature-substring detection, not `_`-token splitting** — the names are padded to fixed columns, so a feature run appears fused (`DifSpcBmpMulLitCsd`) or split (`DifSpcBmpMul_Csd`) depending on where the columns fall, and only substring detection reads both shapes identically. Verified against the whole corpus: **612 of 612 mounted MTDs resolve, zero unresolved.**

**Routing runs off this as of 2026-08-28.** `FlverModelBuilder.ClassifyMaterial` takes its water/blend/lightmap decision from the resolved family and feature set — `Mul` is what it used to detect as the `"[M]"`/`"[ML]"` bracket tag, `Lit` as `g_Lightmap` presence — falling back to the old slot/tag heuristics only when the `.mtd` can't be read at all. Checked against the whole corpus before switching: **610 of 612 MTDs classify identically**, and both disagreements are the magic barrier, a genuine `ColDifMul` two-layer material whose name carries no bracket tag. No FLVER map material references it, so that fixes a latent case rather than a visible one.

**A load-bearing negative result: the material does *not* determine the lighting model.** `DS_Phn_ColDifSpcBmp.spx` (104 MTDs, the most common map material) and `DS_Phn_ColDifSpcBmpMulLit.spx` both resolve to the *same* 13 lighting models — `HemDir3`, `HemEnv`, `HemEnvLerp`, their point-light variants, and `Non`. So which model a surface gets is a pure runtime choice and cannot be inferred from the shader path; `MTD.LightingType` remains the only authored signal for it. Anything that tries to route lighting off the `.spx` name is building on sand.

**Material → shader is an authored mapping, not a heuristic.** Every `.mtd` carries a `ShaderPath` naming its `.spx` (32 distinct values across the 612 mounted MTDs), and those map 1:1 onto the fpo names — `DS_Phn_ColDifSpcBmpMulLit.spx` → `DS_Phn_DifSpcBmpMulLit_<shadow>_<model>.fpo`. The material fixes family and texture set; the runtime picks the shadow variant and lighting model. (`Col` is the vertex-colour multiply this project already implements.)

**Every MTD also carries a dev-written Japanese `Description`.** These confirm, in the authors' own words, routing this project previously derived statistically: **`Mul` = multi-texture (the terrain blend), `Lit` = light texture (the lightmap), `α抜き` = alpha cutout, `半透明` = semi-transparent.** Worth reading before inferring anything else about a material family.

**What the binaries do *not* contain: symbols.** A `.vpo`/`.fpo` is raw RSX microcode behind a `FF 0F 00 11` header with the parameter name table stripped, so uniform register names are not recoverable from these files, and the CPU-supplied per-draw constants (`c104`–`c110` in the scattering chain) are not in them either. What *is* present is the compiler's **embedded literal pool**, which is often enough to identify what a stripped shader is doing: in `DS_Phn_PINTT_DDL_Sdw.vpo` it decodes to `(1/1024, 1/ln2, 1/ln2, 1.0)` — the `c466` block — and to `127.5/256` and `512/255`, the standard unsigned-byte vertex-attribute decode constants.

**A standalone tool names the anonymous RPCS3 captures against this library — `tools/RsxShaderMatch` (2026-08-31).** RPCS3's shader-log dumps (`shaderlog/FragmentProgramN`) are plain GLSL with the names stripped. The tool decodes each `.fpo`'s raw RSX fragment microcode into a structural fingerprint (ordered texture-unit run, inline-constant count, KIL/FENC, sampler types) and matches the captures against it, restoring the dev's own filename: on the captures collected so far, **363 high-confidence names across 423 captures, 195 distinct shaders identified**. It also carries a readable RSX disassembler (`disasm`) — the D5/D6/D7 shader fixes in the pipeline section below were read straight from the disassembled reference programs, not inferred. Plain .NET console app, no Godot/SoulsFormats dependency, excluded from `Soulbrandt.csproj`; `tools/RsxShaderMatch/README.md` documents the `.fpo` format and the four build stages. Vertex-program matching is a separate unstarted pass (different RSX ISA). Two findings that correct earlier inferences: the `HemEnv` reference bytecode carries **no** bumpmap term in the variant captured most often (per-pixel relief there is entirely the env-cubemap reflection, matching the D-series conclusion below); and **`HemEnvLerp` is an environment-lighting *transition*** — env-diffuse cross-faded between *two* cubemaps by a per-draw scalar — not the "lerp toward a constant colour" the part-18 trace attributed to it (that behaviour is in plain `HemEnv`).

## The DeS rendering pipeline, reconstructed (and what this project implements of it)

Traced 2026-08-27 from real RPCS3 fragment-program dumps of the Nexus and Boletaria, not inferred — see `docs/context.md`'s "part 18" for the trace. The reference material is `FragmentProgram151` (a lightmapped HemEnv map piece, the family most Nexus geometry uses) cross-checked against `FragmentProgram124` (a bumpmapped HemEnv material with EnvSpc) and `FragmentProgram11` (a HemDir3 terrain blend).

**Per-material, in the fragment shader:**

1. **Diffuse** sampled at UV0; a second layer sampled at the same register's `zw` pair and blended into it by **vertex-colour alpha** (the terrain-blend family) — `fma(diff_color.wwww, layerB - layerA, layerA)`.
2. **Normal**: when the material has a bumpmap, a per-pixel normal is reconstructed (2-channel tangent-space sample, `Z = sqrt(1 - dot(xy,xy))`, TBN basis built by cross product); when it doesn't, the interpolated vertex normal is used directly. Both paths are real and appear in different shaders.
3. **EnvDif** cubemap sampled by the **surface normal**; **EnvSpc** cubemap sampled by the **reflection vector** (`2(N·V)N - V`), weighted by the **RGB** specular sample and by vertex colour — both confirmed in the disassembled `DS_Phn_DifSpcBmp…HemEnv` (the term folds `COL0` in, and uses the sampled `.xyz`, not just red). EnvSpc is per-material — plenty of shaders bind only EnvDif.
4. **Hemisphere** = `mix(down, up, (N.y + 1) / 2)`, using whichever normal step 2 produced. **Not gated by anything.**
5. **Shadow**: a cascaded shadow-map projection (the long matrix-select chain at the top of the shader) plus a distance fade.
6. **The gate** — literally `min(shadow_attenuation, lightmap)`, the lightmap sampled at its own separate UV set.
7. **Composition** — `result = diffuse * vertex_colour * (hemisphere + EnvDif * gate)`, with the EnvSpc term added on after the diffuse multiply.
8. **Atmosphere** — `result * tc8 + tc9`, both interpolated per-vertex and applied per-pixel, so this is a *per-material* term in this engine, not a scene-wide pass. **`tc8` is a vec3, not a scalar**, and the vertex program builds it from a per-channel `exp2()`: this is extinction plus in-scatter, i.e. **Hoffman & Preetham's real-time outdoor light-scattering model**, whose parameters `LIGHT_SCATTERING_BANK` carries under the paper's own names (`lsBetaRay` Rayleigh, `lsBetaMie` Mie, `lsHGg` the Henyey-Greenstein asymmetry, plus `distanceMul`/`inscatteringMul`). `FOG_BANK`'s plain linear fog is the *other* half and applies underneath it; `blendCoef` ("scattering's degree of involvement, 100 = max") is a strength dial on the scattering, not a selector between the two. Addressed by `MSBD.Part.ScatterID`, a sibling of `LightID`/`FogID`.
9. **Exposure normalize** — `output = clamp(result * k / exposure_constant, 0.0, 1.0)`. **This is universal: 190 of 219 real material shaders end with exactly this.** DeS packs HDR-range lighting into a `[0,1]` target *in the material shader itself*.

**Per-frame, in `ds_filter.shaderbnd`:** luminance downsample → `CalcAdaptedLum` (temporal adaptation, clamped to `TONE_MAP_BANK`'s `[minAdaptedLum, maxAdapredLum]`) → bright-pass/blur/bloom (`bloomBegin` as a threshold on the now-`[0,1]` range) → `DS_Fil_HDR`'s per-channel 1D LUT built from `grayKeyValue` + adapted luminance → `DS_Fil_HDR_ColAdj` instead when `TONE_CORRECT_BANK` is non-identity → DOF/motion blur. **Of this chain, only the bright-pass→bloom stage is approximated so far** — see "Bloom" below; eye adaptation has no path under the Compatibility renderer, and the transfer function / tone correction live in-shader per the note above.

**What this project implements, as of 2026-08-27:**

| Pipeline stage | This project |
|---|---|
| diffuse × vertex colour | ✔ matches |
| two-layer blend by `COLOR.a` | ✔ matches (`terrain_blend.gdshader`) |
| per-pixel normal when bumpmapped, vertex normal otherwise | ✔ matches (`use_normal_map`) |
| hemisphere `mix(down, up, (N.y+1)/2)`, ungated | ✔ matches |
| EnvDif by normal, EnvSpc by reflection × specular | ✔ matches |
| gate = `min(shadow, lightmap)` | ~ lightmap only — no shadow system exists |
| per-material fog | ~ `des_fog()` implemented from `FOG_BANK` but **not called** — blanket lerp was wrong, see below |
| per-channel scattering (Rayleigh/Mie/HG) | ~ structure matches (`LIGHT_SCATTERING_BANK` via `ScatterID`), active; scalar in-scatter divide + one fitted unit-scale + fitted wavelength weights, see below |
| point lights on map geometry (`HemEnvPntS/SS/SSSS`) | ✘ not implemented — `POINT_LIGHT_BANK` unread |
| `HemDir3` (hemisphere + 3 directional + specular directional) | ✔ matches (`g_LightingType=1`, from `LIGHT_BANK`) |
| `HemEnvLerp` (lerp toward a constant by EnvDif alpha) | ✘ not implemented |
| **exposure normalize + eye adaptation → tonemap LUT** | ✔ folded into one in-shader Reinhard curve — see below |
| per-channel tone correction | ✔ matches (`TONE_CORRECT_BANK`; hue included) |
| bloom, DOF, motion blur | ✘ not implemented |

**The output stage** (`addons/archstone/shaders/output_stage.gdshaderinc`, added 2026-08-27) implements steps 8-10 as `des_output(color, view_depth, view_distance, view_dir)`: `LIGHT_SCATTERING_BANK`'s extinction-plus-in-scatter, then the transfer function, then `TONE_CORRECT_BANK`'s per-channel brightness/contrast plus saturation and a hue rotation. `FlverLoader.ApplyDrawParams` pushes all four banks per placement from the part's own `FogID`/`ScatterID`/`ToneMapID`/`ToneCorrectID`, alongside the `LIGHT_BANK` values it already resolved. `des_fog()` (the `FOG_BANK` linear lerp) is still present but **not called** — the real fragment corpus applies it in only 7 of 183 scattering-carrying programs, all unlit (`g_LightingType=0`), so a blanket per-pixel lerp was wrong; see `docs/context.md`'s part 28.

**The atmosphere is `LIGHT_SCATTERING_BANK`'s Hoffman-Preetham scattering**, structurally confirmed from the vertex bytecode and now user-accepted as close ("about the closest we can get it for now" — 2026-08-28), **not** claimed engine-accurate solved. In-scatter is normalized by the **scalar** `1/(lsBetaRay + lsBetaMie)` (H&P's own normalization with the authored coefficients as scalars — a scalar divide, so it rescales brightness without moving any channel ratio; the per-channel `betaTotal` form was tried and rejected in part 27 for cancelling the wavelength split). `scatter_distance_scale` is `3.5e-3`, set so `(1 - Fex)` approaches its ceiling by the ~150-220 m back of the visible room. `RAYLEIGH_WAVELENGTH_WEIGHTS` is λ^-1.5, fit to the reference frame's measured ceiling B/R ~1.56 (parts 30-31), not the old textbook λ^-4. See `docs/context.md`'s parts 27-33 for the full elimination trail.

**What is still open**: the scattering model rests on one `[INFERRED]` normalization (the scalar denominator — corroborated by three consistent measurements, not by the bytecode; see `docs/context.md`'s part 33), one fitted wavelength exponent, and one observational distance scale, none independently verifiable until there is a full graphics pipeline (VFX, bloom) to judge against. The user's read as of 2026-08-28 is that the map-piece lighting colour may now be *more* accurate than the fog, and the fog is the easier of the two to revisit later.

**Not recoverable from files:** `c104`/`c108`/`c109`/`c110` are CPU-supplied per draw. The `.vpo` literal pool is exhausted (`c466` = `(1/1024, 1/ln2, 1/ln2, 1.0)`, plus vertex-attribute decode constants), and a survey of `other/*.properties`, `paramdef/*.tdf` and `other/*.tpf` found only network config, param-editor enum labels and texture banks.

Two deliberate compressions of the engine's structure, both because the target is the same output rather than the same intermediate:

- **The exposure divide and the tone LUT are evaluated as one curve.** DeS divides by a per-shader exposure constant and then runs `DS_Fil_HDR`, a tabulation of Reinhard 2002 (the operator `tonemapbank.paramdef`'s own field descriptions spell out). Since the LUT is that curve, the constant cancels, and evaluating the curve directly on the HDR value is the composition of both steps — which also avoids needing a constant the dumps don't expose. It is applied *per channel*, because `DS_Fil_HDR` is a 1D LUT and a 1D LUT is by construction a per-channel curve.
- **Contrast is an unverified stand-in, and known to be so.** `DS_Fil_HDR` is five instructions — sample the scene, then three per-channel `TEX1D` lookups — and does **no arithmetic at all**: tonemap, brightness and contrast are every one of them baked into a CPU-side LUT this project cannot read. So the engine applies them as a *single* per-channel transfer function, not as a tonemap followed by a separate contrast op, and neither formula this project has used was engine-accurate. **`des_tone_correct` uses the pivot form `(x - 0.5) * contrast + 0.5`** — this is the part-19 output stage (2026-08-27), the composition the user recalls as the closest map-piece lighting *colour* to RPCS3, because pivot brightens above 0.5 where `pow(x, contrast)` only ever darkens. It has a real hazard: with `m01`'s authored brightness 0.80 / contrast 1.1 it clamps anything below a scene value of ~0.027 to zero, and a bare ambient-lit face sits near 0.015. It was swapped to `pow` twice (part 23, and again during the LIGHT_DIG pass) on that ground before being put back — the swap-back rests on the now-engine-accurate scattering haze lifting shadowed geometry clear of the black point at player range, which is the condition the pivot form always needed and never had while the fog was a weak stand-in. If a deep pocket the haze doesn't reach goes pure black, that is the known pivot trade-off; see `docs/context.md`'s parts 23/26/33.
- **Adapted luminance is a uniform, not a measured value.** The engine derives it from the frame's own average luminance, clamped into `[minAdaptedLum, maxAdapredLum]`; the Compatibility renderer can't read frame luminance back. `FlverLoader` passes `minAdaptedLum` — where a dark interior would settle — and it stays a uniform so a bright exterior can be given the other end. **This is the one value in the output stage not read straight from authored data.**

**Both lighting models live in one shader family, selected by a `lighting_model` uniform** (`hemisphere_ambient.gdshaderinc`): `LIGHTING_HEM_ENV` (`MTD.LightingType=3`, the map/lightmap population — hemisphere + environment cubemaps) and `LIGHTING_HEM_DIR3` (`=1`, chr/parts/obj — hemisphere + `LIGHT_BANK`'s three directional lights, plus a **three-lobe Phong** specular: `pow(max(reflect(-V,N)·L_i, 0), g_SpecularPower)` over those *same* three directions, weighted by the single spec-only colour `colA_s` and the RGB specular sample. The reference bytecode builds no half-vector — it is Phong, not Blinn-Phong — and `LightBank.paramdef` has no per-light spec colour or a used spec-only direction, so `degRotX_s/Y_s` stays a uniform only for the unaudited `HemDir3Pnt*` family. Disassembly in `docs/context.md` part 34). The engine compiles a separate binary per combination; a uniform branch is the same choice made at the same point and is what Godot can express. **The two are mutually exclusive on purpose** — `HemDir3` carries no `Env` in its name and `MTD.LightingType.HemDirDifSpcx3` lists no environment term, so a HemDir3 material takes no cubemap contribution. That also avoids a material with no lightmap picking up `env_diffuse` at full strength, since the lightmap sampler defaults to white.

This is what took `g_LightingType=1` materials off `StandardMaterial3D`, which had no real lighting path at all in a project with no light nodes — the reason placed props rendered black without a `WorldEnvironment`. Verified on a real `m01` load: 75 surfaces route to HemDir3 and all 75 bind real directional lights.

**Every material with a real lighting model now goes to the shader family, lightmap or not** (closed 2026-08-28). A `g_LightingType=3` material shipping no lightmap is not a special case: the engine's gate is `min(shadow, lightmap)`, so such a material is gated by the shadow term alone — ~1 wherever nothing shadows it — and the shader's `hint_default_white` lightmap is the correct stand-in for that with no shadow system. It lands about 2.3x brighter than an equivalent lightmapped surface, not blown out. **This was the last population still relying on Godot's own lighting, and therefore the actual reason props rendered black without a `WorldEnvironment`** — the HemDir3 work alone didn't fix it because only 4 of m01's meshes are `g_LightingType=1`; the 60 black ones were all type 3 without a lightmap. Only type 0 (unlit — sky domes, ghost/dissolve, additive VFX) stays on `StandardMaterial3D`: on a real `m01` load that is now **518 HemEnv + 75 HemDir3 + 1 StandardMaterial3D**, and on `m02` **1651 + 37 + 1**.

**`water.gdshader` is `unshaded` too, and takes the same output stage** as of 2026-08-28. It previously wrote its result to `EMISSION` with `ALBEDO=0` plus a `ROUGHNESS`/`SPECULAR` sun-glint — and that glint came from the editor's preview sun, not from anything in the scene. `FlverLoader` gates the light-bank and output-stage uniform groups separately (`HasUniform`), so water gets fog/scattering/tonemap without needing ambient uniforms it has no use for.

**These shaders are `unshaded`.** They compute a finished colour the way DeS's material shaders do, so there is nothing for Godot's own lighting to add; `EMISSION`/`NORMAL_MAP`/`METALLIC` are gone and the `envSpc` term is summed straight into the result. Before this they were lit shaders in a scene with no lights and no `WorldEnvironment`, which meant **the only thing lighting them was the 3D editor viewport's default preview sun and sky** — an arbitrary input that scaled every result and tinted it blue. Anything measured against the old look was measured through that.

**The material-shading half is now structurally engine-accurate; the entire remaining gap is the output stage.** That reframes the standing "too bright"/"too dark" problem: absolute brightness in DeS is set by the exposure divide and the tone LUT, neither of which exists here, so a raw material result reading too dark or too bright is expected and is *not* evidence that the shading math is wrong. It also resolves the architectural question about where a transfer function belongs — **DeS applies its exposure step inside the material shader**, so doing the same here is engine-accurate rather than a workaround for Godot's Compatibility renderer being RGBA8/LDR (see "Known deferred work"). The two constraints happen to point the same way.

## Bloom (`WorldEnvironment` glow)

`FlverLoader.BuildBloomEnvironment` adds one `WorldEnvironment` per loaded map (node "BloomEnvironment", added 2026-08-31). It approximates DeS's `DS_Fil_BrightPassFilter` → `DS_Fil_Bloom` stage, which is the one post-process effect that has to run screen-space **and** show in the editor's own 3D viewport — the only Godot mechanism that does both under the Compatibility renderer is the built-in `Environment.glow`. A `CanvasLayer`/`hint_screen_texture` pass composites only at runtime; `CompositorEffect` needs Forward+/Mobile.

**It is deliberately bounded to glow.** Every other `Environment` feature is pinned to identity/off — `AmbientLightSource`/`ReflectedLightSource` **disabled**, `TonemapMode = Linear`, adjustments/SSAO/SSIL/SSR/SDFGI/fog all off. This is *not* the "ambient/reflection `WorldEnvironment`" that earlier notes say this project must not have: the reason that one regressed was the `StandardMaterial3D` map population collapsing under engine ambient with no light nodes (part 25), and a glow-only Environment with ambient disabled cannot bring that back. The unshaded shader family takes no ambient or reflection regardless.

**Calibration** comes from `TONE_MAP_BANK` row 0: `bloomMul/100` → `GlowBloom` (0.80 Nexus, 0.50 Boletaria/Latria — the dial that actually carries the effect on an LDR buffer), `bloomBegin/100` → `GlowHdrThreshold` (0.20), plus a mid-level `SetGlowLevel` spread standing in for `DS_Fil_Bloom`'s wide downscaled gaussian. User-checked in-editor 2026-08-31: present and roughly right, Nexus a little hot — the numbers are a placeholder to retune against RPCS3, the mechanism is not.

**Ceiling.** This can absorb one more real stage — a colour-correction LUT built from `TONE_CORRECT_BANK`, via `Environment.adjustment_color_correction` — but no further. Eye adaptation (`CalcAdaptedLum`) has **no path** under Compatibility (auto-exposure is Forward+/Mobile only), a true HDR tonemap needs an HDR viewport this renderer doesn't have, and `Environment` is one-per-viewport so it can never do per-part `ToneMapID`/`FogID` (which is why tonemap/fog/atmosphere stay in-shader). Hosting the whole `ds_filter` chain accurately would mean a `CompositorEffect` and therefore a renderer switch off Compatibility — a real fork the project has avoided for weaker-hardware reasons, not a near-term option.

- **Nothing in the lightmap/blend shader family read the normal map — every lighting term was blind to it, which is why engraved/relief surface detail disappeared ("waxy" walls). Root-caused and fixed 2026-08-27; kept here for the reasoning trail.** Per-pixel normals and env-cubemap sampling landed together, as the scoping check at the end of this entry required. `hemisphere_ambient()` blends on `world_normal`, a varying computed from the **vertex** normal in `vertex()`, and the env term is a flat `lightmap` sample with no normal dependence at all. `NORMAL_MAP` *is* assigned, but in Godot that only feeds the engine's own lighting response — and this project has no light nodes, so it modulates nothing. The real HemEnv shader does the opposite: it reconstructs a per-pixel normal from the bumpmap (2-channel tangent-space sample, `Z = sqrt(1 - (x²+y²))`, TBN basis built by cross product) and uses that per-pixel normal for **both** the hemisphere blend factor **and** the env cubemap's reflection vector. So the fix is per-pixel normals inside our own shading math — **not** adding directional lights, which the map family provably doesn't use (see the `LIGHT_BANK` entry above). User-reported via a Nexus wall comparison where RPCS3 shows clear engraving relief in shadowed arches and this project shows nearly flat black. **Important scoping check before anyone implements this: per-pixel normals in the *hemisphere* term alone would be invisible in both current test areas.** The hemisphere blend interpolates between the `_u` and `_d` colours, and on the real rows those endpoints are equal or nearly so — `m02` rows 0/1/2/4 (Boletaria B0, the main test block) have `up` and `down` **byte-identical**, so the blend is a constant and no normal, per-pixel or not, changes its result; `m01` row 0 (the main Nexus) differs by only 0.06 total across RGB. The normal-dependence that actually carries engraved detail in the real shader is the **env cubemap reflection** (`TEX3D(11, reflect(V, N_perpixel))`), which is high-frequency and genuinely normal-driven — our env term is a flat lightmap sample instead. So per-pixel normals and env-cubemap sampling have to land **together** to be worth anything; neither delivers alone.
- **Godot's Compatibility (`opengl3`) renderer is RGBA8 low-dynamic-range, with no HDR viewport and no HDR output** — per Godot's own renderers documentation. That suits this project's shaders, which already hand-compute a final colour rather than feeding Godot's lighting model. Relevant because this project targets Compatibility deliberately (weaker-hardware support is a stated goal) and because the real DeS operator is now reconstructable: `tonemapbank.paramdef`'s own field descriptions (`grayKeyValue` "larger → brighter", `minAdaptedLum`/`maxAdapredLum` the dark/bright adaptation window, `adaptSpeed`) identify it as **Reinhard 2002 photographic tone reproduction with temporally-adapted luminance**, so `DS_Fil_HDR`'s 1D LUT is a tabulation of a curve that can be rebuilt from authored per-map values without capturing the LUT itself. **Built 2026-08-27** — `output_stage.gdshaderinc`'s `des_tonemap()`, applied in-shader as this entry requires. - **Some `obj/` FLVER0 files genuinely contain zero meshes — this is correct, not a resolution failure.** Confirmed by scanning every mounted `obj/` FLVER0 directly: of 1068 files, 62 have no mesh. 57 of those are real, by-design attach/anchor markers (0 meshes, 0 materials, just 1-2 `Dummy` points and a single root `Node`, e.g. `o6511`/`o6600`) — the same attach-point convention (recurring refids like 191/192/200) also shows up on real meshed props (`o6700`'s `dmy_191`/`dmy_192`), so it's a generic game-wide convention, not unique to the empty files. The other 5 (`o2305`, `o2309`, `o2310`, `o4700`, `o6351`) are 288-byte bare-minimum stubs with nothing at all — read as allocated-but-never-built object IDs. Neither case is fixable by a smarter `CandidateDirs`-style rule, since there's no mesh anywhere to find.
- **`g_TexScroll_0` UV-scroll animation shipped 2026-08-27 for every material family — closes half of this item.** `m3051b0`'s Nexus sun-ray quads (`A05_vollight[Dn]_Add.mtd`, also present under `area02`/`area03`/`area99`) and the broader animated-material set (water, lava, clouds, light shafts, skies, the `c5000` slime terrain-blend materials — 52 MTDs with `g_TexScrollType=1`, ~92 with nonzero `g_TexScroll_0`) now scroll: unlit standard-family materials (108 meshes — skies/clouds/light shafts/vollight) got a small new shader family, `vfx_scroll.gdshader`/`vfx_scroll_add.gdshader` (split because blend mode is a compile-time `render_mode`, same reason the lightmap family needs a separate file per blend mode); lightmap and terrain-blend materials got a `tex_scroll_0`/`_1` uniform instead (14 meshes). User-confirmed in-editor (2026-08-27): sky and light-shaft/fog materials scroll correctly. **Remaining ceiling:** the 25 *lit* scrolling standard meshes (lava, slime, `a05water03`) still don't scroll — `StandardMaterial3D` has no UV-animation hook, and moving them to a shader would mean reimplementing Godot's PBR by hand for 25 meshes, not judged worth it. Those same 108 unlit VFX meshes also inherit the already-documented double-sided ceiling below (12 of them lose two-sidedness, since cull mode is also a compile-time `render_mode` keyword). **The glow half of this item — `g_DiffuseMapColorPower`-driven materials (runes, sky dome) not self-illuminating — is still open**, blocked on the same missing-`WorldEnvironment`/`CameraAttributes` prerequisite described in the entry immediately below; see `docs/context.md`'s "Nexus VFX gaps investigated" entry for the full trail.
- **`StandardMaterial3D.Emission` (texture-driven) renders badly wrong without a calibrated `WorldEnvironment`/`CameraAttributes` — confirmed via real rendering, not assumed, and this blocks any glow/self-illumination fix, not just the two materials above.** Tried feeding `g_DiffuseMapColorPower`-driven materials' diffuse texture into `Emission` so they'd read independent of scene darkness. A real (non-headless, opengl3) render showed `Emission`-driven output desaturating toward flat white well before `EmissionEnergyMultiplier` reaches 1.0 — reproduced with a synthetic solid-color texture with zero FLVER/TPF involvement, so it isn't a decode or resolution bug, it's `Emission` itself in this project's current unconfigured-exposure state. `Emission` set to a plain color (no texture) renders correctly; only the texture-driven path is affected. Since this project has no ambient/exposure `WorldEnvironment` or `CameraAttributes` anywhere yet (the glow-only bloom `WorldEnvironment` added 2026-08-31 disables ambient and pins linear tonemap, so it doesn't help here; the same gap already pauses water/lightmap tuning below), and exposure control lives on the camera/environment rather than anything `FlverModelBuilder` touches, there's no tunable constant that fixes this from here — it's a real prerequisite gap, not a smaller bug. Revisit once the map-assembler's planned `WorldEnvironment` work lands (`docs/PLAN.md`'s Phase 1 item 4). See `docs/context.md`'s "Nexus VFX gaps investigated" entry for the full before/after evidence.
- **Destructible-prop debris (a subset of `obj/`, e.g. `o6511`-`o6602`) is a genuinely unhandled system, not a missing resolution rule.** These pair a dummy-only FLVER0 (see above) with an `hkx` file and no `tex/` folder at all — verified directly against the raw, unmounted PS3 `.objbnd`/`.objbnd.dcx` (byte-identical inner content in both) that this is real shipped data, not an extraction artifact. The raw game root also has `map/breakobj/*.breakobj` (20 files, one per map area, magic header `OBJB`) — completely undocumented in `SoulsFormatsNEXT/FORMATS.md` and unparsed anywhere in this project. Working theory, not yet confirmed: these IDs are physics-only fracture anchors, and the actual visible debris is composed at runtime by the Havok destruction system from a small shared library of generic rubble chunks, driven by `.breakobj` data (placement + physics + which chunk to use) rather than stored per-object-ID. Would need `.breakobj` reverse-engineered (and likely `param`/`paramdef` data, currently outside `AssetExtractor`'s category allowlist entirely) before this could become an importer feature at all.
- **The `diffuse * lightmap` multiply's contrast problem is fixed at the formula level using real data; the one thing still open is per-part accuracy.** Decompiled FRPG-engine shader source (Dark Souls Remastered's `FRPG_FS_HemEnv.fx`, the same lighting family DeS's `g_LightingType=HemEnvDifSpc` MTD tag names — not byte-exact to DeS's 2009 shader, but the only concrete ground truth found) showed the real shader never multiplies the lightmap against the base diffuse/ambient response at all; it only scales a secondary environment-reflection term, while a separate always-on two-color hemisphere-ambient term (blended per-vertex by normal Y) provides the actual shadow floor, untouched by the lightmap. **Confirmed against real DeS bytecode (2026-08-17, RPCS3 shader capture, see `docs/context.md`'s "Lightmap/drawparam system, part 11"):** the hemisphere blend shape matches exactly, and — contradicting this doc's own earlier reading of the DSR reference — the real env term is *not* kept separate from the hemisphere sum; it's added into the same accumulator before the diffuse multiply, exactly matching what this project already ships. No shader change resulted; only this doc's framing needed correcting. Three shader-only approximations using invented placeholder numbers (flat neutral floor, hue-preserving reciprocal boost, additive diffuse-tinted floor) were tried and reverted earlier this session — see `docs/context.md`'s "Lightmap system, part 4". `docs/context.md`'s "Lightmap/drawparam system, part 5" then found DeS's own `MSBD.PartsParam.LightID`/`FogID` byte fields (marked `Unknown` even upstream) index into per-map ambient/fog rows in the game's generic `.param` files, and part 6 confirmed this directly: `param/drawparam/m01_lightbank.param`/`m01_fogbank.param` parse cleanly against DeS's own shipped paramdefs (`LIGHT_BANK`/`FOG_BANK`, loose files, no BND unpacking needed) and hold exactly the hemisphere-ambient-shaped row data the DSR source predicted. Both `lightmap_common.gdshaderinc` and `terrain_blend.gdshader` now use that formula shape (see "Lightmaps" above), sourced from `default_lightbank.param`'s real row 0 as a global placeholder, sharing the math via `hemisphere_ambient.gdshaderinc`. **Still open:** per-part accuracy needs the matching per-map `LightID` row. MSB parsing itself already exists (`MsbLoader`, see "MSB map placement" above) and already reads `LightID`/`FogID` off every part struct — what's missing is resolving that byte into a `LIGHT_BANK`/`FOG_BANK` row and wiring the result into each placed instance's shader uniforms, not the MSB reader itself. Confirmed 2026-07-26 this data is worth wiring, not near-constant: `LightID`/`FogID` vary meaningfully per-part within a single map (see `docs/PLAN.md`'s Phase 1 item 4 for the real per-map numbers), which now spells out how per-instance `LightID`/`FogID` resolution and a real `WorldEnvironment` setup both fold into that same future map-assembler work, rather than being separate tasks. **Resolved:** the Boletarian Palace hard-edged dark-block regression (large flat near-black patches, no gradient) — user-confirmed real-editor testing (2026-07-22, `docs/context.md`'s "Lightmap/drawparam system, part 7") traced it specifically to `terrain_blend.gdshader` still running the old plain multiply at the time; porting the same hemisphere/env formula there (sharing the math via `hemisphere_ambient.gdshaderinc` rather than duplicating it) fixed it, user-confirmed. **Closed, not a bug:** the smaller-scale purple/green/magenta block-noise artifact investigated at length in `docs/context.md`'s "Lightmap system, part 5" and "Lightmap/drawparam system, part 9" (leading suspect was a PS3 DXT1 block-swizzle never undone by `Headerizer.ReadPS3Images`, tested and disproven in part 9) turned out not to need fixing at all: user-confirmed by direct in-game observation (2026-07-26) that real, unmodified Demon's Souls shows the same faint green/magenta artifacts on Nexus geometry, to the same subtle degree now visible after the hemisphere/env formula fix — either an intentional blending choice or an original-game imperfection too minor to have been worth fixing, either way not an importer bug. No longer tracked as open work.
