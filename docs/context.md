# context.md

Session history, lessons learned, and ruled-out dead ends for this project. `docs/ARCHITECTURE.md`
covers current architecture and how to work in the repo; this file covers *why* things
are the way they are and what's already been tried and rejected, so it doesn't get
re-litigated. Read both — docs/ARCHITECTURE.md for the current state of truth, this for the journey.

## The arc so far

Started as a proof-of-concept console app (`desflver_test/`, since deleted) that used
WitchyBND + the vendored SoulsFormatsNEXT library to write `.obj`/`.mtl`/`.png` for
Godot's generic Wavefront OBJ importer to pick up — fought constantly (path leakage,
raw DDS bytes, a Godot OBJ/PNG-import race bug) before being replaced entirely by a
native `EditorSceneFormatImporter` (itself later replaced by the current architecture,
see below). Two facts from this era still matter: **no Godot build has C# support except
the official godotengine.org `.NET` build** — confirmed the hard way on Redot (none at
all) and Steam's Godot (also none) — and **a forked/patched vendored submodule's local
commits are a live risk until actually pushed to a real remote**, not just a tidiness
concern: `SoulsFormatsNEXT`'s two local patches sat as uncommitted working-tree edits in
a plain clone for a while, meaning any `git pull`/`checkout` in that directory would have
silently wiped them with no recovery path, before being committed to a real fork and
pulled back in as a proper submodule. The project was also renamed `Boletaria` →
`Soulbrandt` along the way and made public under GPLv3 (required by `SoulsFormatsNEXT`'s
own license, not an arbitrary choice).

## Real bugs found and fixed (root causes, not symptoms)

Each of these produced a plausible-looking but wrong intermediate theory before the real
cause was confirmed — noted so the same wrong turn isn't re-taken.

- **Five foundational bugs from the pre-architecture-pivot era, all now standing conventions described in docs/ARCHITECTURE.md — kept here only as a "why," not the full narrative.** Pfim's decoded buffer holds the full mip chain, not just the base level — must slice to `width*height*4` before `Image.CreateFromData` (confirmed via `pfImage.MipMaps[]`'s real per-level offsets). Godot uses clockwise front-face winding with no UV V-flip needed; the old `desflver_test/` OBJ-export tool's winding-swap/V-flip logic was specific to Blender/OBJ conventions and wrong to port into the native path (confirmed via 16k+ triangle normal comparison and a wireframe-vs-texture visual match). `SoulsFormatsNEXT`'s own `Mesh.cs` picks a UV scale factor by header version (`>= 0x12` → 2048 else 1024) — wrong for DeS, which always needs `1024` regardless of version (confirmed via UV-wireframe overlay on two models with different header versions); patched directly in the vendored fork. **The big one, went unnoticed for a long time**: every import was a left/right mirror of the real thing, invisible because mirroring one axis also flips the apparent triangle winding — the existing winding/UV checks kept passing on a fully-mirrored-but-internally-consistent import, and a bilaterally-symmetric human skeleton doesn't reveal it either. Caught only because the user recognized a real map (`m03_01_00_00`) as a literal mirror of its sibling, then confirmed via `c9990`'s swapped shield/sword hands; root-caused two independent ways (skeleton bind-pose FK, and the map-level mirror itself). Fix: negate X on position/normal, swap two triangle indices per face (required *because of* the X negation, not a separate correction). Verified: reimporting the full corpus produced the same known-error count, and the user visually confirmed both cases.
- **Two empty-imported-scene bugs, one shared root: `ImporterMesh`/`ImporterMeshInstance3D` never render outside Godot's own import pipeline, and `PackedScene.pack()` only serializes descendants with `.Owner` set.** Both are still-live requirements, documented as current architecture in docs/ARCHITECTURE.md. Diagnostic trick worth keeping: `ResourceSaver.save(packed, "res://debug.tscn")` dumps a resource as human-readable text.
- **Case-sensitive texture lookup and a race condition in an old area-texture cache — both closed.** Texture-name dictionaries are `OrdinalIgnoreCase` throughout (a material referenced `m03_01_wall_cliff_00`, the real TPF entry was `m03_01_Wall_Cliff_00`). The cache race was a non-thread-safe `Dictionary` under Godot's old multi-threaded reimport dispatch — can't recur, `FlverLoader` is single-threaded with no such dispatch anymore. Worth remembering the diagnostic signature: inconsistent, non-reproducible-the-same-way symptoms mean a threading bug, not a logic bug.
- **Alpha/cutout MTD-suffix convention (`_Edge`/`_Alp`/`_Add`) and map texture resolution (same-basename sibling vs. shared per-area folder) — both fully described as current behavior in docs/ARCHITECTURE.md.** `_Add` was a later addition (found via `m8003b1`/`m3051b0`'s missing volumetric-light blending, confirmed real via a 22-material/15-file corpus scan, never used on solid geometry).
- **Terrain ground-blend layer (hard seams between grass/dirt/stone) — fixed, fully described in docs/ARCHITECTURE.md's terrain-blend entry.** Gated on FromSoft's own `[M]`/`[ML]` MTD bracket tag, not `g_Specular_2`/`g_Bumpmap_2` presence (tried first, wrongly excluded real materials missing an optional specular layer — confirmed via a 963-material scan). Blend weight is `VertexColor.A`, not `.R`/`.G`/`.B` (confirmed via corpus correlation stats, not just "varies 0-1" — R turned out to be a binary per-vertex flag when tried as AO and visually disproven). **Superseded 2026-09-15:** `.R`/`.G`/`.B` is no longer unknown — the map-shading research pass's finding #3 (instruction-level comparison against native `Mul`-family HemEnv fragment programs) found it's a real free multiplier on both the blended diffuse and the blended RGB specular sample, the same role the single-layer family's vertex colour plays; `terrain_blend.gdshader` now applies it that way. See `docs/ARCHITECTURE.md`'s terrain-blend entry for the current behavior.
- **Water surfaces and cross-category texture reuse — both fully superseded/described elsewhere, kept only for what isn't duplicated.** Water: `g_Envmap` uniquely gates the family (confirmed via direct scan, not a filename heuristic); `g_WaterColor`'s alpha channel was initially silently discarded, which is what actually separates murky from clear water — see the interop gotchas section below for the real `SetShaderParameter`/`source_color` bug found while wiring this up. Cross-category reuse (a corpse pile rendering fully white, reusing a *character* model's texture set) is now handled by `CandidateDirs` — see the "Texture-resolution redundancy" entry below.
- **Map-piece naming investigation (`l1` suffix, Boletarian Palace) — curiosity-driven, findings scoped into docs/PLAN.md's map-assembler item.** `l1` is a map-piece-only convention, unrelated to parts' `_L` LOD suffix (confirmed: `l1` appears nowhere else in the ~1030-file map dataset, no `l2`/`l3` anywhere). Geometry comparison mostly but not cleanly supports "reduced-detail variant" (5/8 have fewer verts at the same bounding box, but one has identical counts and another has nearly double). The white patches on 3 of these files are unrelated and fully root-caused: all reference `m02_tower_wall_plain.tga`, which doesn't exist anywhere in the extracted dataset — genuinely orphaned source data, not an importer bug. Tested "used in the opening cutscene" against real placement data and found no support: a crude but effective diagnostic (raw string-count of each model name in the `.msb`) showed every ordinary placed piece scoring exactly 3 occurrences, all 8 `l1` files scoring 0 — more likely intended-but-cut content than cutscene-specific. **Bigger-picture lesson, confirmed not assumed: not every loose FLVER sitting in a map's folder is actually placed in that map** — any future map assembler needs to consult the MSB's own Parts list, not just glob the directory.
- **Origin-offset decoration sub-meshes — investigation only, conclusion now in docs/ARCHITECTURE.md's coordinate-conventions section.** Confirmed real and general (not a one-off): several map pieces (`m2501b0`, `m2210b0`, `m2601b0`, `m4013b0`) have a sub-mesh sitting at local origin instead of its real position, alongside a `FLVER.Node` whose name and `Translation` match where it should go — but `Mesh.NodeIndex` (the one field that could link them) is uniformly `0` everywhere checked, so it's not a live, importer-readable binding. Best-supported explanation: each decoration gets its own MSB placement entry referencing this shared FLVER plus a specific node — another confirmation that real map assembly needs MSB parsing, not just FLVER import.
- **Asset mounting system built — WitchyBND no longer needed, fully described as current behavior in docs/ARCHITECTURE.md's "Asset mounting" section.** Confirmed `SoulsFormatsNEXT`'s `DCX`/`BND3`/`BND4` readers handle this game's real containers directly (`DCX_EDGE` compression, confirmed via raw header bytes and the library's own `Type.DemonsSouls` alias; no external name-dictionary needed, unlike later-game hashed-name formats). One real interop gotcha: BND entry names use a `DVDROOT` path segment, distinct from `Model` (what FLVER texture *references* use) — easy to conflate, handled by dropping exactly one segment after `data` regardless of which literal word it is.

- **Non-visual game-logic data investigation (curiosity-driven, not a bug report —
  headline findings already condensed into docs/PLAN.md's Phase 2 section; kept here for
  what isn't duplicated there).** Confirmed directly against the real mounted dump, not
  assumed from general Souls-series knowledge, that none of Phase 2's eventual
  gameplay-logic needs would require any DRM circumvention: `EBOOT.BIN` (Sony's encrypted
  SELF container) is correctly off-limits, but `script/` (plain unencrypted Lua, same
  approach as DS1), `param`/`paramdef` (DeS ships its own paramdefs, unlike later titles
  needing the community `Paramdex` project), and per-character `.tae`/`.esd` files are
  all real, already-parseable, disc-native data. One naming trap worth remembering: DeS's
  poise-like mechanic is internally called **Super Armor**, not Poise — there's no
  DS1-style "Poise stat reduces hitstun" field in any table checked, so porting fan
  terminology directly would be wrong. Two real gaps remain: TAE event `Type` IDs have no
  friendly name without an external template (unbuilt for DeS), and precise i-frame/
  hyper-armor frame counts aren't publicly documented anywhere for this specific title
  (unlike Dark Souls 3) — likely needs direct frame-by-frame observation against the real
  game in RPCS3, not extraction.

- **Texture-resolution redundancy found and unified (`GetAreaTextures` deleted) — the audit and resulting `CandidateDirs` architecture are now fully described in docs/ARCHITECTURE.md's "Texture resolution" section, not duplicated here.** Triggered by asking directly whether the accumulated per-case methods were actually clean or "smaller solutions taped together" — checked via a 26,656-ref corpus scan rather than assumed: `GetAreaTextures` never once succeeded where `GetForeignCategoryTextures` didn't already cover it. Replaced both (plus the about-to-be-added obj/parts sib/tex rule) with one ordered `CandidateDirs` chain. One case deliberately **not** generalized into a fifth rule at the time: `o6510_1`'s bottle/vase texture (byte-identical across 6 unrelated obj containers, not in its own folder or any map bucket) — no cheap signal for which sibling folders to search, flagged as needing more real examples before it's worth the scan-cost/collision-risk tradeoff (later resolved by `SiblingObjTextureDir`, see docs/ARCHITECTURE.md).
- **`obj/` "empty scene" investigation — mostly confirmed-correct-as-is, conclusions in docs/ARCHITECTURE.md's "Known deferred work."** Of 1068 mounted `obj/` FLVER0 files, 62 have no mesh: 57 are genuine dummy-only attach/anchor markers, 5 are bare allocated-but-never-built stubs. Neither is fixable by a smarter resolution rule — there's no mesh anywhere to find.
- **FLVER0 vertex-layout crash — two crash sites, one root cause, closed and confirmed corpus-wide (zero errors across ~3411 files); surviving fallback logic documented in docs/ARCHITECTURE.md.** Some meshes' `BufferLayout` genuinely has no Normal/UV/VertexColor member at all — not a parser bug. Needed two fixes: the importer's own vertex loop (guard on `.Count > 0`, fall back to sane defaults) and one level deeper in `SoulsFormatsNEXT` itself (`Mesh.Triangulate`'s `doCheckFlip` crashed on the same meshes — gated at the call site rather than passing `false` unconditionally, which would have silently broken winding-correctness on strip meshes that legitimately need the check).
- **Lightmap system added, then parts 2-3 fixed two shader-compile bugs and a `WorldEnvironment`/sky gap — all now fully described as current behavior in docs/ARCHITECTURE.md's Lightmaps section.** The lightmap is a genuine per-mesh UV atlas bake, confirmed via manual decode before committing to any shader architecture. `blend_mix`/`blend_add` being compile-time `render_mode` keywords (not a per-material property) is why there are three thin shader variants instead of one runtime-switched shader; `Custom0`'s component format has no explicit-array-format parameter in 4.7's `SurfaceTool` C# binding, worked around via `ImporterMesh.AddSurface`'s `flags` parameter. Part 2's two real shader-compile bugs (assigning built-ins from a helper function; reading `CUSTOM0` outside `vertex()`) are both invisible under `--headless` and only caught by a real Xvfb+opengl3 driver check — now standing restrictions documented in ARCHITECTURE.md. Part 3: darkness/contrast root-caused to a missing sky in the scene's `WorldEnvironment`, not a shader/color-space bug — ruled out sRGB/gamma mismatch directly via pixel-readback test first. Two still-generally-useful process lessons from this stretch: a background `godot-mono --import` launched via a trailing shell `&` can report "complete" almost instantly while the real process keeps running detached — verify via `ps aux`, don't trust a quick tool-call return; and reflection into a private method (`ResolveTexture`/`DecodeTexture`) is a legitimate way to test the *exact* pipeline in a throwaway probe rather than reimplementing it by hand.
- **Lightmap system, part 4 — three shader-only contrast/artifact fixes attempted, all reverted; real architecture correctly identified (hemisphere-ambient floor + lightmap-scaled env term, not a plain multiply) but blocked at the time on unparseable per-map color data.** Real DeS MTD data confirmed these materials are tagged `g_LightingType = HemEnvDifSpc`. Community ground truth (`AltimorTASDK/dsr-shader-mods`, decompiled Dark Souls Remastered HLSL — same FRPG engine lineage, not byte-exact to DeS's 2009 shader but the only concrete source found) showed the real shader never multiplies the lightmap against the base diffuse/ambient result — it only scales a secondary env/IBL term, while an always-on two-color hemisphere-ambient term (blended by vertex-normal Y) is added on top, untouched by the lightmap. Three attempts, all reverted: (1) a flat neutral floor fixed the crush/blowout but looked "dull," diluting the real warm-toned baked color; (2) a hue-preserving reciprocal boost blew up DXT block-compression noise into visible purple/green/magenta patches via division by near-zero luminance; (3) an additive floor tied to diffuse color (matching the real shader's actual structure, no division anywhere) still showed color patches, which was itself a finding — it pointed away from the compositing formula and toward the raw lightmap texture decode as the artifact's real source. Reverted to the original plain multiply; real fix stayed blocked on per-map hemisphere-ambient color data no format in this project could parse yet.
- **Lightmap block-noise artifact (parts 5 / 9 / 10) — closed as *not a bug* (2026-07-23 → 07-26).** Faint purple/green/magenta speckle on `m01` lightmap textures, aligned to 4×4 block boundaries. Chased: manually decoding the worst BC1 block per spec showed Pfim's output (`(19,19,19)`+) exceeds anything the block's own bytes can produce → suspected an un-undone PS3 block-swizzle for compressed formats. Tested directly against Soulstruct's format-generic PS3 deswizzle — it made the texture *worse* (coherent → scrambled), and `Headerizer.Headerize`'s own doc-comment already said DeS/DS1 don't PS3-swizzle most formats. Closed in part 10: the user played real unmodified DeS and saw the identical artifact at the same subtlety — an original-game characteristic, not an importer decode bug. **Standing lesson:** read every doc-comment/guard on the exact function before trusting an external comparison, however well-evidenced.
- **Lightmap/drawparam system, part 5 — an outside contact with DeS reverse-engineering knowledge, asked cold, confirmed drawparam colors and vertex color both matter for DeS shading and are applied via per-part `LightID`/`FogID`-shaped MSB fields referencing `.param` rows.** No literal `DrawParam` format exists in `SoulsFormatsNEXT`; the graphics-config formats that do exist (`GPARAM`/`BTL`/`BTAB`/`BTPB`) are all confirmed DS2-and-later via their own doc comments, and zero `.btl`/`.gparam` files exist in the mounted extraction — DeS predates that format lineage entirely. `MSBD.PartsParam.LightID`/`FogID` (both marked `Unknown` upstream) already existed, parseable, unused — matching the contact's hazy recall. The actual color/ambient values live in generic `.param` rows, not a dedicated format — `PARAM`/`PARAMDEF` support already exists generically, but the specific target paramdef wasn't identified yet at this point. Recommended and later-taken next step: a small throwaway investigation to confirm what `LightID`/`FogID` actually resolve to before committing to real MSB-parsing plumbing — same "verify the premise before building on it" lesson as the DSR-shader-approximation caveat in part 4.
- **Lightmap/drawparam system, parts 6-8 — `LIGHT_BANK`/`FOG_BANK` confirmed against real data and wired into the shader; now fully described as current behavior in docs/ARCHITECTURE.md's Lightmaps section.** Row IDs/names line up 1:1 between `LIGHT_BANK`/`FOG_BANK` (confirmed, not inferred). A distinct, worse regression on Boletaria (hard-edged dark patches, no gradient) surfaced only via real in-editor testing — `terrain_blend.gdshader` hadn't gotten the hemisphere/env formula yet; porting it there fixed it, user-confirmed.
- **Nexus VFX gaps investigated (2026-07-26) — two real, separate root causes for map-piece "glow"/"animation" materials looking flatter than the real game, both scoped as future work.** `m3051b0`'s sun-ray quads carry real, authored `g_TexScroll` UV-scroll data (`A05_vollight[Dn]_Add.mtd` family, confirmed present under multiple areas) currently only wired for water materials — `BuildStandardMaterial` has no scroll path at all. Separately, `m3030b0`'s runes and `m9501b0`'s sky dome carry real `g_DiffuseMapColorPower` values meant to make them glow, but the tint math is a no-op whenever the base tint is pure white (true for the large majority of materials, including both of these). An `Emission`-based fix was tried and reverted: real rendering showed `Emission`, unlike `Albedo`, renders badly wrong (desaturates toward flat white) with no `WorldEnvironment`/`CameraAttributes` anywhere to calibrate exposure against — reproduced with a synthetic texture, zero FLVER involvement, ruling out a decode bug. Genuinely blocked on the same missing-environment gap as water/lightmap tuning, not a smaller fixable issue. (Later superseded for the sky-dome case specifically by the `g_LightingType=0` fix, see the 2026-08-18 entry below — the real mechanism turned out to be "skip ambient entirely," not "boost emission.")
- **MSB-parsing next-step scouting (2026-07-26) — confirmed the `MSB1`-can't-read-DeS blocker was stale, and confirmed `LightID`/`FogID` genuinely vary per-part rather than being near-constant per map.** DeS uses `MSBD` (its own reader), not `MSB1` — the `Treasure.ReadTypeData` assert bug lives only in DS1-specific `MSB1` code this project never calls; corrected in `docs/PLAN.md`/`docs/ARCHITECTURE.md`. A temp debug dump against four real maps confirmed `MSBD.Read()` completes cleanly end to end and that `LightID` varies real and wide within a single populated map (real per-category numbers now live in `docs/PLAN.md`'s Phase 1 item 4, not repeated here) — investigative only, no code kept from this pass.
- **The old `EditorSceneFormatImporter` pipeline (deleted 2026-07-24) absorbed several rounds of real stability work before being replaced outright — compressed here since none of the mechanism still exists.** In order: a bulk-reimport-only `o0103.flver` hang (unbounded per-instance texture cache growth); a batching mitigation that needed a second fix after wiping its own restart-recovery on the first test; a texture-cache self-eviction fix (`MaybeEvictDecodedTextures`, still present today, this part outlived the importer it was written for); and a concurrency gate that, after confirming directly against Godot's own engine source that no lever exists to control reimport concurrency at all, still didn't fix the underlying crash cycle. That last dead end — Godot gives a plugin no control over its own reimport concurrency — motivated the architecture pivot below, not another patch attempt.
- **The `res://`-bypass pivot — prototyped from a peer developer's real reference implementation (thanks Nox, see `.local-notes.md`), then actually implemented, and is now the shipped architecture (2026-07-24), user-confirmed working, fast, and the best state this plugin has ever been in.** Four real bugs surfaced during implementation, each found by testing against real data: (1) an unrelated, pre-existing hard engine crash on `m2011b1.flver` (confirmed pre-existing by reproducing it on the un-split code too) — not root-caused, flagged as a known open issue, moot for the reimport-queue path specifically since that path no longer exists; (2) a prototype custom `Tree`-based file browser (`mounted_browser_dock.gd`) whose expand arrows never worked in the live editor despite verified-correct handler logic in isolation — abandoned in favor of the already-proven `EditorFileDialog` pattern rather than continuing to debug blind, deleted outright; (3) the one that actually mattered: extraction still triggered the exact crash-prone reimport cycle the pivot existed to avoid, via a leftover `EditorInterface.get_resource_filesystem().scan()` call and the old importer still being registered — fixed by removing both, `FlverSceneImporter.cs` deleted; (4) loaded models had correct structure but were completely invisible — `ImporterMesh`/`ImporterMeshInstance3D` are import-pipeline-only placeholder types with no rendering of their own, and `FlverLoader` never goes through that pipeline. Fixed via `ImporterMesh.GetMesh()` → real `ArrayMesh`/`MeshInstance3D`. **Process lesson**: two of the four bugs were found only because the user actually exercised the feature end-to-end in the real editor — neither `dotnet build` nor a headless structural smoke test caught them, the same category `--headless`'s dummy rendering driver already can't catch for shader errors.
- **Armor/character specular flatness — root-caused and fixed (2026-07-24), now fully described as current behavior in docs/ARCHITECTURE.md's roughness section.** `Roughness` sat at `StandardMaterial3D`'s own default (`1.0`, fully rough) since only `Metallic` was ever set from `g_Specular` — silently true for every non-lightmapped chr/parts material, not armor-specific. Verified against real `c9990` data that the fix reads genuine per-material values, not one hardcoded number.
- **Destructible-prop debris cluster (`o6511`-`o6602`) — investigated, root-caused as genuinely out of importer scope for now.** Verified directly against raw, unmounted PS3 files: the shipped game data for these objects really does contain 0 triangles. Found `map/breakobj/*.breakobj` (20 files, magic `OBJB`, completely undocumented) as the likely real geometry source — working theory is a Havok-destruction system composing debris at runtime from a small shared chunk library, which would mean no per-file resolution rule could ever recover it. See docs/ARCHITECTURE.md's "Known deferred work."
- **Lightmap/drawparam system, part 10 — scouted (not implemented) whether DeS's unused/underused armor reflection system is real; confirmed as a genuine cubemap system.** (Water's `g_Envmap` is also a real cubemap — established later, part 50.) Scouting only, per the user's own framing — no code changed. **Conclusion: real, extractable, structurally-legible data — a genuine reflective-cubemap upgrade for armor materials is possible, not just rumored.** Findings folded into docs/ARCHITECTURE.md's "Character/parts specular accuracy" bullet, which also lists the concrete blockers (param/paramdef extraction, unconfirmed per-map cubemap resolution, the same MSB per-part resolution work `LIGHT_BANK` needed, and no cubemap slot on `StandardMaterial3D`).
- **MSB map-piece placement — first slice implemented, 2026-07-24, fully described as current behavior in docs/ARCHITECTURE.md's "MSB map placement" section.** New `MsbLoader.cs` mirrors the `FlverModelBuilder`/`FlverLoader` split (pure parsing, no scene nodes). Real finding, corpus-checked before assuming the transform math mattered: most `MapPiece` parts carry an identity transform (geometry pre-baked into the FLVER's own world-space data), but a real minority are genuinely reused at multiple instances per block and need a real per-instance transform — varies enormously by map (Boletaria 1/61, `m08_00_00_00` 84/85). Even before rotation correctness was confirmed, the membership filter alone was real working value: it distinguishes placed `.flver`s from unused leftovers for the first time. Position/X-negation matched `FlverModelBuilder`'s own convention and was structurally verified; rotation was a starting hypothesis at the time, later spot-checked (see "MSB map placement" in ARCHITECTURE.md). Scoped to `MapPieces` only — `Objects`, `Enemy`/`Player`/`Collision`/`Navmesh`, and drawparam wiring all deliberately deferred to later slices.
- **Rigid mesh-to-node binding — the real cause of "decorations sitting at the world origin," root-caused and fixed via real user testing of the MSB slice (2026-07-24), now fully described in docs/ARCHITECTURE.md's coordinate-conventions section.** Found only because the user tested "Load Map..." in the real editor — a category of gap headless checks structurally can't cover. A re-test after the first fix caught a real gap in it (a mesh can mix vertices bound to *different* palette entries, not just one per mesh). Process note worth keeping: a headless verification script hung indefinitely for reasons never root-caused — add progress prints and a hard timeout by default rather than trusting a long wait as progress.
- **`m2304b0` window one-sidedness — root-caused and fixed (2026-07-25), fully described in docs/ARCHITECTURE.md.** `FLVER0.Mesh.CullBackfaces` was correctly parsed off disk but never once read anywhere in `FlverModelBuilder.cs`. Corpus-scanned before fixing: 713/3411 files have at least one affected mesh; separately found 39 real files where meshes with different `CullBackfaces` share one `MaterialIndex` (a second latent bug — `GetOrBuildMaterial`'s cache key gained `CullBackfaces` alongside `materialIndex`). Deliberately scoped to `StandardMaterial3D` only, matching where the reported bug actually lived — `ShaderMaterial`'s cull mode is a compile-time keyword, so the 338 lightmap-path double-sided meshes are still open (see ARCHITECTURE.md's "Known deferred work"). Process note: this exact suspect had been named once already (the rigid-node entry above) without being followed through — naming a plausible cause isn't the same as ruling it out.
- **Post-`CullBackfaces` sweep (2026-07-25) — systematically checked every unread FLVER0/MTD field against what `FlverModelBuilder.cs` actually reads; three real fixes shipped, three more found and deferred.** Shipped: `g_SpecularPower`→roughness extended from chr/parts to the lightmap/blend `ShaderMaterial` family (63% of all materials in the game, previously untouched — refactored into a shared `ResolveMtdShading()`); `g_DiffuseMapColor`/`g_DiffuseMapColorPower`, a real per-material tint read by nothing before this; `g_BumpMapSmoose` on water materials. Found and deferred (write-ups in ARCHITECTURE.md's "Known deferred work"): `g_BlendMode` (doesn't correlate cleanly with the existing filename heuristic), `g_LightingType` (applied unconditionally at the time, not yet gated on), and a real `g_IsGhost` material family needing its own shader. Ruled out: `FLVER.Node.Flags` (always `0` across 51,923 nodes — not a real signal in DeS data), `Tangent`/`Bitangent` (real but low-impact vs. Godot's auto-generation).
- **The lightmap/blend roughness fix immediately regressed most map surfaces into a washed-out, glassy sheen (2026-07-25) — root-caused, "fixed," then found NOT actually fixed, then reverted outright the same day.** Root cause diagnosed as a pre-existing `metallic = spec` line, invisible before because `ROUGHNESS` used to default to Godot's fully-rough `1.0` — with zero `WorldEnvironment`/reflection probes anywhere, a nonzero `METALLIC` at real (lower) roughness reads as a flat misplaced sheen with nothing real to reflect. First fix (`metallic = 0.0`) did **not** actually resolve it on user re-test — the diagnosis was plausible and internally consistent but wrong, or not the whole story. Rather than keep guessing same-session, the whole roughness/metallic change on this material family was reverted outright (not commented out — matches this project's standing convention for abandoned attempts, see the PS3-deswizzle entry above), keeping only the unrelated diffuse-tint read and the original chr/parts roughness fix. Needs real `WorldEnvironment`/lighting groundwork and probably `g_LightingType` gating before it's worth re-attempting — see docs/ARCHITECTURE.md's "Known deferred work."   - **The map/lightmap family genuinely has NO directional lights — confirmed, and it kills a planned change.** Cross-tabulating the hemisphere-blend signature (`(N.y + c) / 2.`) against directional `dot(normal, constant)` terms across all 228 real shaders: **44 shaders have the hemisphere blend with zero directional terms** (HemEnv), 43 have hemisphere + directional (HemDir3). Directional-term counts are **only ever 0, 3, or 6, never 1 or 2** — 3 = three diffuse N·L, 6 = three diffuse plus three specular R·L, exactly matching `MTD.LightingType.HemDirDifSpcx3`. So adding `LIGHT_BANK`'s directional trio to the lightmap shader would be adding light the real engine does not apply to those materials. The trio belongs to `g_LightingType=1` (chr/parts/obj) only. A plan to "fix the waxy walls with directional lights" was dropped on this evidence.
  - **The real cause of the flat/"waxy" look, and it needs no new lighting data at all.** A real HemEnv shader (`FragmentProgram124`) reconstructs a full per-pixel normal from the bumpmap - samples a 2-channel tangent-space normal, rebuilds Z as `sqrt(1 - (x²+y²))`, builds a TBN basis by cross product, transforms to world space - and then uses that per-pixel normal `h6` for **both** the hemisphere blend factor (`(h6.y + c) / 2.`) **and** the env cubemap reflection vector (`TEX3D(11, h6.xyz)` off a reflection built from `h6`). This project's shaders do neither: `hemisphere_ambient()` blends on `world_normal`, a varying computed from the *vertex* normal in `vertex()`, and the env term is a flat lightmap sample with no normal dependence whatsoever. `NORMAL_MAP` is assigned but only feeds Godot's own lighting response, and there are no lights in the scene - so **every lighting term in the lightmap family is currently blind to the normal map**, which is exactly why engraved relief disappears. Fix is per-pixel normals in the hemisphere term, not more light sources.
  - **The tonemap operator is reconstructable analytically - no runtime LUT capture needed.** `tonemapbank.paramdef`'s own descriptions: `grayKeyValue` "larger → screen brighter, smaller → darker"; `minAdaptedLum` "make smaller to adapt to seeing in dark places"; `maxAdapredLum` "make larger to adapt to bright places"; `adaptSpeed` "speed of light/dark adaptation"; `bloomBegin` "starts to bleed when luminance exceeds the threshold"; `bloomMul` "multiplied above the threshold (0 = no bleed)". That is Reinhard 2002 photographic tone reproduction with a temporally-adapted luminance clamped to a `[min, max]` window - so `DS_Fil_HDR`'s 1D LUT is a tabulation of a curve we can rebuild from authored values. Supersedes docs/DIG-era "needs runtime instrumentation" framing for the *operator*; the LUT's exact contents still aren't captured, but no longer need to be.
  - **Godot's Compatibility (opengl3) renderer is RGBA8 low-dynamic-range with no HDR viewport or HDR output** (per Godot's own renderers doc). This settles an architectural fork: a `CanvasLayer`/`hint_screen_texture` post-process pass **cannot** recover clipped highlights, because clipping already happened in the 8-bit framebuffer. Any DeS transfer function has to be applied **in-shader, before writing `ALBEDO`** - which suits this project, since these shaders already hand-compute a final colour. (An older Godot status article also states the OpenGL3 renderer works in sRGB space rather than linear, unlike the Vulkan renderers; not confirmed against current docs, worth verifying separately before relying on it.)
  - **Incidental independent confirmation:** a real terrain-blend shader (`FragmentProgram11`) does `fma(diff_color.wwww, layerB - layerA, layerA)` - i.e. the two diffuse layers are lerped by **vertex-colour alpha**, confirming from engine bytecode the `COLOR.a`-is-the-blend-weight finding this project derived statistically back in the terrain-blend work.

- **Lightmap/drawparam system, part 17 — env cubemap decoding built and verified (2026-08-27), the prerequisite slice for a real env term. No shader consumer yet, so no visual change.** Chosen as the first implementation step because it was the one genuine unknown gating everything else, and it carries zero visual risk.
  - **Pfim silently decodes only face 0 of a cubemap.** Handed a valid 6-face DDS from `Headerizer`, it returns one face plus its mip chain (a 64x64 `m01` cubemap came back as 21952 bytes = exactly one face + mips) with no error. Worked around by re-wrapping each face as its own single-image DDS: copy the 128-byte header, zero `dwCaps2` (offset 112) to clear the `CUBEMAP_ALLFACES` flags, append that face's slice, decode. Face stride is always an exact sixth of the headerized payload - verified on both real layouts (`m01` block-compressed with per-face mips, 2744B; `m02` uncompressed 32x32, 4096B). This reuses Pfim's DXT decoding instead of reimplementing block decompression.
  - **Cubemap faces decode to two different Pfim formats in real data** - `Rgba32` for `m01`, `Rgb24` for `m02`. The existing 2D `DecodeTexture` throws on anything but `Rgba32`, so a naive reuse of that path would have rejected half the corpus.
  - **`Cubemap.get_layer_data()` returns blank images under the Compatibility renderer** - confirmed with a control: a cubemap built in pure GDScript from six known solid colours also read back as `0.00` on every face. So it is a Godot readback limitation, not a decode bug, and **cubemap contents cannot be verified by reading them back** in this project at all. The working verification is to *render* with them: bind to a `samplerCube` uniform, sample the six axis directions across a `ColorRect`, and read the rendered viewport image. That returned non-zero, per-face-distinct values whose extremes matched the pure-C# harness (face 4 brightest, face 3 darkest), and it doubles as proof that **`samplerCube` binding works in the Compatibility renderer** - which the eventual env-term shader depends on.

Verified: build clean, zero shader errors under a real `opengl3` driver across all 8 shaders, and on a real Nexus load **335 of 335 surfaces bound a real per-situation cubemap with zero white fallbacks**, with `use_normal_map` true on 225 and false on 110 (the materials that genuinely ship no bumpmap). **Expected visual direction, worth stating before testing:** the env term changes from `lightmap × 3.0` to `lightmap × cubemap × 3.0`, and real cubemap samples run ~0.1-0.5, so the env contribution drops roughly 3-5x. Scenes should get **darker**, not brighter — the opposite of the hemisphere-diffuse regression. - **Lightmap/drawparam system, part 19 — the whole output stage built and wired (2026-08-27): per-material fog, the transfer function, and per-channel tone correction, plus the discovery that these shaders were never really being lit by anything we controlled.** Landed as one unit because all three are per-material stages in the real engine and a half-built transfer function isn't testable.
  - **The finding that reframes every earlier brightness judgement: the lightmap family's shaders were lit by the 3D editor viewport's default preview sun and sky.** They were ordinary lit `spatial` shaders writing `ALBEDO`/`EMISSION`, in a scene with no light nodes and no `WorldEnvironment` — under which Godot's diffuse contribution is zero and only `EMISSION` survives. Since the maps visibly showed diffuse texture, something *was* lighting them, and the editor's preview environment is the only candidate. That means an arbitrary, blue-tinted sky ambient was scaling everything, and **every "too bright"/"too dark"/"too cool" reading in parts 15-18 was taken through it** — including the user's own observation that the editor look leans white/blue against RPCS3's warmer cast. Fixed by making the whole family (plus `terrain_blend.gdshader`) `unshaded`, which is what DeS does: its material shaders emit a finished pixel. `EMISSION`/`NORMAL_MAP`/`METALLIC` are gone and the envSpc term is summed straight in. **Worth carrying forward as a general trap: a Godot shader that hand-computes a final colour must say `unshaded`, or the editor silently becomes an uncontrolled input to it.**
  - **The transfer function collapses DeS's two output steps into one curve, on purpose.** The engine divides by a per-shader exposure constant in the material shader, then runs `DS_Fil_HDR` — a 1D LUT tabulating Reinhard 2002 — over the result. Since the LUT *is* that curve, the constant cancels and evaluating the curve directly on the HDR value is the composition of both. That also sidesteps needing the constant, which the dumps don't expose. Per channel, not on luminance, because a 1D LUT is by construction a per-channel curve.
  - **One value in the output stage is not authored data: adapted luminance.** The engine measures the frame's own average luminance and clamps it into `[minAdaptedLum, maxAdapredLum]`; Compatibility can't read frame luminance back. `FlverLoader` passes `minAdaptedLum` (`m01`: 0.08) as the value a dark interior would settle at, kept as a uniform so a bright exterior can be given the other end. Everything else — fog distances/colour/density, `grayKeyValue`, brightness/contrast/saturation/hue — is read straight from the banks.
  - **The bank data says the missing warmth is real and was reachable all along.** `m01`'s tone-correct row 0 is `brightness (0.80, 0.87, 0.83)`, `contrast 1.1`, `saturation 0.9` — relative to its own maximum that is a green-leaning, slightly desaturated cast, which is the direction the user described RPCS3 as leaning. **189 of 209 `m01` parts use `ToneCorrectID=0`** and 197 use `ToneMapID=0`, so this is the Nexus proper, not an edge row. Fog row 0 is literally named `神殿部分` ("temple section"): begin 10, end 220, colour `(54, 50, 120)` — the blue haze visible in the RPCS3 reference.
  - **Verified before hand-off, under a real `opengl3` driver:** all 8 shaders compile, and on a real `m01` load **335 of 335 surfaces bound output-stage uniforms** alongside the light-bank ones. Rendered stills from inside the Nexus (see the camera trick below) show engraved wall relief clearly readable and shadowed areas holding their contrast — the "waxy" complaint from part 16 — with a warm-neutral rather than blue-white cast.

- **The atmosphere / output-stage investigation (parts 20–33, 2026-08-28), condensed.** Current truth is the shader + `docs/ARCHITECTURE.md`'s output-stage section + parts 35–37; this is the journey, kept for the elimination record and the standing lessons.
  - **What it is.** The Nexus/outdoor atmosphere is Hoffman & Preetham real-time outdoor light-scattering — `LIGHT_SCATTERING_BANK` carries the model's parameters under the paper's own field names (`lsBetaRay`/`lsBetaMie`/`lsHGg` = Henyey-Greenstein asymmetry / `inscatteringMul`/`distanceMul`/`blendCoef`), addressed by `MSBD.Part.ScatterID`. Traced from the *vertex* programs (`tc8`/`tc9` in 67 of 110 VPs; the fragment side is just `result * tc8 + tc9`). Decisive number: `m01` scatter row 0 (`神殿部分`, same name as `FOG_BANK`/`LIGHT_BANK` row 0) sets `blendCoef=100`, white sun 200%, `lsBetaRay=6.0` — so the Nexus haze is white-light Rayleigh scatter. (`FOG_BANK`'s violet `(54,50,120)` was said here to "contribute zero" — **corrected by part 45**: it does contribute as a `mix()` target, but m01's strong scattering washes it out at distance, so the *conclusion* held for m01 even though "contributes zero" was too strong.) (Also confirmed: `: source_color` is a no-op under Compatibility — a hinted and a plain `vec3` uniform render identically, part 44.)
  - **Initial approach, all wrong or unverified:** a `FOG_BANK` linear-fog lerp on every surface; textbook λ^-4 wavelength weights dropped in unchecked; a normalization inferred not read; `scatter_distance_scale` fitted by eye. ~10 rejected iterations across those four before parts 35–37 settled it by measurement.
  - **Bytecode findings that stuck** (now in the shader + ARCHITECTURE.md): `blendCoef` is a strength dial — `tc8 = mix(1, Fex·c105, blend)`, not a crossfade between banks. Distance is the raw radial `|V|`, fed to the exponent **un-clamped** (clamping to [0,1] saturates the curve and kills the per-channel split that makes scattered light blue). `exp2`, not `exp` (the instruction is `EX2`, folding `ln2` into the scale). The literal pool holds `c466 = (1/1024, 1/ln2, 1/ln2, 1)` (`c466.w = 1` is the `(1-Fex)` factor) and `c467 = (3, ~0.5, ~2.0, 0)` (understood in part 37 as the shadow-atlas remap constants). Everything left in the scattering chain is one CPU-computed vec3 (`c104`/`c108`/`c109`) — "wavelength split" and "distance scale" are the *same* vector, which is why every single-knob fit failed.
  - **The rejected iterations, one line each:**
    - **Normalization:** per-channel `/betaTotal` cancels the wavelength split (ceiling B/R → 1.06) — rejected. Re-added as a *scalar* divide (part 33); part 35 confirmed the fold is scalar from measured `c108`/`c109`.
    - **Wavelength weights:** λ^-4 → λ^-1.5 (fit to one reference number) → **measured** from `.rrc` captures (part 35): Rayleigh 1:1.30:1.87, Mie 1:1.69:3.50, stable across four areas.
    - **`scatter_distance_scale`:** fitted at 2.5e-5, 1.66e-4, 4.0e-5, 6.73e-4, 3.5e-3 and rejected or re-anchored every time. **A parameter that fails across a >100× range means the model around it is wrong** — the model was fixed by measurement; the scale itself is still an open fit, deferred to the screen-space pipeline work.
    - **`FOG_BANK` composition:** crossfade vs series against the scattering — both produced a violet Nexus. Part 36 removed the RSX-fog `des_fog()` as unused; **part 45 then found `FOG_BANK`'s colour IS used** as a `mix()` target in the HemEnv epilogue and re-added `des_fog` correctly. The "violet Nexus" from the early attempts was the blanket-lerp-on-everything, not this bounded per-distance fade.
    - **`des_tone_correct` contrast:** convention pivot → `pow` (on an invalid inference from `DS_Fil_HDR_ColAdj` having no float literals) → back to pivot (part 33), once the accurate haze lifted the pivot's ~0.027 black point. **"Shadowed geometry too dark" was missing-atmosphere all along** — not the tone curve, not missing point lights (both were chased). Don't reach for the tone curve for that report.
    - **`LIGHT_BANK`'s diffuse-hemisphere pair (`colA_du`/`colA_dd`):** 5–30× the ambient pair on real rows; wired three ways (flat ×2, lightmap-gated) and every one flattened the Nexus or washed it to beige. This engine's visible contrast is the *ratio* between a small shadow floor and a much larger lit floor; a big flat constant added to both collapses it regardless of the transfer function. **Not read now; do not re-add without a full pipeline to judge against.**
  - **Reusable measurement facts:** `m01` also contains the entire Old One endgame area (a flat ~1.4 km terrain plane reached via a shaft below the Nexus). Measure per-piece FLVER *header* bounding boxes — not the aggregate (contaminated by that terrain), and not MSB placement transforms (identity for map pieces; their vertices are already world-space). Nexus-proper pieces run 170–330 units, matching `FOG_BANK.fogEndZ = 220`. 1 unit = 1 metre (character models 1.73–1.76 tall).
  - **The reasoning-failure meta-lesson** — parts 21/22/23/26/29 each caught a distinct one in themselves: textbook-formula substitution for a trace gap; fitting N knobs against fewer than N independent observables (produces a number that satisfies the metric and is wrong in every particular); treating a real observation as proof of a mechanism it doesn't constrain; writing a justification without checking it against evidence already in hand. When a reading from real data renders wrong, the failure has been *composition* every time — but "the data is right" does not license fitting a constant to make the picture match; that just moves the error somewhere unmeasured.
  - **Structural note, still true:** DeS applies tonemap *and* per-channel brightness/contrast as a **single** per-channel 1D LUT (`DS_Fil_HDR` is five instructions, all curve content baked CPU-side — part 26). This project models them as two sequential steps (`des_tonemap` + `des_tone_correct`) — a shape difference, not just parameters; `des_tone_correct`'s pivot contrast is not engine-accurate, kept because the real curve is unrecoverable. **User verdict:** "about the closest we can get it for now… still something missing, revisit after VFX and bloom." Not "engine-accurate solved."

- **Part 24 — the "rainbow speckle / swimming reflections" regression on most maps was the uncompressed-cubemap decode path (2026-08-28).** `Pfim` reports an uncompressed ARGB8888 cubemap face as `Rgb24` and reads 3 bytes/pixel out of 4-byte data → channels rotate on a four-pixel cycle (a literal RGB rainbow). Maps split cleanly on format: DXT1 (m01/m03/m05/m07) fine, uncompressed (m02/m04/m06/m08/m99) broken — the two symptoms are the EnvDif (normal-sampled → static speckle) and EnvSpc (reflection-sampled → swims with camera) lookups. **Lesson:** an earlier revision wrote the misread down as a feature ("faces come back in two formats"). When a decoder reports an unexpected format, **check the byte budget first** — 32×32 Rgb24 = 3072 bytes but the face stride was 4096 = exactly 4 bytes/pixel. **Fix:** uncompressed faces bypass Pfim, read straight as A,R,G,B (byte order confirmed — first byte is a constant `0xFF`), base level only, Godot regenerates mips. Verified by rendering across all nine maps. **Scope note:** shipped alongside the cubemaps in part 17, so any m02 visual judgement from that window is suspect; m01/Nexus unaffected.

- **Part 34 — the anonymous RPCS3 shader captures were named against the dev shader library, and the disassembled references drove three shader fixes plus a bloom approximation (2026-08-31).** Tooling is `tools/RsxShaderMatch`, a standalone console app excluded from the Godot build.
  - **Why this was possible at all:** `mounted/shader/ds_flver/*.fpo` (1215 fragment programs) each keep the dev's build path as a filename (`DS_Phn_DifSpcBmp______Csd_HemDir3.fpo` etc.) but have the parameter-name table stripped (part 13). RPCS3's `shaderlog/FragmentProgramN` dumps are readable GLSL but carry no names. Matching one to the other recovers the name.
  - **The `.fpo` format, confirmed corpus-wide (1421/1421 parse):** a FromSoft wrapper (`FF 0F 0F 11` fragment / `FF 0F 00 11` vertex, u32 payload offset at `0x04`) around a big-endian Sony `CgBinaryProgram` + raw RSX microcode. Invariants that held on every file: `totalSize == fileLen - cgOffset`, `ucodeSize % 16 == 0`, `instructionCount*16 == ucodeSize`, fragment `parameterCount == 0` (stripped), vertex keeps the table with names nulled.
  - **RSX fragment microcode decode:** 4×u32 big-endian per instruction, then a 16-bit halfword swap (`(d<<16)|(d>>16)`); `opcode = ((w0>>24)&0x3F) | (((w2>>31)&1)<<6)`; an inline 128-bit constant follows when any source `reg_type == 2` (step 32 bytes instead of 16, value shipped as zero and patched per-draw); NV output scale in SRC1 bits 28-30 (`_x2`/`_x4`/`_x8`/`_d2`/`_d4`/`_d8`); walk until `OPDEST.end`. RPCS3's `CgBinaryFragmentProgram.cpp` (`CgBinaryDisasm::TaskFP`) and `ShaderParam.h` were the ISA reference. - **Part 39 — shadow research pass: what DeS actually does (2026-09-03).** Prompted by part 38's "shadows from things I can't find". Three prongs: unread `MSBD.Part` fields, the `SHADOW_BANK` drawparam, and the `DS_*_Sdw` fragment disasm + `rrc-shadow`.

  **1. `MSBD.Part` carries a full visibility/shadow control set that `MsbLoader` reads none of:** `uint[4] DrawGroups` + `uint[4] DispGroups` (128-bit masks, "controls when the part is visible"), `ShadowID`, `LodParamID`, `IsShadowSrc`/`IsShadowDest`/`IsShadowOnly`, `UseDepthBiasFloat`, `DrawByReflectCam`/`DrawOnlyReflectCam`. Dumped across `m03_01_00_00.msb`:
  - **`DrawGroups`/`DispGroups` gate what is in the scene at all.** m03_01: every one of 70 MapPieces has a *unique* DrawGroup mask; all MapPieces share *one* DispGroup; the 51 Collisions carry *46 distinct* DispGroup sets. The FromSoft rule (unverified for DeS but consistent): a renderable part draws when its `DrawGroups` intersect the *active* `DispGroups` — those of the Collision the player is standing on. **We render every part in the block simultaneously**, so Boletaria 1-1's overlapping upper/lower routes are all present and all shadow-casting at once → the "casters I can't find". This is the dominant cause, and it is the **core map-assembler prerequisite** (`docs/PLAN.md` Phase 1 item 4), not shadow-specific.
  - **`IsShadowSrc`/`IsShadowDest`/`IsShadowOnly` are `0` on every m03_01 part** — either inverted semantics or SoulsFormatsNEXT's `MSBD` field names are mis-mapped guesses (all `/// Unknown.` in the source). **Not usable as-is.** Whether a part casts is better taken from the RSX frame or "all lit geometry casts".

  **2. `m<XX>_shadowbank.param` (`SHADOW_BANK`, indexed by `Part.ShadowID`)** — real per-map, per-group shadow tuning, completely unused by this project:
  - `lightDegRotX/Y` — the shadow's **own** light direction, per group, **separate from `LIGHT_SCATTERING_BANK`'s sun** (Nexus temple X50/Y0; Old One "地下世界" X25/Y10; m03_01 "基本" X60/Y140; m02 B0 X50/Y60). ShadowRenderer currently uses the scatter sun — wrong source.
  - `endDist` — shadow region size: **10–70 world units**, camera/player-relative — *not* a whole-map region. The capped-400 v1 region is ~10× too big.
  - `fadeBeginDist`/`fadeDist` — the shadow **fades out** before the region edge, so the boundary is never visible (m03_01 row 0: fade 10→20).
  - `densityRatio` — shadow darkens by at most **60–100%**, never full black.
  - `colR/G/B` — shadow may be **tinted** (mostly 0, but m03_01 objects row 2 `colB=20`).
  - `depthOffset` ≈ **−0.01** (a few −0.02…−0.15) — the constant depth bias, and `persedDepthOffset` (slope term) ≈ 0: DeS relies on the *small region* keeping texels fine, not on slope-scaling.
  - `shadowVolumeDepth` 1–50 (ortho depth along the light axis), `calibulateFar` 0–50, `radFactor` ≈ 0 (no PCF-kernel scaling).

  **3. `DS_Phn_DifSpcBmp___LitSdw_HemEnvLerp` disasm + `rrc-shadow` (`rsxshadermatch`):**
  - Receive is **hardware shadow compare**: `TXPR` (projective texture + hardware depth compare) on `tex7`, a single fetch (hardware 2×2 PCF if the sampler is linear). **No manual multi-tap kernel** — our manual 3×3 is already more than DeS does.
  - The projected coord is clamped into an **atlas sub-tile** (`c[2]`/`c[3]` = tile min/max) even in the single-`Sdw` variant — the 2048² / 2×2×1024² atlas is always the target; `Csd` selects among 4.
  - **No shader bias op** — bias is folded into the per-split cast matrix CPU-side (matches `depthOffset` being a bank value). `rrc-shadow` shows no bias constant in `c[466]`/`c[467]` (`= (1/1024, log2e, log2e, 1)` / `(3, ~0.5, ~2.0, 0)`, every frame — texel, pass-id, clip→UV half-scale, 2048/1024 tile ratio).
  - **Gate = `MINH H0, shadowTerm, lightmap`** where `shadowTerm = 1 − (fadeScaled·densityColor)·compare` — a *partial, distance-faded, tint-capable* darkening, `min`'d with the lightmap and applied to the **env/spec term only**; `result = env·gate + hemisphere`, hemisphere ungated. Our composition point is right; the shadow *term* (`mix(1, pcf, strength)`) is the oversimplification.
  - `rrc-shadow` per-split caster counts: **136–470 per split**, near split densest, ~2× region growth per cascade; enclosed views render 2 tiles, open views 4. A whole m03_01 load is 408 casters — DeS spreads a similar total across 4 small splits.

  **Implication — the v1 region shape is wrong.** DeS's shadow is a **small (~10–70 unit) region that follows the camera**, edge hidden by a **distance fade**, applied as a **partial (`densityRatio`) tint-capable** darkening, lit from **`SHADOW_BANK`'s own direction**. And **draw/disp groups gate which geometry exists at all** — the biggest fix, shared with the map-assembler. Revised shadow design in `docs/PLAN.md`'s shadow item.

## C#/Godot interop gotchas worth remembering

- `ShaderMaterial.SetShaderParameter()` from C#, for a shader uniform hinted
  `: source_color` (e.g. `uniform vec3 water_color : source_color`), needs a `Color`, not
  a `Vector3` — passing `Vector3` doesn't throw, it silently no-ops (the parameter reads
  back `null` via `get_shader_parameter()`, as if never set, while every other
  non-color-hinted uniform set the same way works fine). Found by inspecting an imported
  water material headlessly and noticing exactly the color-hinted uniforms were null.
- **A method whose signature uses a non-Variant type (a custom `record struct`, `PARAM.Row`, a
  nullable struct) is not exposed to GDScript at all** — calling it fails with `Invalid call.
  Nonexistent function '<name>' in base '<Class>.cs'`, not a marshalling error, so it reads like
  the method is missing. Since throwaway GDScript check scripts are this project's only
  verification path, a C# API meant to be *verified* has to return Variant-compatible types
  (`Godot.Collections.Dictionary`/`Array`, `string[]`, primitives). Found 2026-08-27 on
  `DrawParamReader.GetEnvCubemapNames`.
- **`ImageTextureLayered.get_layer_data()` (so `Cubemap`, `Texture2DArray`) returns blank images
  under the Compatibility renderer** — not null, not an error, just zeros, so it reads as "the
  texture is empty" rather than "readback is unsupported". Verified with a control built from
  known solid colours in pure GDScript. To check a layered texture's real contents, render with
  it and read the *viewport* image instead. Found 2026-08-27 while verifying env cubemaps.
- `ProjectSettings.GlobalizePath()` is a safe no-op on paths that are already absolute
  filesystem paths (not `res://`), so it's fine to call it even when unsure whether the
  path Godot hands you is virtual or already global.
- `Image.CreateFromData`'s `useMipmaps` parameter means "this buffer already contains a
  full mip chain" — not "please generate mips for me." Pass `false` and call
  `image.GenerateMipmaps()` yourself, or the base-level-only buffer gets rejected/
  misread.
- `StandardMaterial3D.Metallic` defaults to `0.0` and *multiplies* against
  `MetallicTexture` — setting the texture alone has zero visible effect without also
  setting `Metallic = 1.0f`.
- `MetallicTextureChannel` defaults to reading only the texture's Red channel. A true
  full-RGB spec map's G/B data is silently dropped. Known, accepted ceiling — not
  chased further since there's no PBR-correct slot for a Blinn-Phong spec map anyway
  without a custom shader.
- A `CSharpScript.new()` call can transiently fail (`Invalid call. Nonexistent function
  'new' in base 'CSharpScript'`) for the *first* headless invocation immediately after a
  project directory rename — Godot's own editor-side "is the C# assembly ready" tracking
  seems to be keyed off the old path. A `dotnet build` from the new location plus one
  throwaway import pass resolves it; it isn't a real code regression when it happens
  exactly once right after a move.

  builds — neither does; only the dedicated `.NET`/mono build does.
